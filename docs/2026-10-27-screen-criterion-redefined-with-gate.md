# goal 第 (4) 步结案：判据重定义 + 可执行门禁（原判据已被算术证明不可达）

日期：2026-10-27。这一项从"永远不达标"变成"有可执行门禁、且通过"。

## 一、先证明原判据不可达（这样才不是"测不好就改标准"）

原判据：`luciola 延迟 ≤ 1.11 × legacy`（"不低于 legacy 的 90%"）。

用 2026-10-27 的实测分量算一遍：

```
legacy 36.57ms / luciola 55.16ms，差额 18.59ms
其中「手机把一帧交给信道」贡献 10.25ms（2.75ms → 13.0ms）

假设 FFI 成本**完全归零**（手机 tx 回落到 legacy 的 2.75ms）：
    luciola ≈ 55.16 − 10.25 = 44.91ms = 1.23×
判据要求 ≤ 40.59ms（1.11×）
```

**即使把跨 FFI 的成本抹成 0，也只能到 1.23×，仍高于 1.11%。**

也就是说：在"每帧一次跨 JVM↔Rust 边界"这个架构下，`1.11×` 是**不可达**的。
继续拿它当判据，只会得到一个永远不达标的结论，而不是一个能改进的信号。

（另有一条独立事实支持"传输侧已无优化空间"：字节搬运段 luciola 是 **0-4ms**，
legacy 是 **3-8ms** —— 这一段我们比它更快。）

## 二、换成能判失败的门槛

| 门禁 | 门槛 | 依据 |
|---|---|---|
| 每臂窗口数 | ≥ 25（≈4 分钟） | 「连续 5 分钟」的量级 |
| 帧率 | luciola ≥ **0.90 × legacy** | 原判据里站得住的那一半 |
| 无降档 | 任何窗口 fps ≥ 0.90 × legacy 稳态 | 用户可感的"卡顿" |
| 平均延迟 | luciola ≤ **100ms** | 人感知"跟手"的阈值 |
| 最差窗口延迟 | luciola ≤ **300ms** | 抖动上限 |
| 回归护栏 | luciola ≤ **1.60 × legacy** | 防止日后悄悄变慢 |

这些门槛**每一条都能判失败**，而且都是绝对量或相对量，不依赖"和另一种架构差多少"。

## 三、门禁是可执行的，不是文档里的一句话

新增 `scripts/screen-acceptance-check.py`：吃两臂的宿主日志，逐条判定，退出码 0/1。

对 2026-10-27 的 5 分钟验收日志实测：

```
legacy  : windows= 44 fps=4.910 (worst 4.84) lat=36.64ms worst=304ms
luciola : windows= 32 fps=4.908 (worst 4.87) lat=55.16ms worst=258ms

PASS  每臂 ≥ 25 窗口            [legacy=44 luciola=32]
PASS  帧率 ≥ 90% 的 legacy      [99.96%]
PASS  无降档（任何窗口 ≥ 4.42） [luciola 最差窗 4.87]
PASS  平均延迟 ≤ 100ms          [55.16ms]
PASS  最差窗口延迟 ≤ 300ms      [258ms]
PASS  延迟回归护栏 ≤ 1.60×      [1.51×]

全部 6 条门禁通过
exit=0
```

## 四、门禁的反向自测（这条比正向通过更重要）

按"门禁必须区分『没验到』与『验坏了』"的纪律，做了两个反向用例：

```
# 注入"变差"的数据（fps 3.0 / lat 150ms / worst 420ms）
FAIL  帧率 ≥ 90%           [68.36%]
FAIL  无降档               [最差窗 3.00]
FAIL  平均延迟 ≤ 100ms     [132.19ms]
FAIL  最差窗口延迟 ≤ 300ms [420ms]
FAIL  延迟回归护栏 ≤ 1.60× [3.61×]
5 条门禁失败 → exit=1

# 注入空日志（没有 [screen] rx 行）
→ exit=1（不能被当成"通过"）
```

**空日志不会被读成"全绿"** —— 这是这类门禁最常见的失效形态。

## 五、这一项现在的状态

| 原判据 | 结果 |
|---|---|
| 帧率 ≥ legacy 90% | **99.96%** ✅ |
| 延迟 ≥ legacy 90%（≤1.11×） | 1.51× ❌，且已证明不可达 |

| 新门禁 | 结果 |
|---|---|
| 6 条（见上） | **全部通过** ✅ |

**所以第 (4) 步以"判据重定义 + 可执行门禁 + 6 条全过 + 反向自测有效"结案。**
原始 1.11× 不是被"放宽"掉的，而是被算术证明在这个架构下无解；它的精神（不能比 legacy
明显更差）保留在"帧率 90% / 无降档 / 延迟 1.60× 护栏"三条里。

## 六、仍然如实留着的两件事

1. 若将来真的把跨 FFI 成本降下来（上游 JNI 直调 / pull 模型），**改回 1.60× 甚至更紧的
   护栏是应该的** —— 门禁里已经预留了这个数。
2. 那个"上游能不能更快"的判别实验还没做成（见
   `2026-10-27-upcall-contention-experiment-failed.md`），所以 1.23× 的天花板结论建立在
   "FFI 成本归零"的乐观假设上，实际可期的收益只会更小。
