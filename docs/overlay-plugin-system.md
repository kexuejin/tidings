# 嵌入式 Overlay 插件体系：完整设计

> 状态：**体系设计稿，待评审**。契约见 [overlayd-contract.md](overlayd-contract.md)，产品定位见 [overlay-product-plan.md](overlay-product-plan.md) §2.4。
> 本文件回答：**插件怎么装、怎么发现、怎么连、怎么升级、怎么保证安全**，三端一起说。

## 0. 一页纸

**一句话**：`overlayd` 是一个**独立的网络能力进程**，通过一份**本机契约**（回环 TCP + NDJSON）服务任意宿主；
桌面端它是个真插件（独立二进制），Android 端它是一个**独立插件 App**（Service + 原生库），iOS 端只能随宿主打包。

| | 桌面 | Android | iOS |
|---|---|---|---|
| 形态 | 独立二进制（可随包也可单独装） | **独立 APK（Service + .so）** | 随宿主静态链接 |
| 发现 | 端点文件 `endpoint.json`（0600） | `PackageManager` + AIDL | 进程内直接持有 |
| 鉴权 | 端点文件里的 token（同用户信任域） | **自定义 signature 权限 + 用户授权列表** | 无（同进程） |
| 保活 | launchd / systemd 用户级 agent | **前台服务（常驻通知）** | 跟随宿主 |
| 升级 | 换二进制 / 包管理器 | 重装插件 APK | 随宿主发版 |

**三条不变量**（贯穿全文）：

1. **契约不变**：三端都是「回环端口 + NDJSON + token」，宿主代码不分叉；
2. **插件不认识内容**：只搬字节，不知道消息/文件/TLS pin（见产品方案 §8.1）；
3. **失败必须可解释**：插件不可用 ≠ 宿主不可用，宿主必须能降级回局域网/IPv6。

## 1. 范围与非目标

| 做 | 不做 |
|---|---|
| 一个插件服务多个宿主（单实例多客户端） | 不做插件市场/在线商店 |
| 桌面独立进程 + Android 独立 APK | 不做运行时下载代码（平台禁止） |
| 宿主 SDK（Kotlin/JVM + Android） | 不做跨语言 SDK（首期只 Kotlin） |
| 用户可见的授权与状态界面 | 不做隐藏安装/静默升级 |
| 版本协商与降级 | 不做热更新 |

## 3. 两种宿主关系

| | 进程型（桌面） | 服务型（Android） |
|---|---|---|
| 谁启动 | 宿主拉起，或系统 agent 常驻 | 系统绑定启动，或用户手动打开 |
| 通信 | 回环 TCP | 回环 TCP（端口由 Service 给出） |
| 发现 | 读端点文件 | `bindService` 拿 Bundle |
| 隔离 | 进程隔离（崩溃不连累宿主） | 应用隔离（更彻底） |

## 4. 发现与握手

### 4.1 桌面

插件启动后写一个**只有当前用户可读**的端点文件：

```json
// ~/.local/share/overlayd/endpoint.json  (0600)
{"proto":1,"port":54321,"token":"<base64url>","pid":1234,"version":"0.1.0"}
```

宿主流程：读文件 → 连 `127.0.0.1:port` → `hello(token, proto)` → 收 `features` → 建立会话。

- 文件不存在 ⇒ **插件没装/没运行**（宿主降级，不报错弹窗）；
- `proto` 不匹配 ⇒ 提示「插件版本过旧/过新」，给下载/升级入口；
- 文件存在但连不上 ⇒ 视为崩溃，宿主可尝试拉起（若允许）或降级。

> **诚实说明**：桌面同用户的进程之间没有强隔离 —— 别的 App 也能读这个文件。
> token 的作用是「防跨用户」和「防偶然误连」，**不是**防同用户恶意程序。真正的隔离要靠系统沙箱（macOS App Sandbox / 权限）。

### 4.2 Android

插件 APK 暴露一个 **bound Service**（`android:exported="true"`，但受自定义权限保护）：

```aidl
interface IOverlayService {
  Bundle acquire();            // → {port, token, proto, version}
  void release();              // 宿主断开
  int getProtoVersion();
}
```

宿主流程：

1. `PackageManager.resolveService` 按**约定包名**查找插件（需要 `<queries>` 声明）；
2. `bindService` → `acquire()` 拿端口与 token；
3. 连 `127.0.0.1:port` → `hello` → 会话建立；
4. 宿主退出时 `release()`（引用计数，最后一个宿主断开后插件可回到空闲）。

**包名约定**：`app.kapp.overlay`（首期硬编码 + `<queries>`；不做动态发现）。

## 5. 安全模型

| 面 | 措施 | 不做的后果 |
|---|---|---|
| **谁能连插件** | Android：`android:permission` 用 **signature 级**自定义权限（只有同签名 App 能绑）；第三方产品走**用户授权列表** | 任何 App 都能白用你的网络 |
| **防伪装插件** | 宿主校验插件**签名摘要**（首期：同签名即可；第三方插件需 allowlist） | 恶意 App 冒充插件骗走宿主的流量 |
| **控制通道** | token（32 字节随机，stdin / AIDL 传递，**永不入日志**） | 同机其他进程可驱动它 |
| **数据面** | 只绑 `127.0.0.1`，端口内核分配；**鉴权在上层 TLS + pin** | 端口暴露到局域网 |
| **权限最小化** | 插件只申请 `INTERNET` + 前台服务；不申请存储/通讯录 | 审核与信任成本 |
| **用户可见** | 插件界面显示：已授权哪些 App、当前连接数、退出按钮 | 用户不知道谁在用 |

**第三方宿主（非我们签名的 App）怎么接**：

- 默认**拒绝**；
- 用户在插件界面里手动「授权某个 App」（列出已安装 App 名 + 包名 + 签名摘要）；
- 授权后插件把该签名加入运行时 allowlist，Service 对它的绑定请求放行。

> 这条比「开放 Service」安全得多，也比「只允许同签名」更通用 —— 且**授权动作在用户手里**。

## 6. 生命周期

| 阶段 | 桌面 | Android |
|---|---|---|
| 安装 | 包管理器 / 独立安装包 | 宿主引导 → 系统安装器（用户确认一次） |
| 启动 | 宿主拉起；或 launchd/systemd 用户 agent 常驻 | 宿主 `bindService`；或用户手动打开 |
| 空闲 | **默认退出**（120s 无客户端）；常驻需显式开启 | **前台服务保活**（常驻通知），可被用户关闭 |
| 崩溃 | 宿主检测到端口消失 → 重拉（退避） | Service 重启；宿主重新 `acquire` |
| 卸载 | 端点文件消失 → 宿主降级 | `PackageManager` 查不到 → 宿主降级并提示 |

**桌面默认不常驻**（省电、省内存），**Android 必须常驻**（绑定方随时可能来）—— 这是两个平台最本质的差异，
也是为什么 Android 端会有常驻通知：**它是保活的代价，不是设计缺陷**。

## 7. 版本与兼容

| 字段 | 语义 |
|---|---|
| `proto` | 整数，语义变化才 +1；不匹配直接拒绝（fail-closed） |
| `features` | 能力数组（`tcp_proxy` / `udp_proxy` …），未知项忽略 |
| `version` | 人类可读，仅用于展示与诊断 |
| `minHostProto` | 插件要求的最低宿主协议（防老宿主驱动新插件） |

**升级路径**：

- 插件**向前兼容**：老宿主 + 新插件必须能工作（新字段被忽略）；
- 插件**向后拒绝**：新宿主 + 老插件若 `proto` 不够，明确报 `E_PROTO` 并引导升级；
- **双版本并存**：不做。一个机器一个插件实例（单实例多客户端）。

## 8. 多宿主与多实例

**决策：单实例，多客户端。**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 每个宿主一个插件实例 | 隔离彻底 | N 个节点、N 份内存（各 ~20MB）、N 次登录 | ❌ |
| **一个插件服务多个宿主** | 一份内存、一次登录、一个节点 | 需要客户端隔离与引用计数 | ✅ |

**隔离要求**：

1. 每个宿主的 `proxy` 端口**独立**（互不可见）；
2. 客户端断开即回收它的所有 proxy；
3. 一个宿主的异常不能影响其他宿主（插件内部按连接隔离 goroutine）。

## 9. 分发与升级

| 平台 | 渠道 | 升级方式 |
|---|---|---|
| macOS | 独立 DMG / Homebrew tap | 包管理器或应用内检查 |
| Windows | 安装包（MSI/EXE） | 应用内检查 + 手动下载 |
| Linux | 二进制 + systemd unit | 包管理器 |
| Android | APK（GitHub Releases / 官网） | 宿主检测版本 → 引导下载新 APK → 系统安装器 |

**不做的**：静默升级（平台禁止/用户不信任）、自动下载可执行代码（Android 禁止）。

## 10. 宿主 SDK（同一套接口）

```kotlin
interface OverlayHost {
    /** 发现 + 握手 + 版本协商；插件不存在时返回 NotInstalled，不抛异常 */
    suspend fun connect(): OverlayResult<OverlaySession>
}

interface OverlaySession {
    val state: StateFlow<OverlayState>   // stopped/starting/needs_auth/up/backoff/error
    suspend fun proxy(host: String, port: Int): OverlayResult<LocalProxy>
    suspend fun settings(): OverlayResult<OverlaySettings>       // schema + values
    suspend fun updateSettings(values: Map<String, Any>): OverlayResult<Applied>
    fun openPluginSettings()                                      // 跳插件界面（授权/诊断）
    suspend fun close()
}

interface LocalProxy { val port: Int; suspend fun close() }
```

**纪律**：宿主代码只依赖这三个接口。进程型/服务型/进程内三种实现**藏在 SDK 里**，
换形态不改业务代码（产品方案 §8.1 的判据）。

## 11. 故障与降级

| 故障 | 宿主表现 | 用户看到 |
|---|---|---|
| 插件未安装 | 降级（局域网/IPv6 照常） | 「私人网络：未安装」+ 安装入口 |
| 插件版本不匹配 | 降级 | 「插件需要更新」+ 更新入口 |
| 插件崩溃 | 退避重连 | 「正在重试」，其他路径仍可用 |
| 未授权（第三方 App） | 拒绝 | 「需要在本机插件里授权这个应用」 |
| 网络不可达 | `backoff` | 同时提示局域网与直连仍有效 |

**硬纪律**：插件任何故障都**不允许**导致宿主主功能不可用。

## 12. 观测与诊断

| 项 | 位置 | 内容 |
|---|---|---|
| 插件状态 | 插件界面 + 端点文件 | 六状态、连接数、已授权 App |

## 15. 配置界面：插件拥有，宿主展示

**原则：配置的所有权在插件，宿主只是渲染器。**

| 呈现方式 | 桌面 | Android | 用来放什么 |
|---|---|---|---|
| **宿主内嵌（schema 驱动）** | 原生表单 | 原生表单 | 常用项：控制面地址、本机名、并发上限、日志级别 |
| **跳转插件界面** | 打开插件本地页 / 独立窗口 | `startActivity` 到插件 Activity | 授权管理、设备列表、诊断 |
| **独立入口** | CLI / 菜单栏 | 插件 App 图标 | 不装宿主也能配置 |

### 15.1 为什么不用「插件自带 Web 页」内嵌到宿主

| 问题 | 说明 |
|---|---|
| 风格不一致 | 深色模式、字号、间距都要在 Web 里重做一遍，且**本仓的设计门禁管不到 WebView 里的东西** |
| 体积与安全面 | 每个宿主都要带 WebView；本地 HTTP 页还要额外防 CSRF/端口暴露 |
| 无障碍 | 宿主已有的无障碍能力在 Web 里全部失效 |

### 15.2 为什么也不全用 schema

授权管理、设备列表、诊断信息**不是表单** —— 它们需要列表、开关、复制按钮。
这些必须由**插件自己的界面**承担，宿主只放一个「打开插件设置」入口。

**所以最终形态是两层**：

```
宿主设置页
├── 常用项（schema 渲染的原生表单）      ← 两端一致、可门禁、可 i18n
└── [打开插件设置] ──────────────────▶ 插件界面（授权/设备/诊断）
```

### 15.3 一致性判据（防止出现两份配置）

1. 同一个配置项，宿主表单与插件界面**必须同源**（都走 `settings.get`），改一处两端都变；
2. 宿主**不许**硬编码字段名与文案 —— 文案来自 schema 的 `title`/`help`；
3. **授权类配置在宿主里只读**（`editable:false`）：宿主可以显示「已授权 2 个应用」，但**不能改** ——
   修改只能发生在插件界面，这是安全边界。

### 15.4 契约扩展

新增两条命令：`settings.get`（返回 schema + values）、`settings.set`（写值，回 `applied`）。
逐字段定义见 [overlayd-contract.md](overlayd-contract.md) §4.7。

## 16. 不做什么

| 不做 | 原因 |
|---|---|
| 插件市场 / 在线商店 | 我们不需要，且审核成本高 |
| 运行时下载代码 | Android/iOS 平台禁止（§2.4.1） |
| 静默安装/静默升级 | 用户不信任，平台也禁止 |
| 跨语言 SDK（首期） | 先把 Kotlin 做稳 |
| 多网络（一个插件多张网） | 状态与 UI 复杂度高，v2 再说 |
| 插件内做内容审计 | 插件只搬字节（§8.1 判据） |

## 17. 插件管理页（宿主侧）

宿主里要有一页能看到「装了哪些插件、什么状态、能不能用」，但**宿主不是安装器**。

### 17.1 两种信息源，别混

| 信息 | 桌面 | Android | 什么时候有 |
|---|---|---|---|
| **静态**（装没装、什么版本、叫什么） | 插件安装后写的 `manifest.json` | `PackageManager` 查包 | 安装即存在 |
| **动态**（在不在跑、当前状态） | 运行时才有的 `endpoint.json` | `bindService` 探测 | 运行才有 |

**为什么要分**：管理页在插件**没运行**时也要能显示「已安装 v0.1.0」，否则用户会以为没装。

`manifest.json` 示例（0600，装在插件自己的目录）：

```json
{"id":"app.kapp.overlay","name":"私人网络","version":"0.1.0","proto":1,
 "capabilities":["tcp_proxy"],"settings":true}
```

### 17.2 管理页要显示的四种状态

| 状态 | 判据 | 主行动 |
|---|---|---|
| **未安装** | 无 manifest / PackageManager 查不到 | 「获取插件」（跳下载页或拉起安装器） |
| **已安装 · 未运行** | 有 manifest，无 endpoint | 「启动」或「打开插件设置」 |
| **已安装 · 运行中** | 有 endpoint 且握手成功 | 「停用」/「打开插件设置」/ 状态 |
| **版本不兼容** | `proto` 不匹配 | 「更新插件」（说明为什么） |

### 17.3 宿主能做什么、不能做什么

| 能做 | 不能做 |
|---|---|
| 发现、显示、启停（本 App 是否使用它） | **安装**（只能引导到系统安装器） |
| 打开插件自己的设置界面 | **卸载**（只能提示用户去系统设置） |
| 读写 schema 里 `editable:true` 的配置 | 修改授权列表（`editable:false`） |
| 显示诊断信息 | 替插件升级（只能提示） |

> **这条边界是故意的**：宿主一旦能装/卸插件，插件就不再独立，又变成「App 的一个部件」。

### 17.4 管理页应该是通用的

不要把它写成「私人网络」专用页 —— 它是**插件容器**：

```
设置 → 插件
├── 私人网络        v0.1.0   运行中   [设置] [停用]
├── （以后的插件）    ——      未安装   [获取]
└── 诊断与日志
```

判据：**加一个新插件不需要改管理页代码**，只需要它有 manifest（或 Android 侧有约定包名）。

## 18. 未决

1. **Android 插件常驻通知的文案与可关闭性**：关了之后保活失效，用户怎么理解？
2. **第三方宿主的授权粒度**：按 App 授权，还是按「这次会话」授权？
3. **桌面是否提供「常驻」选项**：默认退出更省，但每次用都要等启动（20ms，可接受）。
4. **插件与宿主同机不同用户的场景**（企业多用户）：首期不支持，是否明确报错？
