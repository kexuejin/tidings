# 云推送（FCM / APNs）设计 · 供决策（task-23 ①）

> 状态：**设计稿，未实现**。本文件只描述形态、依赖、代价与取舍，不改任何生产代码。
> 相关：task-20 ③ / `docs/cross-network-keepalive-design.md`（K1 长连接）、task-13 /
> `docs/public-transport-security.md`（公网内容只走 TLS）、task-15（Android 前台服务保活）。
> 边界：本文不讨论"推送里带什么业务内容"以外的协议细节；协议帧一旦要定，另开一页。

## 0. 结论速览

1. **云推送的定位是"唤醒"，不是"搬运"**。首期只发 **data-only 唤醒帧**（不含消息正文），
   手机醒来后走 K1 长连接 / 离线队列把内容取回来。这样 Google / Apple 只看到"某台设备在
   某时刻被唤醒"，看不到消息内容 —— 与 task-13"公网内容只允许经 TLS 的 TCP 通道"的边界一致。
2. **它补的是 task-15 补不上的那一格**：task-15 的前台服务管"进程还活着但被系统打成 cached"，
   云推送管"进程已被杀 / 长时间离线 / Doze 里连 K1 都建不起来"。两者互补，不是替代。
3. **形态**：主机（或一台薄中继）→ FCM / APNs → 手机。手机不需要任何入站可达性，
   这正是"手机长期离网、连 K1 长连接都建不起来"时唯一还能到的通道。
4. **推荐选项 B（自建薄中继）**：中继只保存"设备令牌 + 在线与否"并转发一个不含内容的唤醒帧，
   不保存、不转发消息正文；凭据（FCM 服务账号 / APNs Key）与设备令牌集中在中继，不散落到每台主机。
   选项 A（主机直发）作为自托管兜底，选项 C（UnifiedPush）作为 Android 的自托管开关。
5. **不做会怎样**：手机长期离网时，消息只能等用户**主动打开应用**才到达；群消息、agent 进度、
   文件 offer 全部静默积压。"手机没推送"这个原始诉求原样留着 —— 这是本页要回答的问题。

## 1. 现状（先看清今天有什么、没有什么）

### 1.1 有：本地通知 + 跨网文本的第三条承载（设计稿）

| 能力 | 今天的状态 | 证据 |
|---|---|---|
| 收消息后弹通知 | **本地通知**，进程活着才发 | `PushNotificationHandler`（`PlatformContracts.kt:236`）明说"远程推送需要服务器"；`AndroidPushNotificationHandler.kt:25`、`IosPushNotificationHandler.kt:29` 都是本地 |
| iOS 后台到达 | **做不到**，等 APNs（P5） | `IosPlatform.kt:48` 逐字："真正的后台到达需要 APNs（P5），这是平台限制而不是实现偷懒" |
| 跨网下行 | K1 长连接（手机主动连主机，设计稿） | `docs/cross-network-keepalive-design.md` §0；**未实现** |
| 后台存活（进程没被杀时） | Android 前台服务保活（task-15，已实现） | `ConnectionKeepAliveService` + 设置里「后台保持连接」 |
| 离线消息 | 落盘队列，上线补发 | `handleRestoreMessages` / 队列契约 |
| "云"侧组件 | 有，但服务的是 **agent 控制面**，不是 P2P 消息 | `RemoteRelayConfig` / `RemoteRelayClient` / agentNode 控制面（Cloudflare Tunnel 形态） |

### 1.2 没有：任何"进程不在时把手机叫醒"的通道

今天能到手机的**只有**手机自己发起的连接（K1 长连接）或应用在前台。一旦：

- 进程被系统杀掉（内存压力 / 用户划掉 / 厂商省电清理），或
- 手机长时间离线（飞行模式、地铁、国外漫游、只在蜂窝上且主机地址全过期），

那么 K1 建不起来、task-15 的前台服务也不存在（它随进程走）—— 此时**没有任何路径**能让手机知道"有人给你发消息了"。
这正是云推送要补的洞。

### 1.3 现有通知策略必须被尊重（否则推送会绕过静音）

`RelaySettings` 里已经有 `notifyAgentMessages` / `notifyMentionOnly` / `notifyQuietHours` 三个策略，
以及"前台抑制"的既有语义（`PushNotificationHandler` 的 KDoc 明说前台抑制尚未做）。
云推送**不允许**成为绕过这些策略的第四条路：唤醒帧到达后，是否响铃仍由同一套策略决定；
免打扰时段只允许"静默唤醒 + 不响"，不允许"照响"。

## 2. 谁发、发什么、载荷里有没有内容

### 2.1 发送方

消息先落到**主机**（或中继）的队列里。发送方只有两类候选：

- **主机**（桌面端 / 另一台手机）—— 它是消息的源头，但它不一定能直连 Google / Apple（国内网络）；
- **薄中继**（我们自建的一台小服务）—— 主机把"唤醒请求"交给它，由它去调 FCM / APNs。

### 2.2 载荷三档（这是本页最关键的取舍）

| 档 | 载荷 | 延迟 | 隐私面 | 平台限制 |
|---|---|---|---|---|
| **D（推荐）** | data-only：`{"type":"wake","convId":"…"}`，**无正文** | 醒来后再取内容（多一个 RTT） | Google/Apple 只见唤醒事件，**内容不出门** | iOS 静默推送会被节流、不保证即时；Android Doze 里高优先级 data 有配额 |
| N | notification：通用文案「你有新消息」 | 立即可见 | 文案经 Google/Apple（仍是通用文案） | 两端都稳；但"看得见却打不开内容"体验一般 |
| C（不推荐） | notification + 消息正文 | 立即可见 | **正文经 Google/Apple 与厂商服务器**，与 task-13 的边界冲突 | 最稳，但隐私代价最大 |

**推荐 D**，并接受"iOS 静默推送不保证即时"这一条平台事实（见 §5 风险）；
当 D 在 iOS 上被节流到不可接受时，降级为 N（通用文案），**永远不降级到 C**。

### 2.3 唤醒之后手机做什么

1. 唤醒帧到达 → 应用获得一小段执行时间（Android：`onMessageReceived`；iOS：`didReceiveRemoteNotification`）；
2. 若 K1 长连接不在，**立即重连**（手机主动方向，天然穿 NAT）；
3. 连上后触发一次队列 flush（既有机制）；
4. 通知展示复用 `PushNotificationHandler.showNotification`，`focusPeerId` 语义不变（点通知定位到会话）。

## 3. 方案取舍（三个选项 + 推荐）

### 选项 A：主机直发 FCM / APNs

- 主机自己持有 FCM HTTP v1 服务账号 / APNs Key，直接调厂商 API。
- 优点：**零自建服务端**；消息源头就是发送方，链路最短。
- 缺点：凭据与设备令牌散落在**每一台主机**上；主机必须能访问 Google / Apple（国内主机通常不行，
  要么走代理，要么这条路对国内主机不可用）；多设备 / 群发要主机自己维护令牌表；
  令牌失效、APNs 证书轮换都要在每台主机上重做一遍。

### 选项 B：自建薄中继（推荐）

- 一台小服务：保存"nodeId ↔ 设备令牌"，接收主机（或对端手机）的"唤醒请求"，
  按设备所在平台调 FCM / APNs / UnifiedPush。**不保存消息正文，不转发正文**。
- 优点：凭据与令牌集中；主机不需要访问 Google/Apple（中继在国内可自建或选可达的出口）；
  多设备 / 群发 / 令牌失效 / 证书轮换只在一处处理；隐私边界清晰（中继只看到"谁要唤醒谁"）。
- 缺点：多一台要运维的服务（域名、证书、监控、限流）；它一旦不可用，唤醒就全断（但消息仍在队列里，不丢）。
- 形态可以复用今天的既有资产：agentNode 控制面已经跑在 Cloudflare Tunnel 后面（`RemoteRelayConfig`），
  中继完全可以挂在同一套部署与鉴权思路上（但**协议与职责要分开**：控制面是 agent 的，不是消息推送的）。

### 选项 C：UnifiedPush（自托管，Android 侧）

- Android 上用自托管的 `ntfy` / UnifiedPush distributor，**完全绕开 Google Play services**；
  iOS **没有** UnifiedPush，仍然只能 APNs。
- 优点：对"自托管 / 去 Google"的用户是唯一干净答案；与仓里的自托管气质一致。
- 缺点：要用户装一个 distributor 应用；国内 ROM 的省电清理对第三方 distributor 同样不友好；
  它仍然需要一台自托管服务器（与选项 B 的中继可以是同一台）。

### 对比与推荐

| 维度 | A 主机直发 | **B 薄中继（推荐）** | C UnifiedPush |
|---|---|---|---|
| 自建服务端 | 无 | 一台小服务 | 一台小服务（可同一台） |
| 凭据 / 令牌位置 | 每台主机 | **集中** | 集中 |
| 国内主机可用 | 差（需代理） | **好** | 好（Android） |
| iOS 覆盖 | 好 | **好（APNs）** | **无** |
| 隐私（内容） | 不含内容 | **不含内容** | 不含内容 |
| 运维成本 | 低 | 中 | 中 |
| 工作量（首期） | 小 | 中 | 中 |

**推荐：B 为主**（Android FCM + iOS APNs 都经它），**A 作为"完全自托管"的替代**（给不想用中继的用户），
**C 作为 Android 的自托管开关**（与 A/B 互斥，不叠加）。首期只做 **B + D（data-only）**。

## 4. 依赖与代价（如实列）

| 依赖 | 代价 | 备注 |
|---|---|---|
| FCM（Android） | 需要 Google Play services；国内大量 ROM 不带 → 必须叠加**厂商通道**（小米 / 华为 / OPPO / vivo / 荣耀），每家有 SDK、账号、审核 | FCM 本身免费，但有配额与速率限制 |
| APNs（iOS） | 需要**付费** Apple Developer 账号 + APNs Key/Cert + HTTP/2 provider API | 静默推送（`content-available:1`）被系统节流，不保证即时 |
| UnifiedPush | 用户要装 distributor；自托管服务器与域名 | 只覆盖 Android |
| 薄中继 | 一台服务器 + 域名 + 证书 + 监控 + 限流；它是**可用性单点** | 中继挂了不丢消息（队列仍在），只是不实时 |
| 客户端 | 新增"设备令牌注册 / 刷新 / 注销"的生命周期；隐私开关（用户可关云推送） | 与 task-15 的开关并列，两个开关各自说清 |
| 电量 / 流量 | 唤醒本身很小（几百字节），但"被唤醒后重连 K1"是真实开销 | 与 task-15 的常驻连接开销叠加，设置页要合并说明 |

## 5. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **iOS 静默推送不可靠** | `content-available` 在低电量 / 后台被节流，甚至完全不投 | 降级为通用文案通知（档 N）；对时效要求高的场景由"用户主动打开"兜底 |
| **国内 ROM 不投递** | 无 Google Play services、厂商省电清理杀进程 | 厂商通道适配（分期 P5.3）；同时保留 task-15 保活 + 队列 |
| **隐私被误解** | 用户以为"用了云推送 = 消息经过 Google" | 首期 data-only + 设置页逐字写"内容不经过推送通道，只唤醒" |
| **中继成为单点** | 中继不可用 = 全平台无唤醒 | 队列兜底不丢消息；中继健康探测 + 告警；A 方案作为自托管替代 |
| **令牌泄漏** | 设备令牌泄漏 = 别人能向该设备发唤醒（骚扰，但不泄漏内容） | 中继按 nodeId 鉴权、限流、令牌加密存储；推送 payload 不含内容 |
| **绕过用户静音** | 唤醒后仍按策略响铃，否则就是绕过 `notifyQuietHours` | §1.3 的硬约束：策略判定在客户端，推送只负责唤醒 |
| **合规 / 审核** | 国内厂商通道要企业资质与内容合规；APNs 需要开发者账号 | 分期做，先 Android FCM + APNs，厂商通道单列一期 |

## 6. 分期建议

| 期 | 交付 | 验收 |
|---|---|---|
| **P5.0** | 本设计 + 与 task-15 / K1 / task-13 的边界裁决 | 评审通过 |
| **P5.1** | 薄中继 + Android FCM **data-only** 唤醒；设备令牌注册/刷新/注销；设置页开关 + 隐私文案 | 杀进程 / 飞行模式 10 分钟后，收到唤醒并在 30s 内取到消息 |
| **P5.2** | iOS APNs（静默优先，节流时降级通用文案） | 同上，iOS 真机 |
| **P5.3** | 国内厂商通道适配（按 ROM 覆盖数据决定优先级） | 红米 / 华为 / OPPO 真机各一条 |
| **P5.4** | UnifiedPush（Android 自托管）+ 选项 A（主机直发）作为替代路径 | 无 Google 设备上可用 |

**回滚**：云推送是**纯增量**的唤醒通道 —— 关掉开关（或中继下线）即回到"task-15 保活 + K1 长连接 + 队列"，
消息一条不丢，只是不实时。客户端不需要为回滚做协议兼容（推送不是消息通道）。

## 7. 未决问题（需 lead / 产品裁决）

1. **中继谁来运营**？自托管（用户自己的机器）还是项目统一运营？这决定 P5.1 的部署形态与合规责任。
2. **是否允许 notification 档（N）**？它牺牲一点隐私换 iOS 的可靠性；我建议允许，但只允许**通用文案**。
3. **国内厂商通道做几家**？全做是 5 套 SDK + 5 个审核；按真机覆盖数据排优先级（红米已知是用户机型）。
4. **与 task-15 开关的关系**：两个开关（保活 / 云推送）还是一个"后台接收"总开关下的两个子项？
   我倾向后者（用户想的是"我后台能不能收到"，不是两条实现路径）。
5. **唤醒帧要不要带 convId**？带 = 通知能定位会话（体验好）；不带 = 中继连"哪个会话"都不知道（隐私更好）。
   我倾向带 convId（它本来就在主机与手机的授信关系内），但这条要写进隐私说明。
6. **iOS 静默推送被节流时的降级阈值**：多久没取到内容就补一条通用文案通知？
