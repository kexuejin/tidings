# 基于真实天气预报 App 的完整研发生命周期验收方案 (App SDLC Acceptance Plan)

> **核心定位**：软件研发不是单点任务的堆叠，而是一个包含 **「0 到 1 原型化立项」 $\rightarrow$ 「1 到 N 特性迭代合流」 $\rightarrow$ 「线上缺陷定位自愈」** 的完整工程生命周期（SDLC）。
> 本方案基于本地真实工程 `weather-relay`（真实 Web/Node 天气预报应用，含 72 条单元测试与全套状态机），通过物理真机（Android/iOS）与桌面宿主（macOS），全链路实测验证 Tidings 多智能体局域网协同与 DSH Super-Agent 的实际吞吐与鲁棒性。

---

## 一、生命周期映射与架构全景

```
                    【移动端 / 指挥中枢 (Commander)】
                      - 模糊产品意向 / 交互式卡片决策
                      - 差异代码审查 (Pre-merge Review)
                      - 一句话报障 / 毫秒级打断 ("停")
                                     │
                        局域网 IM 协议通道 (Tidings P2P)
                                     ▼
                    【桌面端 / 宿主编排 (Host Orchestrator)】
    ┌─────────────────────────────────────────────────────────────────┐
    │ DesktopWorkerOrchestrator (DSH Router-Worker 调度核心)          │
    │  - 阶段链 StageChain 状态演进 (prototype -> dev -> review_ready)│
    │  - ticketId 并发任务解耦，支持同群多 Agent 双工单独立并行        │
    │  - 纯协程工单闭环、上下文追问唤醒 (Thread Follow-up)             │
    │  - 毫秒级硬打断 (isAbortSignal -> Process Tree Kill)            │
    └─────────────────────────────────────────────────────────────────┘
                                     │
           ┌─────────────────────────┴─────────────────────────┐
           ▼                                                   ▼
 【工作树隔离沙箱 (Git Worktree)】                  【普通文件影子沙箱 (Fallback)】
  - 宿主主工作树零污染 (主分支不动)                  - 无 .git 纯文档环境
  - 独立临时分支开发与全量测试跑通                    - 文件比对与产物卡直传
  - 移动端确认后原子 Merge 合流                      - 零配置双模自适应
  - 终态卡片原位翻绿 (merged)                        - 任务结束后分支/目录无痕销毁
```

### 研发全周期三阶段映射

| 阶段分类 | 业务场景代表 | 核心挑战与人机接缝 | 核心验证机制 |
| :--- | :--- | :--- | :--- |
| **阶段 A：从无到有 (0 到 1 原型与立项)** | 天气预报 App 概念立项与交互选型 | 需求模糊、缺少代码基线、需人类审美与方案决策 | 原型阶段卡（`prototype`） $\rightarrow$ 动态单文件 HTML 产物 $\rightarrow$ 移动端多选卡片 $\rightarrow$ 追问微调 $\rightarrow$ 冻结立项 |
| **阶段 B：新功能迭代 (1 到 N 特性扩展)** | 扩展空气质量指数 (AQI) 面板与预警 | 既有代码防腐化、单测回归、多文件协同、分支隔离 | Git Worktree 独立沙箱 $\rightarrow$ 新增单测驱动 $\rightarrow$ 全量回归全绿 $\rightarrow$ `review_ready` 卡片 $\rightarrow$ 拇指一键合流 $\rightarrow$ 卡片原位翻 `merged` |
| **阶段 C：缺陷定位修复 (Defect 自愈)** | 城市搜索拼音大写/特殊空格匹配失败 | 快速定位、精准修复、不破坏存量逻辑、极简吞吐 | 一句话报障直达沙箱 $\rightarrow$ 编写复现测试 $\rightarrow$ 修复通过 $\rightarrow$ 原位刷新卡片 $\rightarrow$ 轻量合流 |

## 二、测试拓扑与前置环境准备

### 2.1 物理节点拓扑与群装置前提
- **指挥端（Device A，移动端）**：Android 物理真机（如红米、Pixel）或 iOS 真机，安装最新版本 Tidings App。
- **宿主端（Device B，桌面端）**：macOS 物理机，运行 Tidings 桌面端（具备本地 AgentNode 与 DesktopWorkerOrchestrator 调度能力）。
- **局域网连接**：两台设备接入同一 Wi-Fi 或通过直连热点，且双方已在「节点」页面互相配对并建立研发群聊（如「天气预报研发协同组」）。
- **群内装置前提（关键）**：
  1. 群内必须预先声明 Agent 席位（例如 `@codex-e2e`、`@claude` 等）并绑定目标工作区（例如 `ws-weather-e2e` 指向宿主真实工作区）；
  2. 移动端标准派单操作：点击输入框右侧按钮 $\rightarrow$ 底部弹层「选择目标」 $\rightarrow$ 选择绑定的具体席位与工作区 $\rightarrow$ 输入框上方出现席位胶囊 Chip（例如 `@codex-e2e · ws-weather-e2e 默认`），生成带 `agentIntent` 的结构化派单上下文。直接手打裸文本 `@Worker` 不带 intent，不会进入沙箱派单流。

### 2.2 宿主环境基线与实测考量
1. **真实代码基线与时延指标**：
   - 目标路径：宿主机器上的 `weather-relay` 项目目录；
   - 校验：执行 `npm test`，确认基线包含 **71** 条单元测试且在 **500ms 内** 全部通过（`478f060` 干净检出实测 243ms，多次运行 243–267ms；指标定为 `<500ms`，严禁定为 <200ms 以免造成无意义的假红）。
2. **底层 CLI 驱动与沙箱安全**：
   - 终端验证宿主系统环境中存在可调用的 Agent CLI（如 `codex`、`claude` 或 `agy`）；
   - **沙箱家目录隔离**：沙箱启动时自动生成轻量 `.sandbox-home` 并白名单符号链接工具凭据，阻断对宿主 `~/.workbuddy`、`~/.ssh`、`~/.aws` 等隐私目录的非法读取；
   - **进程树治理**：宿主支持进程组级别追踪与摘除（Process Tree Kill），Abort / 超时时执行 SIGTERM $\rightarrow$ 宽限 3s $\rightarrow$ SIGKILL，杜绝后台孤儿僵尸进程。
3. **真机自动化注入避坑指南（关键规程）**：
   - 若通过 ADB 自动化注入文本，**必须预先切换至纯文本输入法**（如 `adb shell ime set com.timecove.adbime/.TimeCoveAdbIme`），防止系统默认拼音输入法吞字截断（实测曾将 `stop` 吞成 `stp`，将 `weather` 吞成 `weaher`，甚至空格误触系统 `@所有人` 广播）；
   - 派单指令中不要使用英文分号 `;`，防止被设备 shell 误判为命令截断符。
4. **ADB 观测链路（移动端日志监控）**：
   ```bash
   adb devices
   adb logcat -v time -s RelayApp:D Tidings:D
   ```

## 三、阶段 A：从无到有（0 到 1 原型化探索与立项验收）

### 3.1 业务场景叙述
产品经理或业务负责人在手机端提出一个极简天气预报 App 的构想，希望看到交互原型，并确认视觉布局和关键指标后，再进入正式代码实现。

### 3.2 标准操作规程 (SOP)

#### 步骤 A1：移动端点选席位发起产品概念探讨
- **操作**：在手机端研发协同群聊中选择席位胶囊（如 `@codex-e2e`），输入需求：
  > `请为 weather-relay 设计一个极简天气预报交互原型：需要支持当前温度、未来 7 天预报、摄氏/华氏切换，以及空气质量模块。请生成可交互原型并给出方案选项。`
- **预期响应**：
  1. 宿主收到消息，invoke 执行桥通过 `handlePromptAwait` 将任务交由 `DesktopWorkerOrchestrator`；
  2. 群内流式收到动态进度卡片（当前阶段标识：`Stage: PROTOTYPE`，状态：`working`，明确标示负责的 Agent 身份）。

#### 步骤 A2：接收原型产物与交互卡片
- **预期响应**：
  1. Worker 在沙箱内生成单文件可交互原型 `prototype.html`；
  2. 群内投递富交互卡片（`card`），包含：
     - **原型预览链接/产物入口**：点击可在手机系统浏览器中实时打开查看动态效果；
     - **方案选择表单/决策按钮组**：
       - `[方案 1：极简折线图布局]`
       - `[方案 2：分面卡片胶囊布局]`
       - `[方案 3：紧凑表格平铺布局]`
     - **阶段状态**：`Stage: PROTOTYPE`，状态置为 `prototype`（等待人类决策）。

#### 步骤 A3：移动端交互式决策与 Follow-up 追问微调
- **操作 1（决策选择）**：移动端用户点击卡片上的 `[方案 2：分面卡片胶囊布局]`。
- **操作 2（追问微调）**：在群内继续发送补充要求：
  > `胶囊卡片方案很符合预期，但请将背景调整为毛玻璃动态渐变，且华氏度切换开关置于右上角。确认后直接初始化项目骨架。`
- **预期响应**：
  1. 卡片操作与 Follow-up 文本作为同一工单（Thread）上下文，直接唤醒正在挂起的 Worker 协程（`state: prototype -> working`）；
  2. Worker 微调 `prototype.html`，随后自动触发 `StageChain` 流转：从 `prototype` 跃迁至 `dev`；
  3. 群内原位卡片刷新为：“原型已确认，正在初始化代码架构与测试桩...”。

### 3.3 验收判定标准
- [ ] 原型产物在移动端浏览器中能流畅交互（点击摄氏/华氏切换，数据实时变动）；
- [ ] 移动端发送微调指示后，无需重启工单，原工单在 1.5 秒内响应并继续执行；
- [ ] 宿主主分支工作树没有出现任何未经确认的脏文件。

## 四、阶段 B：新功能迭代开发（1 到 N 特性扩展与合流）

### 4.1 业务场景叙述
在既有成熟工程 `weather-relay`（已有 72 条单测）的基础上，新增“空气质量指数（AQI）面板”，要求包含数值计算、预警分级以及配套单元测试，且主工程在移动端审查通过后方可合流。

### 4.2 标准操作规程 (SOP)

#### 步骤 B1：移动端点选席位发起新特性工单
- **操作**：在群聊中选择席位胶囊（如 `@codex-e2e`），发送：
  > `请为 weather-relay 新增空气质量 (AQI) 面板：支持 PM2.5/PM10 指数展示，按照 0-50 优、51-100 良、101+ 预警三级色彩展示，编写完整单元测试，确保全量测试通过后提交审查。`
- **预期响应**：
  1. Worker 识别项目根目录包含 `.git`，自动激活 **Git Worktree 隔离沙箱**；
  2. 宿主在临时目录（如 `/tmp/tenon-ws/artifacts/t-...`）检出独立分支，机主在主目录的未暂存修改丝毫未受影响；
  3. 群内卡片以 `rev++` 原位更新状态：`Stage: DEV` $\rightarrow$ `action: coding` $\rightarrow$ `running npm test`。

#### 步骤 B2：沙箱自测与质量卡点拦截
- **预期响应**：
  1. Worker 编写业务模块代码（如 `src/aqi.js`）；
  2. Worker 编写配套测试（如 `test/aqi.test.js`）；
  3. Worker 在沙箱内执行 `npm test`：
     - 若测试红灯：Worker 根据失败堆栈自动进入“自愈循环（Heal Loop，最多 3 轮）”，修复实现直至全部绿灯；
     - 测试最终通过：72 条老用例 + N 条新用例 = **100% 通过**（耗时 < 500ms）。

#### 步骤 B3：移动端代码审查卡片（Pre-merge Review）
- **预期响应**：
  1. Worker 生成 Diff 补丁文件（`patch.diff`）；
  2. 协同群内弹出审查卡片（`review_ready`），内容包含：
     - **改动摘要**：文件变更行数统计（如 `+85 lines, -0 lines, 2 files changed`）；
     - **执行摘要**：CLI 真实总结；
     - **原生操作按钮组**：`[合并此补丁 (Merge)]`。

#### 步骤 B4：移动端拇指一键合流 (Mobile One-click Merge)
- **操作**：移动端用户在群内审查卡片上点击 **`[合并此补丁]`** 按钮。
- **底层链条验证**：
  1. 移动端发出 `card_action` 载荷（`actionId = "merge-patch"`，`cardId = "..."`）；
  2. 宿主端 `DesktopExtension.onHostCardAction` 拦截动作，通过 `latestPatchRefForCard` 找到对应补丁；
  3. 触发原子合流命令：在宿主主仓库执行 `git apply --check` $\rightarrow$ `git apply`；随后把合并后的工作树打成滚动基线快照（`refs/tenon/base`，不动 HEAD/索引），供下一张工单的沙箱起步（D5）；
  4. 自动销毁临时 Worktree 目录与分支，释放磁盘；
  5. **卡片原位闭环更新**：协同群内原位卡片状态由 `review_ready` 翻为 **`merged`**，横幅显示绿色成功文本 `Changes merged into workspace`，宿主台账落盘 `merge-result (applied)` 审计记录。

### 4.3 验收判定标准
- [ ] 宿主主目录在未点击 `[合并此补丁]` 前，`git status` 绝对干净，不包含新代码；
- [ ] 点击 `[合并此补丁]` 后，宿主主仓库自动完成变更落盘，且本地再次运行 `npm test`，通过数提升且全绿；
- [ ] 合并成功后，下一张工单的沙箱以**合并后的工作树**为起点（宿主日志 `next sandbox base=<sha>`），上一轮的代码与测试对下一轮可见（D5）；
- [ ] 群内卡片原位更新为 `merged`，无残留悬空按钮；
- [ ] 宿主临时 Worktree 目录被干净清除，无残留僵尸进程。

## 五、阶段 C：缺陷定位修复（线上报障与极简自愈）

### 5.1 业务场景叙述
线上反馈：“在城市搜索框中输入全大写拼音如 `BEIJING` 或前后带连续空格时，系统未能容错识别，直接返回了 `未找到该城市 (NOT_FOUND)`”。

### 5.2 标准操作规程 (SOP)

#### 步骤 C1：一句话极简报障
- **操作**：移动端选择席位胶囊，在群内发送：
  > `线上 Bug 报障：搜索城市输入全大写 BEIJING 会报未找到城市，请修复大小写归一化容错，补齐测试用例并提交。`
- **预期响应**：
  1. Worker 单工单闭环接单，在独立沙箱中快速定位到 `src/services/weatherService.js` 的 `normalizeQuery`（基线仓**没有** `src/provider.js` / `normalizeCityQuery`）；
  2. Worker 优先在 `test/provider.test.js` 中新增复现用例（Red）；
  3. Worker 修复实现，增加 `.trim().toLowerCase()` 与 NFKC 归一化（Green）；
  4. 运行全量测试，全绿通过。

#### 步骤 C2：极简自愈结果通知与轻量合流
- **预期响应**：
  1. 群内刷新卡片为 `review_ready`，展示修复摘要与行数变动；
  2. 用户点击 `[合并此补丁]`，宿主执行原子合并并原位刷新卡片为 `merged`；
  3. 宿主主工程拉取该修复，缺陷闭环。

## 六、横向全周期防护与极端异常演练

### 6.1 演练 1：即时硬打断 (Hard Interrupt & Process Tree Kill)
- **场景**：在 Worker 执行复杂生成或陷入死循环时，用户在移动端发出打断指令。
- **操作**：当卡片处于 `status: working`、宿主后台正在运行沙箱进程时，用户在群内发送单字：
  > `停` 或 `stop`
- **预期判定**：
  1. 入站层提前识别打断信号（`isAbortSignal` 命中）；
  2. 宿主立即取消当前协程，并调用 `destroyProcessTree` 向底层整棵进程树发送 `SIGTERM` $\rightarrow$ 宽限 3s $\rightarrow$ `SIGKILL`；
  3. **耗时断言**：**宿主从收到打断文本到完全摘除进程树在 500ms 内**（端到端网络投递受物理局域网环境制约，通常在 1~2s 内完成响应）；
  4. 宿主后台执行 `pgrep codex` 读数立即归 0，绝对无孤儿后台占用 CPU；
  5. 群内卡片状态原位更新为：`status: aborted (Aborted by user request)`。

### 6.2 演练 2：超纲退单机制 (Handed Back)
- **场景**：用户提出破坏全部单测或超出代码库边界的不可行要求。
- **预期判定**：
  1. Worker 尝试修复超过最大尝试次数（`maxHealRounds = 3`），沙箱回归测试持续红灯；
  2. Worker 绝不上报虚假成功，而是触发退单逻辑（`Handed back`）；
  3. 群内卡片原位更新为 `blocked`，横幅显示：“Handed back: exceeded max heal rounds (3) — [错误详情]”，将决策权诚实交还给工程师。

### 6.3 演练 3：脱网去中心化 Git 合流 (Offline P2P Bundle)
- **场景**：无公网 GitHub/GitLab 访问权限，两台设备处于纯局域网脱网环境。
- **预期判定**：
  1. 审查就绪后，宿主端产出轻量 patch 文件；
  2. 通过 Tidings 本地 P2P 文件传输通道直接投递至移动端；
  3. 移动端本地校验后点击合并，验证完全不依赖任何外部中心化托管服务。

### 6.4 演练 4：多 Agent 双工单并发推进与独立流转 (Multi-Agent Parallel Dispatch)
- **场景**：在同一个研发协同群中，同时存在两个不同职能的 Agent 任务。
- **操作**：
  1. 用户先点击输入框选择 `@codex-e2e` 席位，派发任务 A：“修复城市搜索的大小写容错”；
  2. 5 秒后，用户在同一群内点击选择 `@claude` 席位，派发任务 B：“为 weather-relay 编写 API 接口架构说明文档”；
- **预期判定**：
  1. 宿主编排器依据 `ticketId` 独立分配两个不同的沙箱，Codex 和 Claude 同时在各自的 Worktree 里并发干活；
  2. 协同群内同时并存 **两张独立的工单卡片**（一张标示 `Codex`，一张标示 `Claude`）；
  3. 两张卡片各自以自己的 `rev++` 独立原位刷新进度，绝对不发生状态互相覆盖；
  4. 任务 A 跑完出 Review 卡，用户点击合并，任务 A 翻为 `merged`，而任务 B 继续正常推进不受干扰。

## 七、全周期验收判定矩阵与质量守则

### 7.1 判定矩阵汇总

| 检查项 | 验证阶段 | 预期行为与读数 | 失败判定标准 |
| :--- | :--- | :--- | :--- |
| **原型生成时延** | 阶段 A | 单文件 HTML 在 15s 内生成完毕并推送到群 | 超过 30s 或输出格式损坏无法在浏览器渲染 |
| **上下文追问唤醒** | 阶段 A | 移动端发送微调指示后，原工单在 1.5s 内接续唤醒 | 重启新工单、遗忘前置原型上下文 |
| **宿主主工作树隔离** | 阶段 B | 沙箱开发期间，宿主主仓库 `git status` 无新增文件与未暂存修改 | 主仓库被切换分支或主工作树被污染 |
| **单测回归全绿** | 阶段 B & C | 全量 72+ 条测试必须 100% 绿灯（耗时 **< 500ms**，实测基线 238ms） | 存在被跳过（skip）或失败的用例，或耗时严重超标 |
| **原子审查与合流闭环** | 阶段 B | 点击 `[合并此补丁]` 后，主仓库应用变更，卡片原位翻为 **`merged`** | 补丁冲突未上报、卡片无成功反馈、沙箱残留未清 |
| **即时硬打断进程回收** | 横向防护 | 移动端发送“停”，**宿主入站到进程树销毁 < 500ms**，`pgrep` 归零 | 进程挂起在后台持续消耗 CPU 形成孤儿进程 |
| **多 Agent 双工单并发** | 演练 4 | 同一群先后派发两个 Agent，两张卡片独立并行流转且互不踩踏 | 后派发的任务覆盖前一个任务的引用，或卡片错乱 |
| **日志时间真实性** | 全流程 | 检查 `messages.log` 落库时间（`at` 列）与信封时刻一致 | 出现队列死循环重试或静默吞帧 |

### 7.2 质量红线提示 (AGENTS.md 不变量)
1. **严格白名单规约**：卡片与文本交互载荷不得新增未在白名单内的额外键，防止接收端整帧拒收。
2. **字节帧预算**：原型 HTML 或大文件严禁直接塞入群文本帧（超过 32 KiB 会触发整帧丢弃），必须走 Tidings 真实文件传输通道；群卡片严格控制在 24 KiB 内。
3. **一个事实只有一个来源**：发送者标识必须通过 `agentSenderIdFor()` 严格规范化，禁止散乱拼接字符串导致界面显示分裂。
4. **零 Compose 侵入领域层**：领域模型与编排器严禁引入 UI 依赖，保证跨端共享核心的整洁性。
