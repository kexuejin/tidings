# 跨网文件 / 屏幕传输设计 · 供决策（task-23 ②）

> 状态：**设计稿，未实现**。本文件只描述形态、量级、取舍与分期，不改任何生产代码。
> 相关：task-20 ③ / `docs/cross-network-keepalive-design.md`（K1 长连接，只跑文本/控制）、
> task-13 / `docs/public-transport-security.md`（公网内容只允许经 TLS 的 TCP 通道）、
> `docs/spike-kmp-tls.md`（三端 TLS 零新依赖已实证）。
> 事实基线：**今天跨网只覆盖文本 / 消息**；文件与屏幕仍走局域网原路径。

## 0. 结论速览

1. **真正的障碍不是带宽，是"文件的数据阶段不是分帧流"**：`pull-ok` 之后紧跟的是**裸字节**，
   不受 64KB 帧上限约束（`FileTransfer.MAX_FRAME` 的 KDoc 逐字写明）。要把它塞进一条多路复用的
   长连接，就得先把裸流切成分帧段 —— 那是一次协议变更，旧端会按未知帧类型拒收。
2. **屏幕反而是"已经准备好了"的那一个**：`screen-frame` 本来就是长度前缀分帧（≤512KB），
   而且 `ScreenStream` 里已经有**信用制流控**（5MB/s 上限、3/5/10fps 自适应）。
3. **推荐选项 B：手机主动再开第二条 TCP 连接（TLS + pin），原样复用现有 file-ctl / 屏幕协议**，
   不做多路复用。手机开口 ⇒ 天然穿 NAT；主机从 K1 已经学到手机的当前地址，第二条连接同一方向即可。
4. **推荐折中：只搬文件，不搬屏幕**。屏幕 5MB/s ≈ 40Mbps **持续**，一分钟约 300MB ——
   在蜂窝资费与（若走中继）服务器带宽上都不成立。首期屏幕保持局域网，并在界面上**如实说明**。
5. **不做会怎样**：手机与主机不在同一局域网时，文件只能等双方回到同一网段；屏幕协助完全不可用。
   这不是"体验差一点"，是"这两条能力在跨网场景下不存在"。

## 1. 现状（协议与量级的真实数字）

### 1.1 文件：独立 TCP 连接 + 裸流数据阶段 + 断点续传

| 事实 | 值 / 证据 |
|---|---|
| 传输通道 | **独立 TCP 连接**（不是 UDP，也不复用消息连接） |
| 控制帧族 | `file-ctl`（`offer` / `accept` / `decline` / `cancel` / `direct`）+ `pull` / `pull-ok` / `done` / `finish` / `err` / `wait`（`FileTransfer.kt` 的 `FileCtlOps` / `TcpFrameTypes`） |
| 控制帧体上限 | `FileTransfer.MAX_FRAME = 64 * 1024`；`TcpFramedChannel.MAX_FRAME` 同值 |
| **数据阶段** | **`pull-ok` 之后是裸字节流，不受帧上限约束**（`FileTransfer.MAX_FRAME` 的 KDoc 原文） |
| 断点续传 | `.part` 文件 + offset；`PULL_IDLE_TIMEOUT = 60s`，超时判失败但 `.part` 留着可续 |
| 自动接收阈值 | 图片 20MB（`IMG_AUTO_ACCEPT`）、群图 10MB（`GROUP_IMG_AUTO_ACCEPT`），超限退化为手动领取 |
| 规模上限 | 单次传输 ≤2000 文件（`MAX_FILES_PER_TRANSFER`）；offer 认领窗口 24h（`FILE_OFFER_TTL`） |
| 预哈希 / 排队心跳 | `PULL_WAIT_HEARTBEAT = 20s`（`wait` 帧） |

### 1.2 屏幕：独立 TCP 连接 + 分帧 + 信用流控

| 事实 | 值 / 证据 |
|---|---|
| 通道 | **独立 TCP 连接**；`screen-open` / `screen-ready` / `screen-next` / `screen-frame` |
| 帧格式 | **长度前缀分帧**，单帧 ≤512KB（`SCREEN_MAX_FRAME_BYTES`） |
| 分辨率 / 像素 | 长边 ≤1920、像素 ≤2,073,600（`SCREEN_MAX_EDGE` / `SCREEN_MAX_PIXELS`） |
| 速率 | ≤5MB/s（`SCREEN_MAX_BYTES_PER_SECOND`）、最小帧间隔 100ms（`SCREEN_MIN_FRAME_INTERVAL_MS`） |
| 帧率 | 自适应 3 / 5 / 10 fps（`ScreenRate`：Economy / Standard / Smooth·Auto） |
| 流控 | **已有**信用制：`ScreenStream.credit`，按 5MB/s 补充、按帧大小扣减，不够就等 |
| 超时 | 连接 15s、帧 5s、空闲 10s、请求间隔 20s（`Limits.kt`） |

### 1.3 跨网：今天只有"文本/控制"的第三条承载（且未实现）

- K1 长连接（`docs/cross-network-keepalive-design.md`）明确**首期不做多路复用**，只跑控制与文本；
  同一页的未决问题第 3 条就是"文件/屏幕是否复用这条连接"，并建议先不做。
- task-13 的硬约束：**公网对端的内容只允许经 TLS 的 TCP 通道**；
  `docs/spike-kmp-tls.md` 已实证三端 TLS 零新依赖（Android 真机、JVM 完整双向握手、iOS 监听器）。
- 所以：跨网文件/屏幕**不是"能不能加密"的问题**（TLS 已证明可行），而是"挂在哪条连接上、要不要多路复用"的问题。

## 2. 方案取舍（三个选项 + 一个折中，含推荐）

### 选项 A：多路复用到 K1 长连接

- 在 K1 上加 stream id、每流独立流控与背压，文件与屏幕作为两条逻辑流共享一条 TCP。
- **优点**：一条 NAT 打洞连接；身份（`link` 帧）只做一次；手机侧只维护一条连接。
- **缺点（这是本页最重的代价）**：
  1. 文件数据阶段是**裸流**，要改成"分帧段"才能与文本流交错 —— 协议变更，旧端按未知帧类型拒收；
  2. 要自己实现多路复用（队头阻塞、公平性、每流背压、半关、错误隔离），这是**另一个量级**的工程；
  3. 文本/控制的时效会被大文件拖累（同一 TCP 上的队头阻塞），而文本恰恰是最需要低延迟的那条。

### 选项 B：第二条"手机主动"连接，原样复用现有协议（**推荐**）

- 手机向主机的 `tcpPort` 再开一条 TCP；首帧声明角色（与 K1 的 `link` 同一套身份校验），
  之后**原样**跑现有 `file-ctl` / `pull` / `done` 与 `screen-*` 协议；
  **TLS + 双向 pin** 由 task-13 的 P2 提供（字节流，对裸流数据阶段零影响）。
- **优点**：
  1. **协议一行不改**：裸流数据阶段、断点续传（`.part` + offset）、屏幕的信用流控全都原样成立；
  2. 文本流不受大文件拖累（两条独立 TCP，互不阻塞）；
  3. 失败隔离：文件传输失败不影响 K1 的在线判定与下行；
  4. 方向正确：手机开口 ⇒ 穿 NAT，主机在已建立的连接上回程 —— 与 K1 同一条"反方向"思路。
- **缺点**：两条连接各自维护 NAT 映射与重连（映射超时 30–120s，需要各自的心跳）；
  主机侧连接数 ×2（K1 一条 + 传输按需若干）；手机侧要管"第二条连接什么时候开、开多久"。

### 选项 C：经中继服务器转发

- 两侧都不可入站（对称 NAT）时的唯一路径；服务端做字节中转。
- **优点**：不依赖任何一侧的可达性。
- **缺点**：**文件/屏幕的服务器带宽成本极高**（屏幕 5MB/s 是持续流），且内容经第三方服务器，
  隐私面与合规面都变大。它应该是"最后手段"，而不是默认路径。

### 折中（推荐与 B 组合）：**只搬文件，不搬屏幕**

- 屏幕的量级（§3）在蜂窝与中继上都不成立；把它排除在外，能砍掉本页最大的风险。
- 跨网屏幕若一定要做，必须是**显式 opt-in + 硬性流量上限 + 明确告知**（见 F3），默认关。

### 对比与推荐

| 维度 | A 多路复用 | **B 第二条连接（推荐）** | C 中继 |
|---|---|---|---|
| 协议改动 | **大**（裸流要改成分帧段） | **无** | 无 |
| 工程复杂度 | 高（多路复用/背压/公平） | **低**（复用现有代码路径） | 中（服务端转发） |
| 文本延迟影响 | 有（队头阻塞） | **无** | 无 |
| 服务器带宽成本 | 无 | 无 | **高**（屏幕不可接受） |
| 双侧不可入站 | 可用（同 K1） | **不可用**（需中继兜底） | 可用 |
| 推荐 | 否（首期） | **是** | 仅兜底，且只文件 |

**推荐：B + 只搬文件**；C 仅作"双方都不可入站"的兜底且**只允许文件并限大小**；A 明确不做（至少本期）。

## 3. 量级评估（把代价说成人话）

| 场景 | 数据量 | 4G（约 10Mbps） | 5G（约 100Mbps） | 说明 |
|---|---|---|---|---|
| 一张自动接收的图片 | 20MB | ≈16s | ≈2s | 蜂窝流量 20MB；若走中继，服务器也吃 20MB |
| 一个 200MB 的文件夹 | 200MB | ≈3min | ≈16s | 断点续传必须有（蜂窝切换/断网是常态） |
| 屏幕协助 1 分钟（满速） | ≈300MB（5MB/s） | 不可接受 | 勉强，但资费与耗电都很痛 | **这是"不搬屏幕"的量化理由** |
| 屏幕协助 1 分钟（Economy 3fps） | 仍受 5MB/s 上限，实际取决于画面变化 | 不可接受 | 仍不可接受 | 上限是**上限**，不是均值 |

结论：文件在蜂窝上"可接受但要有断点续传与明确的大小提示"；屏幕在蜂窝上"不可接受"，
在中继上"不可接受且要我们付服务器带宽"。

## 4. 与 TLS / 断点续传的关系（两个容易混淆的点）

1. **TLS 不改变裸流数据阶段**：TLS 本身就是字节流，`pull-ok` 之后的裸字节照常走，
   不需要为了 TLS 把它改成分帧 —— 这是选项 B 比选项 A 便宜的关键原因。
2. **断点续传与 TLS 会话无关**：续传靠 `.part` + offset 的应用层状态，
   重连（哪怕换了一条 TLS 连接）后从 offset 继续即可；**不需要** TLS 会话恢复（session resumption）。
   反过来说：如果将来做多路复用，offset 的语义要重新对齐到"流"上，那是额外风险。

## 5. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| **第二条连接也要穿 NAT** | 与 K1 同方向，理论上同一条路径；但每条 TCP 有独立的 NAT 映射与超时 | 传输期间按需心跳；传输结束即可关；映射超时后重连 |
| **主机连接数** | 每设备 K1 一条 + 传输若干；群发文件会叠加 | 连接数上限 + 每连接鉴权（必须校验 nodeId/授信，否则任意人可占资源） |
| **蜂窝资费** | 20MB 图片自动接收在蜂窝上是真金白银 | 蜂窝下**默认不自动接收**大文件，先问；设置里给"仅 Wi-Fi 自动接收" |
| **旧端兼容** | 选项 B 不改协议 ⇒ 兼容性风险低；但要新帧/新握手时仍需"旧端丢弃未知类型"的既有纪律 | 复用 `link` 身份帧与既有 `TcpFrame` 家族 |
| **双方都不可入站** | 选项 B 不成立 | 中继兜底（只文件、限大小）；或明确告知"此网络环境下传输不可用" |
| **屏幕被误以为可用** | 跨网时界面若照旧画"查看屏幕"，用户点了必然失败 | UI 如实说明"屏幕协助需要同一局域网"（不画一个注定失败的入口） |
| **Doze / 后台** | 传输中手机退后台可能被冻结 | 挂到 task-15 的保活前台服务上；传输是短时任务，与"常驻保活"分开说明 |

**回滚**：文件/屏幕仍保留局域网原路径，新路径是**增量**且带开关；关掉即回到今天的行为，
协议上若只复用既有帧族，则连旧端兼容问题都没有。

## 7. 未决问题（需 lead / 产品裁决）

1. **屏幕跨网是否永远不做**？我建议至少本期不做，并在 UI 上把"需要同一局域网"写成一句实话。
2. **文件是否允许经中继**？若允许，大小上限与是否加密到端（TLS 到中继 vs 端到端）要一起定。
3. **蜂窝下的自动接收策略**：默认"仅 Wi-Fi 自动接收"，还是保留今天的 20MB 自动接收（会花用户流量）？
4. **第二条连接的复用粒度**：一次传输一条，还是"一台设备一条传输连接"复用多个 transfer？
5. **与 K1 的连接上限治理**：主机侧要不要把 K1 与传输连接放在同一个上限池里？
