# 智能体全链路方案：从基座配置到派单执行

> 本文回答一个问题：**一个用户从「什么都没配」到「@ 一句话真跑起来」，中间要经过哪几站、  
> 每站长什么样、坏了怎么告诉他。**
>
> 不按功能列清单，按**用户走的那条路**排。每一站必须回答三件事：入口在哪、写的是哪份数据、  
> 失败时用户看到什么。三件事有一件答不上来，这一站就还是假的。

> **读之前先看这一段：本文引用三个不同的代码状态，事实必须带后缀，否则读不出它指哪一份。**
>
> | 后缀 | 指哪份代码 | 怎么复核 |
> |---|---|---|
> | `@HEAD` | 分支 `main` **已提交**的那一份 | `git show HEAD:<path>` |
> | `@worktree` | 当前工作树（含未提交改动，`git status` 里是 ` M`） | 直接读文件 |
> | `@impl` | 分支 `impl/agent-lifecycle`（P1a 的三条提交） | `git show impl/agent-lifecycle:<path>` |
>
> 没有后缀的事实一律按 `@HEAD` 读。**混着写是上一版最贵的缺陷**：§6 P1a 要求「身份锚入帧」，
> 而 §2② 已改走本机投影链 —— 同一份文档两条互斥的实施路径，实现者会先做错的那条。
> 本文所有「已落地」都必须能在上表某一列里指出提交或工作树，指不出的写法一律改成「待做」。

## 0. 结论先行

现在这条链路是**断成三截**的：

| 站    | 现在                                  | 缺的那一截                                             |
| ---- | ----------------------------------- | ------------------------------------------------- |
| ① 基座 | 能列出本机在位的底座                          | 没装 / 没登录 / 没模型时**没有出路**，只告诉你「没检测到」                |
| ② 员工 | 只能给**已经上报过身份**的本机 agent 建档          | 新机器永远建不出第一个员工 ⇒ 冷启动死锁                             |
| ③ 团队 | 领队必须从「已上报的本机 agent」里选；组员只能凭空新建      | 同上，空表时不展开表单（只给「去看看节点」）；AI 建队连员工清单都读不到 ⇒ 明明有人还造陌生人 |
| ④ 派单 | 执行档缺 / 席位没目录 / 无权限都会出 blocked 卡，不静默 | 失败后的**下一动作**是空的：卡上只说「blocked」                     |
| ⑤ 结果 | 会话卡 + 事件流 + 重试                      | 登录等待、模型缺失两类提示没进卡片正文                               |

**一句话**：写路径与 fail-closed 判据基本齐了，**入口与出路不齐**。所以体验是「每一步都  
有人拦着你，还不告诉你怎么过」。

> 每一站具体长什么样、用什么 token、给什么文案，见 **§3 界面样式规格** —— 那一节是按  
> 「拿给实现就能写」的粒度写的，本节的判断在那一节落成布局与状态。

**本轮已落地**（对应你截图里的两处）：

- 本机不再靠「宣告过工作区」才能进员工名录 —— 之前只在本机宣告过目录时才枚举本机，  
  于是「会话已经跑起来、目录还没宣告」这一档整台机器从看板上消失，页面却劝你去看别的节点。  
  现在本机作为宿主**先入表**，聚类仍由台账决定（没有事实仍然没有卡）。测试  
  `localSessionWithoutAnyWorkspaceStillProducesCard` / `localSeatOnlyProducesCard` 钉住。
- 空态不再把「本机没有」说成「对方没有」：文案改成「这台电脑和已连上的设备上都还没有智能体  
  在运行」，出路指向**接运行时 + 建员工**，而不是只有「去看看节点」。

## 2. 目标链路（五站）

```
① 基座 ──▶ ② 员工 ──▶ ③ 团队 ──▶ ④ 派单 ──▶ ⑤ 结果
  │           │           │           │           │
  └── 没装/没登录 ┴─ 没目录/没职责 ┴─ 没执行档 ┴─ 无权限/离线
        每一站的异常都必须落到「一个能点的下一动作」
```

### 2.0 先定一个边界：这一页显不显示别的节点

**显示，但必须按设备分档，且写操作只在本机那一档。**

这一页混着两种东西，这是所有困惑的来源：**名录**（谁在跑，跨设备）与**编制/档案**  
（我能指挥谁、用哪个底座，只在本机）。只显示本机 ⇒ 手机端永远是空页（它一台本机 agent  
都没有），桌面也看不见远端在跑什么；只显示远端 ⇒ 用户以为在管别人的机器。

|                        | 本机卡    | 远端卡                                                    |
| ---------------------- | ------ | ------------------------------------------------------ |
| 在做什么、最近活动、待批数          | 画      | 画（这就是跨设备的价值）                                           |
| 会话 / 目录 / 进度 下钻        | 画      | 画（只读事实）                                                |
| `@` 派单                 | 画      | 画，但过 `AgentExecPolicies`；未授权标「无调用权限」，**不隐藏**（藏了等于说人不在） |
| 编辑档案 / 注销 / 换运行时 / 建团队 | 画      | **不画**（档案、执行档、席位全落宿主本机）                                |
| 它用哪个运行时（名字 / 模型 / 登录态） | 画      | **不画**（见下「三层区分」）                                       |
| 宿主名                    | 「这台电脑」 | 设备名（由**设备段头**承担，卡片副行不重复写）                              |

三条推理：

1. 只按 `agentId` 匹配档案是错的 —— **档案的定位键是 `(hostNodeId, employeeId)`**，两台机器上  
   同时有一个 `dsh` 实例是常态。本轮已把「卡片 → 档案」收成一个判据 `employeeProfileOf`（先宿主、  
   后 `sameEmployee`；旧实现按 `sameAgent`，`@worktree`），并顺手修了孤儿档案的同一处：原先拿别人的卡配对，会让一份本机档案  
   「看起来在线」而从登记簿消失，它名下的群与注销入口跟着一起不见。
2. **分组，不做筛选**。筛选器会让别的设备「消失」，与「不静默」冲突；分组只回答位置。  
   段头 = 设备名，本机排第一并标「这台电脑」。
3. 空态要分**四档**（判据与文案见 §3.1 那张表，按 D → A → B → C 顺序求值）：一台设备都没连 /
   有设备但谁都没跑 / 本机有员工但没在跑 / 只有别的设备在跑。现在四档共用一句话，于是「本机没有」
   被说成「对方没有」（本轮已改文案，分组做完后再分档细化）。

#### 运行时只住本机：三层必须分开

「运行时」是这一页最容易画错的一栏，因为它有三个不同来源，只有前两个与本机有关：

| 层                              | 存在哪里                              | 远端读得到吗          | 界面上怎么用                                                     |
| ------------------------------ | --------------------------------- | --------------- | ---------------------------------------------------------- |
| **基座目录** `driverCatalog()`     | 本机 `CliDiscovery` 扫出来的            | **读不到**（扫的是我这台） | 只用于 ① 基座盘面与「哪些运行时可选」，**永不进远端卡**                            |
| **执行档** `driverKey` + `models` | 席位宿主的盘上（`(dirId, leaderAgentId)`） | **读不到**         | 只在本机队的执行配置里；远端队的成员详情只写「这台电脑读不到它的执行配置」                      |
| **会话种类** `agentKind` / 实例键前缀   | 随 `agent-session` 帧同步             | 读得到             | 只当身份线索（聚类代表），**不当绑定**（`AgentWorkstationPort` 非本机一律 `null`） |

三条纪律：

1. **不拿本机目录解释远端卡。** 远端 agent 用哪个运行时、哪个模型，本进程无从知道；把我这台的  
   `driverCatalog()` 套上去，画出来的是「我这台装了什么」，用户读成「对方在用什么」。
2. **不拿本机状态标注远端。** 本机的「未安装 / 未登录」只描述本机；标到远端卡上等于说  
   「对方没登录」。所以 `driverAuthStates()` 的结果只能在 ① 出现，**员工名录一行都不染**。
3. **实例键前缀不是绑定。** `dsh-029bbbf3` 的前缀只说明「这个名字登记时的前缀」；同一支队在  
   不同群的执行档可以指定不同运行时（见 ③）。据此在远端卡上写「Codex」等于替宿主回答，  
   而它下一单未必用 Codex。

于是远端卡的副行里，`hub_workstation_format` 的「驱动」那半恒为空，只剩目录数；  
「它在哪台电脑上」由设备段头回答（分组之后不再由副行重复一遍）。  
这不是「信息缺失」，是「这半边的事实不在我这」。

**现状**（已核对代码，不是待做）：`DesktopAgentWorkstationPort.workstationOf` 对  
`hostNodeId != selfNodeId` 一律返回 `null`，所以远端卡今天就不画运行时；`employeeProfileOf`  
也已经按宿主收口，编辑键不会长在远端卡上。缺的只有**设备分组**（段头 + 本机优先），  
以及分组后副行去重（宿主名不再写第二遍）。

**一个待收紧的口子（fail-open）**：`AgentTeamDetailView` 的宿主判据是
`selfNodeId == null || detail.hostNodeId == selfNodeId` —— 身份为空时按「我是宿主」处理。
调用方传的是 `settings.nodeId`（正常恒非空），所以现在走不到；但一旦为空，就能给别人的队
写执行档。改成「非空**且**相等」，并给一条测试。

### ① 基座：从「能看见」到「能用」

**目标**：用户打开执行配置，看到的是**七家的完整盘面**，不是「装了几个」，并且**能在派单之前  
自己查出问题、当场拿到解法**。

- 每家一张卡，带**厂商标识**（见 §3.2 的 logo 规格），四态：**可用**（绿点）/ **需登录**（黄点）/  
  **需选模型**（琥珀点）/ **未装**（灰点）。三档「有问题」只在**已知**时着色（`DriverAuthStateUi`  
  的 `NOT_AUTHENTICATED` / `APP_MODEL`），`UNKNOWN` 一律不着色 —— 宁可不说，不许猜。
- **检测是显式动作，不是启动预检**。两级入口：段头「全部检测」（七家并发）、每卡「重查」。  
  一次全量约等于最慢那家（agy 首次 ≈6s），所以**并发 + 先回先渲染**，不做整页 loading。
- 检测结果**直接落在卡片上**，并且自带解法：需登录 ⇒ 「复制登录命令」+ 命令原文；需选模型 ⇒  
  「打开应用」；未装 ⇒ 「安装说明」。**这就是「不用等派单才发现」的兑现方式** —— 检测负责  
  更早地发现，按钮负责把人送到那一步。
- **不在卡片上做「一键登录」**：登录是交互式终端行为，应用代替不了。给命令 + 给复制就是到位。
- 检测**只读、幂等、不写任何档案**，随手点没有副作用；结果带时间戳，过期只标「可能已过期」，  
  不做后台自动重检（那是把「用户触发」偷换成「常驻轮询」）。

> 与 multica 的差别要说清：它不预检，是因为 daemon 常驻、失败即分类、重试有上下文；  
> 我们的 CLI 是**按任务 spawn**，一次失败就是一整轮白等。所以「不自动预检 + 提供按需检测」  
> 才是这个架构下的最优解：不付启动成本，又能在派单前把问题摆出来。

### ② 员工：一个声明，不是一个进程

**这一站是整条链的枢纽，也是现在最假的一站。**

现在的模型把「员工」定义成「已经上报身份的 agent 的档案」。于是：
一台干净的机器 ⇒ 没有 agent 上报 ⇒ 建不了员工 ⇒ 建不了团队 ⇒ 派不了单 ⇒ 更不会有 agent 上报。
**闭环死锁**。

**改成：员工是一份声明，不是等一个进程上线。** 这和主流框架的模型一致，也是本仓派单代码
本来就需要的那一种形状（见下「为什么这样天然成立」）：

| 框架 | agent 身份是什么 | 运行时/模型放哪 |
|---|---|---|
| CrewAI | `role` + `goal` + `backstory`（**纯声明**） | 每个 agent 自带 `llm`（`llm="openai/gpt-4o"`） |
| LangGraph | system prompt 里的人设（**纯人设**） | 每个 agent 绑自己的 model 实例 |
| AutoGen | `AgentId(type, key)`：type = 工厂，key = 运行时给的键 | 由工厂按需创建，**实例不预先存在** |

三家一致的结论：**agent 是「人设 + 模型」的声明，不是「一个已经装在机器上的程序实例」。**
没有任何一家要求「先有个进程在跑，你才能定义 agent」。本方案照此定稿。

#### 三层正交（唯一权威模型）

一个员工的完整描述由三样东西组成，**互不派生、互不替代**：

| 维度 | 值 | 归谁 | 稳定性 | 进身份判定？ |
|---|---|---|---|---|
| **身份** | `employeeId`（`emp-<base36>-<hex4>`） | 员工档案（本机持久化 `settings.employeeProfiles`） | 跨重启稳定、终身不变 | **是** —— 落档 / 配对 / 撞名 / 卡面 / 席位归属 |
| **配置** | `driverKey` + `model` | **员工档案自带**（派单期可被执行档覆盖） | 建人时定，可改 | 否 —— 只决定「用哪家跑、用哪个模型」 |
| **称呼** | `token`（群内 `@` 用） | 员工档案（本机唯一）、席位 `name`（群内可别名） | 可改 | 否 |

**一句话**：`employeeId` 定「是谁」，`driverKey`+`model` 定「谁来干、怎么干」，`token` 定「怎么叫它」。

**`agentId`（`dsh-029bbbf3` 这类）不在上表里，它也不再是身份。** 它是**某个运行时实例自报的路由线索**，
只在这两处出现：① 心跳/会话上报时归组（`sameAgent` 聚类）；② 需要精确投递时区分同家的多个实例
（`wsId` + `sessionId`）。**员工档案不再依赖它存在。**

#### 为什么这是天然成立的形状（三条代码证据）

**[事实] 派单根本不需要「实例 id」。** `dispatchSingleWorker` 只吃三样：

```kotlin
private fun dispatchSingleWorker(
    convId, groupId, prompt,
    agentKey: String? = null,   // ← driverKey（codex/claude/dsh…）
    wsId: String? = null,
    model: String? = null,      // ← 模型
)
```

本仓是**按任务 spawn 一个 CLI 进程**（不是连一个常驻 daemon），所以「派给谁」= 「用哪个
`driverKey` spawn、带哪个 `model`、进哪个 `wsId`」。**没有一处需要预先存在的实例 id。**

**[事实] 派单帧里的 `agentId` 语义本来就是 driverKey。** `handlePromptAwait(agentKey = ...)` 的
注释写着「`agentKey` 来自派单帧的 `agentId`（codex/claude/antigravity…）」——它一直是**类型**，
只是名字叫 `agentId`，于是被误读成实例身份。

**[事实] 团队早就在用合成 id 派单。** 团队组员的 `agentId` 是 `m-<slug>-<rand>`
（`newTeamScaffoldAgentId`），从来不是任何进程的 id，而团队派单一真跑就是一年多。
**员工用 `employeeId` 与团队用 `m-…` 是同一种形状**，不是新发明。

#### 由此重述两个洞（都不是「缺字段」，而是「身份选错了」）

> **洞 A（收敛是假象）**：卡面 `canonicalKey` 取自会话登记 `session.agentId`，而那是 kind/plugin
> 级值；进程自报的 hex 只做路由。所谓「MINT 键与卡收敛」是 `sameAgent` 同 head 全并的假象
> （hex 段是装饰）。**修法不是改 hex，也不是把 hex 塞进帧**：会话登记的 `employeeId` 由**派单侧
> 直接写**（席位 `employeeId` 当场可读），卡面身份 = `employeeId`。
>
> **洞 E（同底座第二个人被堵）**：`createEmployee` 撞名检查用 `sameAgent` 抹平 head ⇒ 同底座第二个
> 员工撞 `EMPLOYEE_EXISTS`。根因是用**路由尺**做**身份判定**。修法：撞名/配对/席位归属全改按
> `employeeId` 精确；`sameAgent` **一字不动**，永久限定为路由聚类。

#### 建档：一张单页表单，四到五个字段

| 字段 | 取值 | 缺省 | 校验 |
|---|---|---|---|
| **运行时** | 在位的运行时（未装的不列），下拉单选 | 只有一个在位时预选并转只读行 | 必填；**绝不给默认值兜底** |
| **模型**（仅该运行时支持按任务指定时出现） | 该运行时可选模型 | 跟随驱动默认（"不指定"是合法选项） | 可空 |
| **名字** | 文本 | 空（不预填 `dsh-coder`） | 必填，长度同 `Limits.NICK` |
| **群里怎么 `@` 它**（token） | 由名字派生、可就地改；字段下方常驻显示最终值 | `slug(名字)`；中文名派生为空 ⇒ `运行时-职责`（如 `claude-coder`） | 必填、已归一、本机唯一；冲突就地加 `-2` 并回显 |
| **职责** | `AgentDuties` 归一后的枚举 | `coder` | 必填 |

> **模型的字段是有条件的，不是漏了。** 是否出现由 `driverCatalog()` 投影里的
> `supportsPerTaskModel` 决定（`CliDriverSpecs.Spec` 已有这个字段）；**`dsh` 与 `zcode` 为 false**
> （不是「那一家」），不支持的不画这一格，而不是画一个点了没用的下拉（不变量 3）。
> 对支持的 5 家（codex / claude / agy / opencode / codebuddy），「同底座两人不同模型」是真实的
> 区分手段（与 CrewAI/LangGraph 的做法一致）；**dsh 上不成立** —— 那一档两人的区分落在
> 名字 / 职责 / 人设上，产品文案不许承诺「同一运行时可以配不同模型」这种一概而论的话。

> **token 这一行不是可选项。** `@` 用的是 token，而中文名（`小科`）的 `slug` 为空
> （`AgentMemberName.slug` 只留 `[a-z0-9]`），token 会回落成 `运行时-职责` —— 用户 `@小科`
> 打不到。不显示最终值，用户只有派单失败那天才知道。**派生规则只有一份**
> （`defaultEmployeeToken`），表单只负责显示与允许覆盖。

> **表单里没有「项目目录」，也没有「用哪个实例」。** 目录不属于人：他在哪个目录干活由**群的项目
> 指针**或会话自己宣告的 workspace 决定；实例不属于人：按任务 spawn，不需要预先存在。

#### 保存时写什么（不新增表，只给 `EmployeeProfile` 补两个字段）

```kotlin
EmployeeProfile(
    employeeId,              // 身份锚（本机分配，终身不变）
    agentId: String = "",    // 兼容/路由线索：最近一次派单用的实例键；空串 = 尚未派过
    name, token, duty,
    driverKey: String = "",  // ← 新增：建人时选定的运行时；空串 = 未选/老数据（必须带默认值，见 §3.9）
    model: String? = null,   // ← 新增：null = 跟随驱动默认
)
```

四条纪律：

1. **`driverKey` 是员工档案的必需字段**（不是"可选参考"）—— 没有它就必须去猜，而本仓不变量 1
   是「不猜底座」。这让 `resolveKey` 的「从实例键前缀反解」彻底退化为**老数据兼容路径**。
2. **`agentId` 变为可空、可更新的路由线索**，不再参与身份判定；建人时为空（还没派过单），
   首次成功派单后由宿主回填（纯观测，失败不回填、不阻塞）。
3. **`driverKey` 必须在该机 `driverCatalog()` 里**（MINT 档的预校验）。**不校验「有实例在跑」**
   —— 那正是死锁的成因。
4. **派单期优先级**：执行档（`(dirId, leaderAgentId)` 的成员 `driverKey`）> 员工档案 > 拒绝。
   执行档更具体（按目录、按队伍），员工档案是默认值。**两处都不给就拒绝，不回落默认驱动。**

#### 建档两档来源（差别只在预校验）

| 来源 | 台账要求 | 用来防什么 |
|---|---|---|
| `REGISTER_EXISTING`（登记一个已经在跑的 agent） | 台账非空时必须命中 | 幽灵员工 |
| `MINT`（新建一个声明式员工） | **不要求命中**，只要求 `driverKey` 在 `driverCatalog()` 里 | 建出一个派不出去的运行时 |

两条路共用一个命令、一份档案结构，差别只在**预校验**，不在落盘。守卫测试要同时钉住两档
（MINT 不能因为台账非空而红；REGISTER 不能因为「反正要建人」而放过幽灵）。

> **为什么现在必须做两档**：`agentIsKnownOrUnknown` 的现行判据是「本机工作区台账非空时，要建的
> agentId 必须已经在台账里」。它防的是登记一个不存在的 agent（幽灵员工），但对「身份由本机声明」
> 这条路是硬拦：机器上只要跑过任何一个 agent，新建员工就会被 `EMPLOYEE_UNKNOWN` 拒掉。

#### 席位：员工进群时发生什么

**席位不是员工的必要条件，是员工进某个群之后才有的东西。**

- 建人时 `groupIds` 可以为空（只建档、不进任何群）—— 员工照样能被 AI 建队复用、能被 1:1 派单；
- 员工进群时建一条席位，席位带 `employeeId` 引用（**字段已存在、已在 `group` 帧里编解码**，无需改协议）
  —— 注意 `group` 帧**故意没有字段白名单**（只有形状校验，未知键照旧忽略），所以加这个键
  既不拒收旧端、也不需要两端同版本；这一点与 `msg` 的严格白名单相反，别混；
- **席位键仍是 `(hostNodeId, agentId)`**，`employeeId` 是引用而非键 —— 所以**同底座两个人天然各占
  一条席位**，只要他们派单时用的 `agentId` 不同（不同实例），或即使相同也不影响身份判定
  （归属按 `employeeId`，不按 `agentId`）。
- **`seatAgentIdFor` 的三段判据（本轮修正，替代现在的两段）**：

  | 序 | 判据 | 结果 |
  |---|---|---|
  | 1 | 某条本机席位的 `employeeId` == 档案 `employeeId` | **命中**（精确，永远优先） |
  | 2 | 无引用，且该群本机**恰有 1 条**席位与档案 `agentId` 精确相等 | 命中（首次挂档案的正常路径） |
  | 3 | 无引用，且 `sameAgent` 命中**多条** | **不猜**：返回「席位待确认」，UI 走 blocked 卡主行动「去群编制确认」 |

  第 2 段的 `sameAgent` **只在「该群本机只有一条席位」时保留**（老数据的首次认领），
  多于一条时绝不认 —— 那是把 A 的席位给 B 的唯一路径。
  第 3 档只在**升级瞬间的老数据**出现（席位由旧版本建、还没有 `employeeId`）；用户确认一次
  写入引用后永久消除。**它不需要新的交互面**：复用 §3.5 的 blocked 卡 + 群编制页既有的席位绑定。

> **上一版把它判成「架构缺口（需迁席位键、牵动 GroupMeta 协议）」—— 这个判断是错的。**
> 代码实测：席位定位 `localSeat` 是 `(hostNodeId, agentId)` **精确实比**，`defaultWsId` 已是投影、
> 不在键里；`planJoinSeat` 的替换条件也是**精确 agentId**；派单按 `agentId` 精确取席位；
> 而 `employeeId` 早已进 `GroupMeta` 且有编解码校验（`CodecGroup` 的 expects-keys + 形状校验）。
> 那次 `@Ignore` 测试里两个员工传的是**同一个常量 `agentId = "dsh"`**，所以它测出来的「顶席位」
> 是**测试构造与旧撞名判据**的产物，不是席位键的设计缺陷。
> 结论：**不需要改协议、不需要迁键**，改的是两处 `sameAgent` 兜底 + 撞名判据。

#### 恢复链路（进程挂了 / 宿主重启了）

- **进程级崩溃（宿主不重启）**：工单 `activeTickets[tid]` 在内存持有 `devPrompt/repoPath/agentKey`，
  自愈循环同工单重发提示词；卡靠 `employeeId` 归同一员工 —— 换的是**壳里的进程**，不是人，
  也不是活儿。模型自洽，无需改动。
- **宿主级重启**：`activeTickets` 是纯内存 `ConcurrentHashMap`（含 `Job`、`CompletableDeferred`
  等不可序列化对象），编排器无 init 回填；`TeamExecutionStore` 只存执行档不存工单 ⇒
  「同一员工接着干」会断。**列为 P3 独立缺口（工单持久化回填），不阻塞 P1a**。
- **员工档案本身跨重启稳定**（`employeeId` + `driverKey` 落 `settings.employeeProfiles`），
  所以重启后「这个人还在、用哪家跑还在」，只是「手上那半件活」丢了。这是两条独立的命，
  不要混成一句「重启即失忆」。

#### 已否决的路（理由记录在案，实现者不要再提）

- **「一个底座一个员工」**：砍掉「同一运行时多席位人设/模型不同」的核心卖点，是伪选项。
  竞品三家都支持同一后端多 agent。
- **「拿进程 hex 当身份、落档 + 精确相等」**：hex 生命周期归进程、可变，重启后归不回档案；
  且正是「类型 + 实例混在一个字段」的病根。
- **「MINT 铸一个假 `<driverKey>-<8hex>` 当 agentId」**（本方案上一版的错案）：铸出来的键与真实
  运行时自报的实例键**永远不相等** ⇒ 会话落不到席位 ⇒ 就是本仓最贵的「发送侧成功、接收侧什么
  都没有」；若为了回避不一致而回写档案，就变成用进程 hex 当身份，洞 A 复发。**假身份比没有身份更糟。**
- **「员工必须绑一个当前在位的实例」**：把「先有进程」重新变成建人的前提，死锁原地复活；
  且与竞品模型相反。

#### 未落地：帧路径（留档，本轮不做）

`employeeId` 进 `agent-session` 帧这条**本轮不采用**，理由在「已否决的路」最后一条同一层：进程
不知道自己是哪个员工，外部 agent 报的会话里永远不会有这个键。它只影响一档 —— **远端宿主起的会话
归到本机员工**；本机链完全不依赖。

**触发条件（满足任一条才回头做，别提前做）**：
1. 产品要支持「员工跨宿主归属」（一个人在 A 机器建档、在 B 机器上跑）；
2. 卡面需要显示「这个会话属于哪个员工」而**本机席位读不到**（今天恒能读到）。

做的时候按这张表四段补齐（已核实每段现状），并注意 `agent-session` 走 `tolerantKeys`
（未知键忽略而非整帧拒收）⇒ 加键不打崩旧端，但**新端要读到它仍需收发两端同版本**，
黄金向量同步更新。`group` 帧不同：它**没有字段白名单**，加键零风险（§2② 席位一节已写明）。

> 四段链路与各自现状：`AgentInvokeTaskRequest` **不带** `employeeId` → `invokeExecutor`
> **不传身份** → `executePluginTask` 写 `SessionRecord.agentId` 为 kind 级值 → `SessionRecord`
> **无** `employeeId` 字段。逐段补即可，无需重构。

#### 不做的事

- **不做「员工级 prompt」**：人设属于**团队名册的一行**（`TeamMemberInfo.prompt`，团队范围），
  派单期作为执行档 `customPrompt` 初值。同一员工在两支队的人设本就该不同（一支写代码、一支做审查）。
  要不要「每个员工一份默认人设」是另一个问题，得先定它与团队人设的优先级，不在本轮。
- **不做常驻 daemon**：本仓按任务 spawn；常驻能换来「登录态一次到位、启动更快」，代价是进程
  生命周期、僵尸进程、升级一致性三座山。等派单频率上来再单独评估。

### ③ 团队：从现成的人里组队，缺了才建

**目标**：从「挑一个已存在的 agent」改成「先有员工，再由员工组队」。

- 新建团队 = 团队名 + 领队（下拉：**本机全部员工**，不是员工名录） + 组员（可 0 人）。
  **没有「群」这一步**：团队不是群的一部分，「去哪干活」在群里决定（见下「目录不是团队的字段」）。
- 领队为空但员工非空 ⇒ 正常；员工为空 ⇒ **表单照常展开**，领队位置放一颗
  「先建一个员工」的按钮（就地跳 ②，回来后带着新员工预选）。**不再整张表单不展开**。
- **组员优先是已有员工，不是新编制行**。这一条以前只写在手动建队的下拉里，AI 建队整条路
  都没兑现（它凭空造名字）。为什么必须兑现：员工的身份是 `employeeId`（`emp-…`），
  而团队组员行带的是编制 id（`m-dev-coder-a1b2`）——**两套 id 空间**，AI 只产第二套，
  于是用户明明已经有两个员工，AI 还是造出两个陌生人；而这两个陌生人的运行时是 LLM 猜的，
  与他真有的人无关。复用行改带 `employeeId` 之后两套空间就并成了一套（§3.4.1）。
- 顺序上**结构约束优先于复用**：恰 1 worker + reviewer 异厂商是硬约束，池里凑不出来时
  宁可新建一行，也不为了让"都用现成人"而派不出去。

#### 目录不是团队的字段（这一条必须钉死）

目录是**群**的属性，不是团队的，也不是员工的：

| 谁持有目录 | 字段 / 命令 | 含义 |
|---|---|---|
| 群 | 项目指针 `dirId`（`POST /v1/host/group-directory`） | 这个群在哪个仓里干活 |
| 会话 | `agent-workspace` 的 `wsPath` | 某个 agent 实际宣告的工作目录 |
| 执行档 | 主键 `(dirId, leaderAgentId)` | **dirId 取自群指针**，不是团队档案 |

于是「一支队去哪干活」和「有几份执行档」是两回事，而两者都**不是团队的字段**：

- 同一个目录下有多个群 ⇒ **一份档**（按群存 N 次是同一份覆盖，不是 N 份）；
- 不同目录 ⇒ 每个目录一份档（工作副本不同，运行时/模型可以不同）；
- 群**没有目录** ⇒ 那个群暂时没有档可挂，在它里面派单会被 `NO_DIRECTORY` 拦住。

**所以建团队时不选群。** 建队只写三样：团队名、领队、名册 —— `TeamProfile` 本来就只有
`teamId / name / leaderAgentId / members`。**「进哪个群」是另一个动作**，而且已经有它的落点：
群信息页的「添加团队」（`attachTeamToGroup`）。派单期再按**该群的项目目录**取/建执行档
（`(dirId, leaderAgentId)`，初值取 `initialExecutionProfileUi`：第一名 worker、其余 reviewer）。

这条同时删掉一整类缺陷：上一版让建队时按 `groupIds` 预写执行档，于是「群没设目录」在
`mapNotNull` 里被**静默丢掉**、横幅只报 `Rejected`，用户以为都配好了。**不选群，就没有这次跳过。**

> **代价要说清（一次性的）**：建队不绑群之后，在一个**还没入驻过**该队的群里 `@队名`，第一次会
> 被 `TEAM_NOT_IN_GROUP` 拦住（§3.5），主行动是「把队加进这个群」—— 点一下就过，之后不再出现。
> 这比「建队时猜它去哪、猜错静默丢」便宜得多，也符合不变量 2（不许静默）。
>
> **现状（`@HEAD`）**：`saveTeamProfile(teamId, name, leaderAgentId, members, groupIds)` 的 KDoc
> 写着「新建 = 要加入的群（**至少一个**）」—— 群现在是**创建契约的必填项**。改成允许 0 个群，
> 动的是 `:app` 接口 + 桌面壳 + 手机壳 + 既有测试，属于 P1b 的工作量，不是 UI 删一行。

### ④ 派单：三个入口，一套编译

| 入口 | 语义 | 失败落点 |
|---|---|---|
| 群内 `@员工` / `@团队` | 席位派单；团队名编译成 worker + reviewers；运行时取**该群目录下的执行档**，没有再取**员工档案的 `driverKey`** | 群里一张 blocked 卡（全群可见） |
| 1:1 会话（对话按钮） | 单员工；运行时同上（执行档缺失时读档案 `driverKey`），两处都没有则拒绝而非猜 | 会话内一条系统消息 + 「去配置」 |
| 工作区任务卡（quest / chain） | 带目录的工单；目录决定执行档查询键 | 卡片正文 + 重试 |

派单时**不自动探登录**（探针留给配置页那颗检测按钮，见 §3.2）。派单当场判的只有三类
**结构性**前提，因为它们不可能靠「再跑一次」自愈：底座能确定、目录存在且在白名单、派单者有权。
三类缺一 ⇒ 立刻 blocked，理由带**分类码**（不再是一句散文）。完整 7 个码与判定顺序见 **§3.5**，
这里只列「结构类」的四条（另三条是 `TEAM_NOT_IN_GROUP` / `TARGET_MISSING` / `DRIVER_MISSING`）：

| 分类码 | 触发判据 | 用户看到 | 下一动作 |
|---|---|---|---|
| `NO_DRIVER` | 该群无执行档 **∧** 员工档案 `driverKey` 为空（老数据再试 `resolveKey`，解不出才算） | 「这个员工用哪个运行时跑，定不下来」 | 「去配置」→ 群编制指派，或员工档案选一个运行时 |
| `NO_DIRECTORY` | 该群 `groupPointerDirId` 为空 | 「这个群还没绑项目目录」 | 「选目录」→ 群信息 |
| `DIR_NOT_ALLOWED` | 目录不在白名单 | 「这台机器没授权这个目录」 | 「去授权」→ 可信设备页 |
| `NOT_AUTHORIZED` | `AgentExecAuthorizer` 拒绝 | 「你没有调用它的权限」 | 「申请授权」（既有 `sendAgentGrantRequest` 通路） |

### ⑤ 结果：失败要带下一步

- 登录等待：`QuestAuthWaitDetector` 已能分流 `TERMINAL_LOGIN` / `TOKEN_ENV` / `APP_MODEL`，
  把 `decorateError` 的产物从「错误尾部」提升到**卡片正文的固定一行**（现在只在折叠的日志里）。
- 模型缺失（`APP_MODEL`）：文案必须是「去应用里选一个模型」，不是「认证失败」。
- 每一次失败卡片都带一颗**重试**，重试前不清空上下文（复用 `retryByCard`）。

## 3. 界面样式规格（每一站长什么样）

> 这一节是**给实现的规格**，不是效果图。所有尺寸写 token 名不写 dp 字面量（`designTokenUsageGate`
> 会红），所有颜色写语义名不写色值（深色模式必须能自动换），所有文案给键名 + 中英成对
> （`designLocaleParityGate` 会红）。

### 3.0 视觉基座：只用已有 token，不新增档

| 用途 | 取值 | 现状 / 出处 |
|---|---|---|
| 页面底 | `colorScheme.background` | 桌面外壳与手机壳同一支主题 |
| 卡片容器 | `colorScheme.surface` + `relayCardShadow()` | `SectionCard` 就是这一套 |
| 卡圆角 | `LocalCardShape.current` | 手机 16dp / 桌面 12dp，**不要写 `shapes.small`**（会污染调用屏的 screenDiff 切片） |
| 凹槽 / 图标砖 / 头像底 | `accents.surface3` | 与分隔线 `outlineVariant` 是两个 token，别互借 |
| 间距 | `AppSpacing` 八档主力（`xxs 2 / xs 4 / sm 8 / md 12 / lg 16 / xl 24 / xxl 32 / xxxl 48`） | 已冻结，不许加档 |
| 卡片标题 | `titleSmall` + `SemiBold` | 与名录行现有一致 |
| 次要信息 | `labelSmall` + `onSurfaceVariant` | 一行，超长省略，不换行 |
| 段头 | `labelLarge` + `SemiBold` | 段头右侧放该段的主行动 |
| 行内图标按钮 | `AppIconButton` + `Modifier.size(sp.xxl)` | 视觉 32dp；触控热区由组件给 48dp |
| 驱动标识 | `DriverBrand.tintOf(vendor)` + 单色 `ic_driver_<vendor>` | 24dp 方砖，按厂商取；规格见 §3.2 |

**状态语义（四档，全局唯一映射）**

| 语义 | 颜色 | 形态 | 用于 |
|---|---|---|---|
| 在位 / 在线 | `accents.online` | 6dp 实心圆点（`StatusDot`） | 卡片、基座卡 |
| 需处理（未登录 / 未设目录 / 跳过） | `accents.warn` | 圆点 + `warn` 12% 底药丸 | 基座卡、横幅 |
| 不可用（未装 / 未授权） | `outlineVariant` 点，字 `onSurfaceVariant` | 灰点，**不置灰整张卡** | 基座卡 |
| 失败 / 拒绝 | `colorScheme.error` | 实心药丸（`PendingPill` 同形） | blocked 卡、校验 |

> **反例：绿点恒亮。** 现在基座卡每张都有绿点，于是这个点零信息。点只有在**有另一档可比**时
> 才有意义 —— 七家全画、三态着色，点才成立。

**用词：界面上不许出现「底座」**

「底座」是内部叫法（代码里是 `driver` / `driverKey`），它准确但不属于用户语言。同一件事在
两层的叫法必须分开，且**只有一张映射表**：

| 界面文案 | 内部术语 | 说明 |
|---|---|---|
| 运行时 | 底座 / `driver` / `driverKey` | 七个具体产品；第一次出现配一句「装在这台电脑上、能替员工干活的程序」 |
| 检测 | auth probe（`driverAuthStates`） | 显式动作，不是启动预检 |
| 员工 | `EmployeeProfile` | 「智能体员工」只在需要强调时用，日常就是「员工」 |
| 执行配置 | 基座盘面 / `DriverCatalog` | 既有页名，本轮不改（改页名要连带改导航与文档，性价比低） |

现有 6 处用户可见文案里带「底座」，随 P1 一起换掉（`exec_config_catalog_title` /
`_catalog_none` / `_subtitle_format` / `exec_config_edit_hint` / `agent_empty_message` /
`agent_empty_card`）。**变量名、注释、文档内部叙述继续用「底座」** —— 换的是用户语言，
不是领域模型；两边都改反而会让代码与实现说明脱节。

### 3.1 智能体页（一级）：档位切换 + 设备分组

**这一页是两档，不是三段堆叠。** 段头左侧写当前档（`智能体 · N 条` / `团队 · N 条`），右侧两枚
chip 换档（`AgentDirectoryView`，实现在 `AgentDirectorySection`）。切换器换的是**哪一段**，
不是「智能体」这个分类的筛选 —— 所以段头文字必须跟档位走：切到团队档还写「智能体」，一屏
会出现两个标题、且第一个是错的（这条已在 `TabChromeConsistencyGuardTest` 附近钉过）。

| 档 | 内部顺序 | 理由 |
|---|---|---|
| 员工 | **执行配置入口行**（`!compact` 才画）→ 设备分组的名录 → 登记簿（未入驻的档案 + 新建档案） | 先「谁在干活」，再「登记簿」；入口行是「去哪加运行时」，窄列里让位给名录。**登记簿里的档案不需要先进群**（§3.4 目录那节） |
| 团队 | 团队名录 → 还没派过单的团队（孤儿档案） | 先「我编了哪些队」，再「孤儿档案」 |

**团队段是「一队一行」，永远不是「一队 × 群 = N 行」**。群归属是**引用关系**（席位住在
`GroupMeta` 里），不是团队档案的字段（`TeamProfile` 只有 `teamId / name / leaderAgentId /
members`）。把它按群展开是**群的视角**，属于群信息页；搬到员工页会让同一支队在这里出现 N 次，
用户以为编了 N 支队。

**为什么不三段堆叠**：团队段仍可能与员工段争同一屏（队多的时候），堆在员工名录下面会把
「员工档案」推到一屏之外；而档案是低频治理动作 —— 藏起来可以，消失不行。

用「名录」不用「卡片流」：它本来就是**一个容器内的行**（`AgentRoster` = `LocalCardShape`
+ 行间 `HorizontalDivider`），不是一叠各自带框的卡。「卡片流」会让实现者对着一堆独立卡
去画，268dp 里三层投影互相吃边距，对不齐。

桌面两栏（`AgentHubLayout.TwoColumn`，左列 `ContentWidths.Sidebar` 300dp／内容 268dp）：

```
┌─ 左列 268dp ───────────────────────────┐┌─ 右列（随下钻换页）────────────────────┐
│ 智能体 · 2 条            [员工] 团队   ││ 员工详情 / 团队详情 / 工作区详情       │
│ 这台电脑          1 个在跑 · 共 2 个   ││ （点左列任意一行 → 右列换页）          │
│ ┌────────────────────────────────────┐ ││                                        │
│ │ ● 小科                    [待批 2] │ ││                                        │
│ │ Claude Code · 3 个目录          💬 │ ││                                        │
│ ├────────────────────────────────────┤ ││                                        │
│ │ ○ 小助手                    [离线] │ ││                                        │
│ │ Codex · 1 个目录                💬 │ ││                                        │
│ └────────────────────────────────────┘ ││                                        │
│ 我的 MacBook                1 个在跑   ││                                        │
│ ┌────────────────────────────────────┐ ││                                        │
│ │ ● 评审员                        💬 │ ││                                        │
│ │ 2 个目录 · 最近 12 分钟前          │ ││                                        │
│ └────────────────────────────────────┘ ││                                        │
└────────────────────────────────────────┘└────────────────────────────────────────┘
```

> **图里的四件事，都是上一版画错的地方**
>
> 1. **不是「每卡一个框」**：行住在同一个容器里（`AgentRoster`：`LocalCardShape` + 行间
>    `HorizontalDivider`）。所以**一个设备段内只有一个圆角块**，段与段之间靠段头 + 间距分开。
> 2. **窄列只有两行**：标题（状态点 + 名字 + 状态格）与副行；第三行（执行中摘要 /
>    最近交付）和右侧活动时刻在 268dp 里不画 —— 画了就会把名字截成 `cod…`（实测只给
>    名字剩 58dp）。宽态才画第三行。
> 3. **宿主名由段头承担**，副行不再重复：本机「运行时短名 · 目录数」，远端「目录数」。
>    原 `hub_workstation_format` 是「运行时 (宿主)」两段，分组后会每行各写一次设备名。
>    **副行里没有群**：群归属是引用关系，画在员工/团队行上等于把群的视角搬进名录（见 §3 开头）。
> 4. **一行一颗图标**（对话）。编辑落详情页（行本身可点），低频且带破坏性的动作不占行尾。
>    现状是「两个回调都非空就画两颗」——窄列里再吃 32dp，名字先被截；P1 收成一颗。

**名录行规格（这张表是本节最该被照抄的部分）**

| 槽位 | 本机行（宽态） | 远端行（宽态） | 窄列（268） |
|---|---|---|---|
| 行首状态点 | 画 | 画 | 画 |
| 标题（`titleSmall/SemiBold`，1 行） | 画 | 画 | 画 |
| 副行（`labelSmall`，` · ` 连） | **运行时短名 · 目录数**（前置 12dp logo） | **只有目录数**（宿主名由段头承担；运行时不在本机，`workstationOf` 对非本机返回 null；**不画群**） | 只画一段：本机 = 运行时短名，远端 = 目录数（拼两段必截断） |
| 第三行（执行中摘要 / 最近交付） | 画 | 画 | **不画**（268 里三行会把状态格挤出去） |
| 右侧状态格（待批药丸 > 执行态 > 离线）+ 最近活动 | 画 | 画 | 只保留状态格 |
| 行尾图标按钮 | 档案编辑 + 对话（两颗 32） | **只有对话**（一颗） | **一颗：对话**（编辑落详情页） |
| 整行点击 | 进员工详情 | 进员工详情（只读） | 同 |

**离线不是一个独立槽位**：它是状态格的第三档（没有待批、也没有执行中时才出现 `[离线]`）。
独立加一行会让窄列同时出现两颗标签，而它们回答的是同一个问题「它现在能不能干活」。

**两层段头，层级必须拉开**（都在 268dp 里，同字号就等于两行并排、读不出谁管谁）：

| 层 | 内容 | 字号 | 颜色 |
|---|---|---|---|
| 档位段头 | `智能体 · N 条` + 两枚 chip（员工 / 团队） | `labelMedium/SemiBold` | `onSurfaceVariant` |
| 设备段头（只在员工档） | 设备名 + `<在跑数> 个在跑 · 共 <总数> 个` | `labelSmall/SemiBold` | `onSurfaceVariant` |

两层的颜色**现在是一样的**，层级全靠字阶（`labelMedium` vs `labelSmall`）承担。**不要**为了「拉开」
把档位段头改成 `onSurface`：切换器会比它管的内容还重，而这一屏的主体是名录不是标题。

本机段名读新增键 `hub_section_local`（**现在不存在，要加**），远端段名读设备名。本机永远
第一段；远端段按近 24h 活跃度降序。**排序键已经存在，不必新增协议字段**：卡片投影已有
`AgentHubUi.lastActivityAt`（来自该实体会话的 agent 事件时刻，`lastEventAtOf`），设备段取
该设备下所有卡片的 `max(lastActivityAt)` 降序，`0` 排后，同值用 `hostNodeId` 稳定排序。
**不要用 `PeerUi.lastSeenAt` 当活跃度** —— 那条时间被局域网发现心跳持续刷新，语义是
「链路可见」而不是「有智能体在干活」，用它排会让一台只是在线但没跑过任何 agent 的设备
冒到最前面（`AgentUi.lastMessageAt` 的注释已经记过同一类混用事故）。**不做筛选器**（§2.0），
「近 24h」只是解释活跃度窗口的说法，不是把更早的设备藏起来的过滤条件。

**名录段头不放「＋新建员工」**：新建员工在员工档案段（P1 收成一条入口，见 §3.3）。段头已经
被「档位 + 计数 + 两枚 chip」占满，再塞一颗按钮只会把 chip 挤成缩写 —— 而这颗按钮的落点
本来就不是名录（名录回答「谁在跑」，不是「怎么加人」）。

计数必须两个数都给：只写「2 个在跑」而下面有一行离线，是这一页最容易犯的错（离线行不是
「不存在的行」—— 它是你的员工，只是现在没跑，还要能点进去改档案）。反过来只写「共 2 个」
也不够：用户来这一页第一眼要的是「现在有几个在干活」。

**空态四档**（现在共用一句话，这是「嫁祸对端」的根因）。**判据按顺序求值，首个命中即用** ——
不然「只有远端在跑」同时满足 A 和 C，两个空态会抢同一块地方：

| 档 | 情境 | 判据（`AgentSlice` / `NodeSlice` 事实） | 标题 | 正文 | 主行动 | 副行动 |
|---|---|---|---|---|---|---|
| D | 一台设备都没连 | 已连节点为 0 | 一台设备都还没连上 | 先在节点页配对，再回来看这里 | 去看看节点 | — |
| A | 有设备，但谁都没跑 | `hubAgents` 为空 | 还没有员工 | 建一个员工，接上本机的运行时，它就能开始接活 | **新建员工**（实心） | 执行配置 |
| B | 本机有员工但没在跑 | 无本机行 ∧ 本机档案非空 | 员工都还没开始跑 | 建一支队，或直接派一次单 | 建团队 | 执行配置 |
| C | 只有别的设备在跑 | 无本机行 ∧ 本机档案为空 | 只有别的设备在跑 | 这台电脑还没有员工；下面这些来自其他设备 | 新建员工 | 看看节点 |

> **员工与团队都不以群为前提 —— 空态里不许出现「先加进一个群」。** 名录只回答「谁在**跑**」；
> 没在跑的档案在**登记簿**里照样可见、照样能点开改，用不着先挂进任何群。把它写成「还没加进任何群」，
> 等于把「员工存在的意义」绑在群上：而团队是「名册 + 执行档（按目录）」，群只是它**去哪干活**
> （§3 已写明群可 0 个），席位与执行档的目录来自群，但**员工与团队的存在不来自群**。
> 真有群相关的那一步只有一个：派单时该群没有项目目录 ⇒ `NO_DIRECTORY`（§3.5），那是派单的拦截，
> 不是建人/建队的门槛。

**空段不画段头**：某一台设备此刻 0 行时，不画「这台电脑 · 0 个在跑」—— 段头只在其下有行时
存在。否则空态卡会和一个「0 个在跑」的段头同时出现，等于把「没有」说两遍。

**每条空态都必须有主行动**，且主行动必须落在**能改变该判据**的那一页 —— A/B/C 落在建人，
D 落在配对。只给「去看看节点」是这次的原始缺陷。

**驱动标识（logo）：要做，而且要按厂商取**

七家里只有 `DeepSeek Harness` 是词组，其余六家都是单个英文词（Codex / Claude / Antigravity /

扫一眼几乎分不出来。这一处正是「友好度」的实感位置，不做是省事不是克制。

| 项 | 规格 |
|---|---|
| 键 | **按 `vendor` 取，不按 `driverKey`**（`CliDriverSpecs.Spec.vendor`：openai / anthropic / google / deepseek / tencent / zhipu / opencode）。同厂商新增驱动自动复用，不必再加资产 |

**tint 表（建议值，落地时以各家官方品牌页为准）**

| vendor | 品牌形 | tint |
|---|---|---|
| openai | Codex 的结 / OpenAI 花环 | `colorScheme.onSurface`（黑白品牌，随主题反色） |
| anthropic | Claude 的星芒 | 品牌橙一档（浅深同值，靠着色不靠明度） |
| google | Antigravity 用 Google 蓝 | `#4285F4` |
| deepseek | 蓝鲸 | `#4D6BFE` |
| tencent | CodeBuddy 用腾讯蓝 | `#0052D9` |
| zhipu | ZCode 用智谱蓝 | `#3859FF` |
| opencode | 自有标记 | `colorScheme.onSurfaceVariant` |

> 资产**从官方站点或对应 CLI 包内取**（`.app/Contents/Resources`、npm 包里的 svg），
> 转成单色 path；**不许手绘近似形** —— 画歪的商标比首字块更伤信任。取不到就回落首字块，
> 并把这家的资产缺口记进「新增驱动必须改的七处」清单。

**这 7 个色值会不会撞 `designTokenUsageGate`：实测结论是「不会」—— 上一版把门禁方向读反了。**

那个门量的是 `ui/theme/` **之外**的字面量欠债（`tools/design_contract.py` 的 `iter_source_files`
默认 `include_theme=False`），而 `DriverBrand.kt` 按 §3.9 就住在 `ui/theme/`。三条实测：

| 事实 | 判据 | 结论 |
|---|---|---|
| `Color(0x…)` 欠债只数主题之外的 | `DEBT_PATTERNS["color"]` + 扫描根排除 `ui/theme/` | 写在 `ui/theme/DriverBrand.kt` ⇒ **0 笔欠债** |
| 棘轮只禁「采用面缩小 / 欠债上涨」 | 同脚本的 `compare()` | 新增 token 只让采用面变大、**不触棘轮** |
| `spec ↔ code` 漂移的正规修法 | `:designSpecDrift` 失败 ⇒ 跑 `:designSpecProject` 重投影 | 是**重投影**，不是「重记基线」，也不需要评审批准 |

> 结论：走 **(a)**，做法照 `Accents` 的先例 —— 色值只写 `ui/theme/DriverBrand.kt`，对 feature 层
> 只暴露 `vendor → Color`；改完跑 `:designSpecProject`，再跑 `:designSpecDrift`。
> **不要动 `designTokenUsageBaseline`**，更不要把这件事写成「需评审人批准的例外」：那会把一条
> 本来能直接落的路，变成等一个人点头才能开工（§8 洞 D 已按此改写）。
>
> **(b) 全部单色**保留为退路：代价不是门禁，是七家在深色下只能靠形状区分。两条路都**不许**把
> 品牌色写进 feature 层（`Accents.warn` / `outlineStrong` 的 KDoc 写着同一句话：
> 「写 `Color(0xFFF59E0B)` 于 feature 层必红」）。
>
> 这条同时划清 §3.0「不新增档」的边界：**间距 / 字阶 / 圆角一档都不加**；品牌色是这一轮
> 唯一新增的一档 token（7 个），且只用于 logo 的 tint，不进任何大面积背景。

**检测结果住哪：一份台账，由发起检测的那一方持有。** 结果只在内存（重启即清）、不写档案、
不进协议 —— 但它必须**只有一个实例**：配置页检测完切到别处再切回来，不能又变回「未判定」。
做法与 `ControlPlane` 里那些台账同一条纪律：`DriverAuthLedger` 住 `:app`，写入方（壳）持有，
对外只给只读快照 + `checkedAt`。**另建一份的症状是「刚检测完，页面说没判定过」** —— 这不是
缓存，是同一个事实的第二份副本。

**检测按钮：两级、只读、结果落在卡上**

现状是「底层齐了、入口没有」：`CliAuthProbes` / `DriverAuthProbes` 已经在跑真实探针，
`driverAuthStates()` 端口也已装配（`DesktopTeamExecutionPort`），只是配置页从来不调它。
所以这一步不是新造能力，是**把已有能力接出来**。

| 项 | 规格 |
|---|---|
| 入口 | 段头右「全部检测」（`TextButton`，**在位各家** `awaitAll` 并发）；每卡右「重查」（32dp `ic_refresh` 图标按钮，单家） |
| 时序 | 并发派发、先回先渲染：每张卡独立显示「检测中…」→ 结果。**不做整页 loading、不闪骨架、不打乱卡片顺序** |
| 结果 | 四态 + 一档沉默：可用（绿）/ 需登录（黄）/ 需选模型（琥珀）/ 未装（灰）/ **检测不到**（灰字 `UNKNOWN`，措辞是「检测不到」，**绝不写成「未登录」**） |
| 解法 | 需登录 ⇒ 卡上直接给命令原文 + 「复制命令」；需选模型 ⇒ 「打开应用」；未装 ⇒ 「安装说明」。词表唯一出口仍是 `DriverAuthStateMapping.remediationOf`，UI 不抄第二份 |
| 时间戳 | 有结果才显示「2 分钟前检测」；超过 24h 加一句「结果可能已过期」。**不做后台自动重检**。这要求结果**有地方存**：`DriverAuthStateEntryUi` 现在没有时间字段，要加 `checkedAt: Long`（0 = 不知道），并由**一份单实例台账**持有（见下） |
| 失败 | 超时 / 子进程异常 ⇒ 该卡「检测不到（超时）」+ 可再点；**不弹错误框**（一次检测失败不该打断配置） |
| 手机端 | 端口返回 `null`（没有执行面）⇒ **整段检测按钮不画**，卡片仍可看目录。这是不变量 3：能力缺失不画按钮，不画一颗点了没反应的 |
| 副作用 | 只读、幂等、不写任何档案；不因为「检测到未登录」就改写执行档或标记员工不可用 |

- 网格 `chunked(2)` + `Row(weight(1f))`（沿用现有实现），窄窗自动单列。
- **盘面全集与在位是两份数据，差集才是「未装」**：全集必须由**端口投影**给出
  （`driverRoster(): List<DriverRosterEntryUi>`，每项 `key / displayName / shortName / vendor`），
  在位仍是 `driverCatalog()`。**UI 不许直接 import `CliDriverSpecs`** —— `composeApp` 只依赖
  `:app` / `:core`，不依赖 `agent-contract`；而且「全集 / 厂商 / 显示名」是宿主事实，与在位集合
  同一条「读端口」纪律（`TeamExecutionPort` 的 KDoc 已经写死这条边界）。
  三份数据（全集 / 在位 / 登录态）各自不许猜，否则会出现「卡片画着、检测说没有」这种自相矛盾。
- **「全部检测」只检在位的**：未装的没有探针可跑，硬跑就是 7 家各等一次超时。按钮文案仍是
  「全部检测」，语义 = 全部**在位**的。
- **本页不做「重新扫描运行时」**。在位集合来自端口（`driverCatalog()` → 装配处的
  `availableDrivers()`），本页能做的只有**检测登录态**。装了新 CLI 之后要**重开执行配置**
  （或重启宿主）才会出现在盘面里 —— 这条如实说，不画一颗「重新扫描」的按钮：
  点了不重扫的按钮，比没有按钮更糟（不变量 3）。
- 「未装」卡上那颗「安装说明」**必须有落点**：打开该驱动的官方安装页（URL 由端口投影里的
  `installUrl` 给出；没有就不画这颗按钮，改画「复制安装命令」）—— 一颗点了没反应的按钮
  比没有按钮更糟。**`installUrl` 的落点已裁定（review 四轮）**：它不住 `CliDriverSpecs.Spec`
  —— 那是 `:agent-contract` 的纯契约，而安装地址是会随发行渠道变的宿主事实；放在
  `:orchestration` 装配处的 `driverKey → 安装指引` 独立表，经 `driverRoster()` 端口投影出来，
  与 `builtins` 同批改（新增一家必须同时补指引，否则那张卡只有检测没有安装）。缺项时
  按上句回落「复制安装命令」，**不许画死链或空跳转**。
- 卡内三行封顶：logo + 名字（+ 厂商名 `labelSmall`）/ 状态词 + 一句解法 / 动作行（1~2 颗
  `AppButtonSize.Small`）。
- 「未装」的卡**必须存在且可点** —— 否则「没装 codex」在界面上根本不存在，用户无从上手。

### 3.3 新建员工：一张单页表单，五个字段，一个下拉

桌面居中弹窗（`RelayDialog`，内容列按 `ContentWidths.Settings` 收列，高度 75% 上限）；手机
同一支组件，宽窗时同壳、窄窗时内容自然满宽 —— **不另做一整页**。

**先把词换掉。「底座」是内部叫法**（代码里是 `driver` / `driverKey`），界面上不该出现。
用户看到的是七个具体的产品名（Claude Code / Codex / DeepSeek Harness…），他脑子里想的是
「这个员工由哪个跑」。UI 词定为 **「运行时」**，第一次出现配一句白话：

> 装在这台电脑上、能替员工干活的程序。

- **为什么不用「智能体程序」**：五个字，太长 —— 下拉项要和状态词挤一行，窄列更放不下；
  而且它读起来像「一个智能体 app」，实际它**不是**智能体，是能跑智能体的环境。
- **为什么不用「引擎」**：这七家都能独立启动，不是被嵌进产品里的库。
- **为什么不用光秃秃的「程序」**：太泛，用户会问「什么程序」。
- **选「运行时」的代价要说清**：它与「正在运行」字面太近。所以**状态词里不许再出现
  「运行中」**，一律用「正在跑 / 在位 / 离线」（员工名录与 `driver_state_*` 一起遵守）。
  英文统一 `Runtime`（`Runtimes on this computer`）。

**形式上用下拉，不用卡片墙。** 三条理由：

1. 这是**单选**，七个选项里通常只有 1~3 个在位；卡片网格里大半格子是空的或不可选，
   视觉上像「有很多选择」，实际是「大部分你都没有」。
2. 表单只有四到五个字段（模型那格只在部分运行时出现），顶部一行方块会把主视觉从「填名字」抢到「选运行时」。
3. 下拉项里**信息一点没丢**：logo、名字、状态词（可用 / 未登录）都能放在同一行。
   「简单」不等于「少信息」。

**反例要一起定死：只有一家在位时不画下拉。** 点开只有一个选项的下拉是**假控件** ——
它让用户以为自己有得选。这一档画成只读一行（logo + 名字 + 状态），右侧一句「本机只有这一个」。

```
┌─ 新建员工 ────────────────────────────────────────┐
│ 给它选一个运行时，起个名字，它就能接单了。        │
│                                                   │
│ 运行时                                            │
│ ┌────────────────────────────────────────────┐    │
│ │ ▣ Claude Code                      可用  ▾ │    │  ← 收起态：当前值
│ └────────────────────────────────────────────┘    │
│ 名字                                              │
│ [ 小科                                       ]    │
│ 群里 @ 它                                         │
│ [ xiao-ke                                    ]    │
│ 名字是中文时派生不出，这里可以直接改。            │
│ 模型                               （仅部分运行时）│
│ [ 跟随默认 ▾ ]                                    │
│ 职责                                              │
│ [ 开发 ▾ ]                                        │
│ ⓘ 在哪个目录干活，由它服务的群决定。              │
│                                                   │
│                            [取消]  [创建员工]     │
└───────────────────────────────────────────────────┘

展开时（浮层，不撑高表单）：
        ┌────────────────────────────┐
        │ ▣ Claude Code        可用  │
        │ ▣ Codex              未登录│   ← 仍可选
        │ ▣ DeepSeek Harness   可用  │
        └────────────────────────────┘
        没有你要的？去执行配置看七家
```

| 元素 | 规格 |
|---|---|
| 控件 | 单选下拉（复用既有下拉件），**不是卡片网格**；收起态显示 logo(16) + 名字 + 状态词 |
| 候选 | `driverCatalog()` 里**在位**的；未装的不列（列了也选不了，等于把「未装」搬进新位置） |
| 只有一家在位 | **不画下拉**，画只读一行 + 「本机只有这一个」；理由见上（假控件） |
| 零个在位 | **表单不展开**：改画「先接一个运行时」+ 主行动跳 §3.2。建不了的时候表单不该长出来 |
| 未登录项 | **仍可选**：先建人、后登录是本方案的宗旨；选项右侧黄字「未登录」，选中后字段下方一行「它还没登录，建完去检测页登录」 |
| 兜底出路 | 展开态底部一行「没有你要的？去执行配置看七家」——用户想用但没装时，别让他以为不支持 |
| 名字 | `OutlinedTextField` 单行；不预填 `dsh-coder`（预填等于替用户回答） |
| 群里 `@` 它（token） | 单行 + 下方常驻一行「最终值」（`labelSmall`）；缺省 = `defaultEmployeeToken(名字)` 的产物，用户可改；改后必须已是归一形态，否则就地报错（不静默改写）。**这一格不画，用户就永远不知道自己该 `@` 什么** |
| 模型 | 下拉，**只在所选运行时的 `supportsPerTaskModel` 为真时出现**（`CliDriverSpecs.Spec` 已有此字段；`dsh` 与 `zcode` 两家为 false —— 别写成「那一家」）；选项 = 该运行时的可选模型 + 首项「跟随默认」。不支持的运行时**不画这一格**。⚠ 因此「同底座两人用不同模型区分」**对 dsh 不成立**（它不支持按任务指定模型）—— 那一档两人的区分只能是名字/职责/人设 |
| 职责 | 下拉，选项来自 `AgentDuties.ALL`。**缺省 `coder`，但不要写 `AgentDuties.normalize(null)`** —— 那个回落是 `assistant`（`DEFAULT_SINGLE`）。在 `AgentDuties` 里加一个 `DEFAULT_MINT = CODER` 常量让表单引用，不在表单里写裸 `"coder"`：那是第二份词表 |
| 目录 | **没有这个字段**。底部用 `ⓘ` + `labelSmall` 明说「在哪个目录干活由群决定」，把用户的疑问就地答掉，而不是留一个空格让他找 |
| 主按钮 | 实心，一颗；文字「创建员工」。**按钮恒可点**（置灰且不说原因是最差的一档），点了再逐字段校验：缺谁就标在谁下面。不要「可点 → 顶部弹一句保存失败」 |
| 错误落点 | 字段下方 `labelSmall` + `error`；跨字段错误（这个运行时刚被卸载）落到下拉行下方，**不弹 toast** |
| 提交中 | 主按钮转「创建中…」且禁用，其余控件一起禁用；成功后**关闭弹窗并停在员工档案段**（新行高亮一次，2 秒后恢复） |

> **运行时 ≠ 员工**：同一个运行时可以建多个员工（不同名字 / 职责，各是一个席位）。选它只说明
> 「这个员工由哪个运行时驱动」，**不改变它的安装 / 登录状态，也不占用它** —— 否则用户会以为
> 「选了 Claude Code，就把它占了」。
>
> **⚠ 洞 E：上面这句在现行写路径下做不到（`@HEAD`）。** `createEmployee` 的撞名检查用
> `sameAgent`（截到 `-` 前比较、同 head 全并）⇒ 同底座第二个员工必撞 `EMPLOYEE_EXISTS`，
> 改名字也绕不过（撞的是 `sameAgent` 抹平后的实例键前缀，不是名字）。按 §2② 定稿落地后：
> - 撞名检查改按 **`employeeId` 精确相等**（只拦「同一份档案重复建档」，那是调用方写错）；
> - **同底座第二人是合法操作**，唯一的正常冲突是 **token（`@` 名）重复** —— 它有自愈出路（改名），
>   所以文案写「这个 `@` 名已经被别的员工用了」，**不写「已经有一个同名员工」**
>   （后者会让用户去改名字然后再次失败）。
> - `sameAgent` 一字不动：它继续只做路由聚类。
>
> **职责选项现在直接显示枚举值**（`coder` / `reviewer` / `assistant`，`EmployeeEditDialog` 的 chip
> 就是这样）。这与 §3.0「界面不出现工程词」是冲突的，但本轮**不动**：词表只有一份，要本地化就
> 连同那个 chip 一个提交做。**不要在新建表单里单独翻译** —— 那是第二份词表，两处必然漂移。

> **三个实现坑，先说在前面**
>
> 1. **展开态在截帧里看不见**：`DropdownMenu` 走 `Popup`，Layoutlib 不组合子内容（这条结论
>    `DesktopChrome` 里已经记过）⇒ `designScreenDiff` 只能覆盖**收起态**。所以选项列表必须是
>    **纯函数**（`employeeDriverOptions(catalog, authStates)` → 列表 + 状态词），用单测钉住
>    「哪些进列表、各自什么状态、只有一家时不画下拉」；展开态靠真机点一次，不指望参考图。
> 2. **下拉件复用既有规格**：M3 `ExposedDropdownMenuBox` + 项目既有 `DropdownMenuItem`
>    字号档（`DesktopChrome` 已把 M3 默认 16sp 收到项目档），不新造一个表单控件。
> 3. **运行时名只有一份真相**：`CliDriverSpecs.Spec.displayName` 已经是「Codex / Claude Code /
>    Antigravity / DeepSeek Harness…」，而 `formatDriverName` 又手写了一张表（「Codex CLI」/
>    「Claude CLI」，还留着 `builtins` 里已不存在的 `gemini`）。两份迟早分叉，这次统一到
>    `Spec.displayName`，`formatDriverName` 收口成委托，并**去掉「CLI」后缀** —— 那同样是
>    工程词，用户要的是产品名。
>    窄列副行放不下「DeepSeek Harness」，所以在 `Spec` 上加一个**可选** `shortName`
>    （缺省取 `displayName` 首个词：Claude / Codex / Antigravity / DeepSeek…），
>    **仍然只有一处数据**，不另写分支表。

**失败文案要说下一步**，不是「保存失败」：

| 情形 | 文案（中） | 文案（英） |
|---|---|---|
| 运行时刚被卸载 | 这个运行时刚被移除了，换一个再试 | That runtime was just removed. Pick another one. |
| `@` 名（token）已被占用 | 这个 `@` 名已经被别的员工用了，换一个 | That @ name is taken. Pick another. |
| 写入失败 | 没写进去，请重试；原有档案未改动 | Couldn't save. Try again — nothing was changed. |

> **不要有「同名员工」这一档**。同底座建第二个人是**合法操作**（洞 E）：撞的从来不是名字，
> 是旧实现用 `sameAgent` 抹平了 head。改按 `employeeId` 精确之后，唯一会撞的是 token（`@` 名），
> 而它有一个能自愈的出路（换一个）。写成「已经有一个同名员工」，用户会反复改名然后反复失败。

### 3.4 新建 / 编辑团队：领队是已有的人，组员优先也是

```
┌─ 新建团队 ────────────────────────────────────┐
│ 领队                                          │
│ [ 小科 · Claude Code ▾ ]                      │  ← 候选 = 员工档案 ∪ 本机卡片
│ 组员                                          │
│ ┌ 老周 · 评审  ✕ ┐  [+ 添加组员]              │
│ ─────────────────────────────────────────     │
│ 派单时用群的项目目录去找执行配置。            │
│                          [取消]  [创建团队]   │
└───────────────────────────────────────────────┘
```

> **这里没有「进哪些群」**（上一版有，本轮删掉）。建队只回答「谁、叫什么、谁带队」；「去哪干活」
> 在群里回答（群信息 → 添加团队），「用哪家跑」在执行档（按目录）。把群塞进这张表单，等于让一个
> 还没用过的队先猜好未来会去哪些群 —— 猜错的代价是静默丢配置（见「目录不是团队的字段」）。

- **领队为空但员工非空** ⇒ 正常空下拉。**员工为空** ⇒ 表单照常展开，领队位置放一颗
  「先建一个员工」（就地跳 §3.3，回来后预选新员工）。**不再整张表单不展开。**
- **「＋添加组员」先给候选，不是直接塞一行空行**。现在 `TeamRosterDialog` 的三条来源
  （`newDraft` / `quickRoles.toDraft` / `teamRosterPreset`）**全是新建行**，手动建队同样
  「不能把已有员工放进队里」。改成：点开先列**已有员工**（点一个就加入名册，`isNew=false`，
  `agentId` = 它的 `employeeId`），最下面的「新建一个组员」才是现在那条路。这样 AI 建队与手动建队
  用**同一份池、同一套 `agentId` 语义**（§3.4.1），不会出现「助手会复用人、表单不会」。
- 底部那句「派单时用群的项目目录去找执行配置」是**解释**，不是校验：它回答「我这队在哪干活、
  用哪家跑」，并指出那两件事各自在哪设置（群信息 / 执行配置）。
- 保存后的横幅只有一句（`Saved: 队名（N 名成员）`）。**没有「跳过 N 个群」这一句了** ——
  建队不再产生群上的写入，也就没有可跳过的对象。
- 保存键文案 = 「创建团队 / 保存团队」，**不写「保存并广播」**（广播是内部行为，不是用户动作）。

#### 3.4.1 AI 建队：先用现成的人，缺了才建

**这一节的前提是一句判断：AI 建队的价值不是「替你编一支队」，是「替你从现有的人里挑一支队」。**
现在它做的是前者，而用户手上明明有人。

**现状三条缺陷（都是判据，不是印象）**

| 症状 | 判据 | 用户看到 |
|---|---|---|
| 组员全是新编制行 | `TeamScaffoldParser` 恒调 `newAgentId(name)` | 明明有两个员工，AI 又造出三个陌生名字 |
| 领队与需求无关（**仅在 LLM 不可用的回落模板里**） | `TeamScaffoldGenerator.generate()` **顶部**就求值 `leaderKeys.first()`（在调 LLM 之前），取值只给回落模板用 | LLM 成功时领队**本来就由 LLM 挑**，这一档没毛病；只有回落模板里说什么需求都是 `Set` 里碰巧排第一的那个 |
| LLM 看不见员工 | `TeamBuilderLlm.systemPrompt` 只注入 `leaderKeys`（一串键）与 `driverKeys` | 它没法「用那个人」，只能编名字 |

三条同源：**候选池没有进生成层**。于是「用我自己的人」这件事，手动建队只在**领队下拉**里兑现了
一半（组员同样只能新建，见 §3.4），AI 建队一次都没兑现。

> **洞 B 更正（现状判据别写错靶）**：`leaderKeys.first()` **只在回落模板路径被用到** —— 但它的
> **调用位置**在 `generate()` 顶部、在调 LLM 之前就无条件求值，所以「只删回落分支里那一行」这种
> 改法删不到东西，会留下一条死赋值。LLM 路径里 `TeamScaffoldParser` 已经对 LLM 给的 `leader` 做
> `canonicalKey(key, leaderKeys)` 校验（不在候选里 ⇒ 整份拒绝），领队从来不是「取第一个」。
> 所以「取 first 是需求对领队无影响的根因」只对回落模板成立，主路径的毛病是
> **LLM 根本没看见员工 roster**。改法：删掉顶部那条赋值 + 池进 system prompt + 领队由 LLM 给；
> 不要动 `canonicalKey` 那条校验 —— 它是本来就对的那一段。

**候选池：一个池，两个来源，按 `employeeId` 合并**

| 来源 | 有什么 | 缺什么 |
|---|---|---|
| 员工档案 `employeeProfiles`（本机） | 档案名、`@` token、职责、`driverKey`+`model` | 在线态（看卡片） |
| 本机卡片 `hubAgents`（`hostNodeId == self`） | `agentKey`、`online`、档案名 | 没登记的人没有职责 |

合并判据 = **`employeeId` 精确**（`sameEmployee`，与 `employeeProfileOf` 同一把尺子）；没有
`employeeId` 的老数据回落 `sameAgent` 兼容。**去重键不是名字**（名字会变），有身份锚时是
`employeeId`、回落时退到 `agentId`。**`driverKey` 直接读档案的 `driverKey` 字段**（§2② C 模型），
不反解、不新增存储；只有老档案（字段为空）才试一次 `resolveKey(agentId, driverCatalog())`。

> **洞 C（两类身份别混成一把尺子；P1a 之后按 `employeeId` 合并，故只需区分「谁说了算」）**：
> 池里两种来源的在线态语义不同，必须分开：
> - **有进程上报的身份**（`hubAgents` 卡片）：`online` 是事实；
> - **MINT 凭空造的身份**（§2②）：永不会有卡片上报，`online` 恒为 false。
>
> [事实·修正] 初版这里写「两者一起进池会**裂成两张候选卡**」——方向反了。`sameAgent` 同 head
> 全合并 ⇒ MINT 身份与**同底座**的真实卡片在池里不是裂开，是**撞键合并**：去重后剩一行，
> `online` 取哪个由合并顺序（`firstOrNull`）决定——两份真相抢一行，谁赢都不对。
>
> **这个缺陷由 P1a 消解**：合并键换成 `employeeId` 之后，MINT 的人与同底座真卡是两行、各带各的
> `online`（一个 false、一个可能是 true），不再抢。**UI 要把这两行画成两个人**：它们本来就是
> 两个员工（一个是造出来的档案，一个是正在跑的进程），差别只在「现在有没有在跑」。
>
> **口径（按 §2② 定稿的 C 模型）**：`canLead` = 池里**有 `driverKey` 的那一行**，
> **档案与卡片一视同仁**（`本机身份 ∧ driverKey != null`），**不要求有卡片、不要求 online、
> 不要求有 agentId、不要求有席位**。
>
> 三条理由，各自都是判据而不是偏好：
> 1. **领队是「声明 + 配置」**，不是「一个正在跑的进程」。C 模型下派单只需要 `driverKey` +
>    `model` + `wsId`（§2② 的三条代码证据），**没有任何一步需要预先存在的实例**。
> 2. **不以群为前提**：领队是「名册里的一行」，席位是群范围内的事实；团队本来就允许 0 个群（§3）。
> 3. **不这样写就是死循环**：`§3.3` 的员工表单没有群字段 ⇒ 新建的人没有席位 ⇒ 如果 `canLead`
>    还要求卡片，那就又劝他「先建一个员工」。用户会在两屏之间来回，且每一步都成功。
>
> `driverKey == null` 的候选仍不进池 —— 但那现在是**老数据的兼容分支**（档案里没有 `driverKey`
> 字段的旧记录），新档案必带。回落规则：老档案用 `resolveKey(agentId, catalog)` 试着反解一次，
> 解不出就不进池（并在员工详情里提示「给它补一个运行时」），**绝不猜**。

**没登记的本机 agent 也能复用**：`token` 取卡片 `displayName`（那本来就是席位 token），`duty` 缺省
按 `AgentDuties.DEFAULT_SINGLE`。预览里它同样标「已有员工」—— 用户认的是「我那台机器上在跑的
那个」，不是「有没有走过登记」。少这一档，「有 agent 没建档」的机器在 AI 建队里等于零员工。

**生成契约：池要进 prompt，领队要由 LLM 挑**

```
TeamScaffoldBridge.generate(need, roster: TeamScaffoldRoster, defaults)
  TeamScaffoldRoster(pool: List<Candidate>)            // 单表，别存第二份 leaders
  Candidate(agentKey, label, token, duty, driverKey, online, canLead)
  leaders = pool.filter { it.canLead }                 // 派生，不是字段
```

- `pool` = 档案 ∪ 本机卡片；`canLead` = `driverKey != null`
  （**不要求有卡片、不要求 online、不要求 agentId** —— 离线与实例都是派单期的判据，不是建队期的；
  理由与死循环见上「洞 C 口径」）。
  只存一份表：`leaders` 另存一份字段，就等于把「谁能当领队」写两处，迟早一处漏改。
- **候选的 `agentKey` 用 `employeeId`**（不是 `agentId`、也不是卡片的实例键）。C 模型下运行时由
  档案的 `driverKey` 直接给，不再需要从任何键反解；`agentId` 只用于「这个人现在在跑哪个实例」
  的展示与精确投递，**复用行不依赖它**。这条同时消掉了上一版那个坑：老档案存短 id（`dsh`）时
  传短 id 会让 `dsh-029bbbf3` 命中不了、复用行当场变成「运行时不确定」—— 现在不存在这一步。
- **`driverKey == null` 的候选不进池**：复用它的唯一收益是「这个人 + 他的运行时」，运行时定不下来
  就只剩一个会在派单期变成 `DRIVER_MISSING` 的名册行。池里少一个人，比池里多一个派不出去的人好。
  新档案必带 `driverKey`，所以这条只对老数据生效（回落规则见上「洞 C 口径」）。
- LLM 的 system prompt 从「一串键」变成「一人一行：token · 职责 · 运行时 · 在线」。
  这是唯一能让它按需求挑人的改法；给 `dsh-029bbbf3` 这种键，它只能当占位符。
- **回落模板不许拿 `leaderKeys.first()` 当领队**。它让「需求文本对领队完全没有影响」。
  改法：**先删掉 `generate()` 顶部那条无条件赋值**，回落模板改为**从池里按 duty 挑**
  （与组员同一份池、同一条优先级），挑不出就返回 null（洞 B 的契约：零员工没有领队）。
  主路径（`TeamScaffoldParser`）已有的 `canonicalKey` 校验保留不动 —— 它本来就是「由池裁决」。

**成员的两种形状（对 LLM 的输出契约）**

| 形状 | JSON 行 | 命中后 |
|---|---|---|
| 复用 | `{"use":"laozhou","kind":"reviewer","prompt":"…"}` | 池里按 token → agentKey → label 精确匹配（大小写不敏感） |
| 新建 | `{"name":"tester","role":"测试","driver":"codex","kind":"reviewer","prompt":"…"}` | 走现有路径 |

**`use` 未命中，不新造。** 这是本节最容易写错的一条：LLM 说「用 laozhou」而池里没有 laozhou，
说明它在编人；若这时按 `name` 新造一个 laozhou，用户会得到一个与真老周毫无关系的同名陌生人，
而 `@` 会打给错的人。所以：`use` 未命中 ⇒ 丢该行并计入「N 行没找到对应员工」的提示；
只有它同时给了 `name/role/driver` 才按新建处理。

**优先级顺序（不能换）**

1. 恰 1 worker（编译期硬约束）；
2. reviewer 与 worker **异厂商**；
3. 复用匹配：职责优先，其次运行时在位；
4. 仍不足才新建；
5. 新建行的驱动必须来自 `driverCatalog()`。

第 2 条在第 3 条之上的理由：池里三个人全是 Claude，凑不出异厂商审核 —— 这时「都用现成人」
换来的是派不出去的方案。**宁可新建一行**。

**复用的落法（不新增协议字段）**

| 行 | `agentId` | `name` | `driverKey` | `TeamMemberDraft.isNew` |
|---|---|---|---|---|
| 复用 | `employeeId`（如 `emp-m3k9-4f2a`） | 档案 `token` | **档案的 `driverKey`**（直接读，不反解） | `false`（**不许重算**） |
| 新建 | `m-<slug>-<rand>` | LLM 给的 slug | LLM/兜底（须在位） | `true` |

> **两行的 `agentId` 都是「合成 id」，没有一个是进程实例键** —— 这不是巧合，而是 C 模型的直接
> 结果：名册行回答「团队里这一棒是谁」，它既不是一个正在跑的进程，也不该依赖某个实例当前在不在。
> 复用行用 `employeeId` 的好处是**同一份真相**：改名、换运行时、注销都只改档案，名册行不用重写
> （快照重建时按 `employeeId` 重新投影即可）。

六条依据，缺一条这个落法就不成立：

- **`agentId` 放 `employeeId` 是合法的**：执行档里本来就有两种形态（`initialExecutionProfileUi`
  的单兵分支用 `seat.agentId`，团队分支用编制 id），`validateExecutionProfileUi` 只要求
  **本档内唯一**；`TeamRosterValidation` 只校验 slug 形状与名册内唯一，`emp-m3k9-4f2a` 与
  `dsh-029bbbf3` 几条都过。选 `employeeId` 而不是实例键，是因为前者**不会因为进程重启而失效**。
- **不存「这一行是复用的」标记**：`employeeProfiles.byEmployeeId(member.agentId)` 命中即员工、
  未命中即编制行。存一个 `reused=true` 会在员工改名/注销之后说谎。
- **不是「复制快照」**：若把员工运行时抄进一个 `m-xxx` 行，①员工换运行时团队不跟（两处真相）
  ②`groupsReferencingEmployee` 永远数不到他（界面写「不在任何群」）③`@` 到的是编制行 token
  而不是员工的 token。
- **预览要画来源**：`TeamScaffoldSpec.Member` 加 `reused: Boolean = false`（只活在 spec 里，
  进不了协议帧也进不了档案 —— 落盘时它的等价物就是 `TeamMemberDraft.isNew = false`）。
  不许让 UI 拿 `agentId` 是否以 `m-` 开头来猜：那是一条靠命名约定成立的判据，
  第一次有人给编制行换前缀就会画错。
- **名册行的 `name` 必须是 token，不能是档案里的中文名**：群里的 `@` 按席位名匹配，写中文名
  等于让这一行派不出去。档案名只是**给人看的副标签**（预览里灰字），不进名册。
  这也是为什么员工建档时要把 token 显示给用户看（§3.3）—— 它在两个地方都是承重字段。
- **撞名只管席位，不改名册**：复用 token 在本群撞上别人的 token 时，走既有
  `TeamRosterValidation.resolveNames` 就地别名（席位叫 `laozhou-2`）；**名册行的 `name` 仍是
  档案 token**。两层不是一个东西 —— 把别名写回名册，下一次重建快照就会把别名固化成"真名"。

**预览：来源要看得见，名字不能就地改**

```
┌─ AI 建队 ────────────────────────────────────────────┐
│ 领队                                                 │
│ 结算退款小组 · 小科 · Claude Code                    │
│ 组员          复用 1 个已有员工 · 新建 1 个          │
│ ──────────────────────────────────────────────────── │
│ 老周 · 审查 · Codex                       [已有员工] │
│ ▸ 人设提示词                                         │
│ ──────────────────────────────────────────────────── │
│ dev-tester · 测试 · Codex                     [新建] │
│ ▾ 人设提示词                                         │
│    真跑命令，以证据说话，逐条给结论。                │
│ ──────────────────────────────────────────────────── │
│                       [重新生成]  [创建团队]         │
└──────────────────────────────────────────────────────┘
```

| 槽位 | 规格 |
|---|---|
| 来源药丸 | 复用 = 「已有员工」（`accents.surface3` 底）；新建 = 「新建」（`primary` 12% 底）。**不写「复用」** —— 用户说的是「我的人」 |
| 汇总 | 组员段头右侧一行 `复用 N 个已有员工 · 新建 M 个`，数字由 spec 现算，不存 |
| 复用行在界面上的称呼 | **名册行（席位名）写 token**（`@` 匹配的就是它，写中文名会让 `@` 打空），旁边灰字补一句档案名（「小科」）。两者都要画：只画 token，用户认不出这是谁；只画名字，他 `@` 不到 |
| 复用行的人设提示词 | 可编辑。它属于**这一支队的这一行**（团队范围的人设），存 `TeamMemberInfo.prompt`，**不回写员工档案**；派单期建执行档时作为 `customPrompt` 初值浇进去 |
| 运行时 | 用 `formatDriverName`（收口后的显示名），**不印原始键**。现在预览里印的是 `claude` / `codex` |
| 运行时已卸载 | 这一行换兜底驱动，并在下一行写「老周的运行时已不在，这一棒改用 Codex」（`warn`） |
| 员工当前离线 | 不拦，副行写「当前离线」（团队执行只看运行时装没装，不看进程在不在跑） |
| 复用 0 而池非空 | 不弹警告、不拦保存，**把数字摆出来**即可（`复用 0 · 新建 3` 已经说明问题），用户点「重新生成」 |

**回落模板也要复用池**

LLM 不可用时 `TeamScaffoldFallback` 固定造 `coder + tester + reviewer` 三行。这条降级路径
**同样要先进池**：按 duty 匹配（worker 槽优先 `coder`/`ops`，tester 槽优先 `tester`，
reviewer 槽优先 `reviewer`），异厂商校验不过就换人，池里凑不出才新建。否则「LLM 挂了」就等于
「复用能力也挂了」—— 同一个缺陷在降级路径复发。

**空态改一条（洞 B 的关键口径：零员工时 AI 建队不可用，这是对的）**

`roster.pool` 为空（更准确：`pool.none { it.canLead }`）时，`TeamBuilderLlm.draft` 与
`TeamScaffoldGenerator.generate` 都在 `leaderKeys.isEmpty()` 处直接返回 null —— 生成层此刻
**根本产出不了方案**。这不是 bug，是契约的必然：`leaders = pool.filter{canLead}`，领队必须是
「本机有 `driverKey` 的人」，一个人都没有时造不出领队，而领队是唯一执行入口。**所以零员工时的正确
行为不是「全新建照常可用」，而是先建人。**

本方案原 §4 第 13 条写「全新建照常可用」，与本节自相矛盾，已删——保留它会让人以为零员工能
直接建出一支队并派单成功，而生成层在第一步就返回 null。要放开这一档，得先定义「虚拟领队」
的身份与执行归属（谁 spawn、落哪个目录），那是另一个方案，不在本轮。

UI 上：没有领队候选 ⇒ 不再只给「去看看节点」。主按钮「**新建员工**」（就地跳 §3.3，回来后预选），
次按钮「看看节点」。`TeamBuilderDialog` 现在恒走 `onFindNodes` —— 那是一颗把用户送到
改不了判据的页的按钮（§3.10 第 10 条），而这一轮的判据恰恰是「本机没有员工」。

**确认落盘**

与手动建队**同一条** `saveTeamProfile`（助手不发明第二条写路径）：复用行 `isNew = false`；
**不带群** —— 与手动建队一样，入驻与执行档留到派单期（见「目录不是团队的字段」）。
「没目录的群被静默丢掉」这个缺陷随之消失，因为这条路径不再碰群。

> **人设提示词因此需要一个落点**：执行档现在不在建队时写，预览里改过的 prompt 不能无处可去。
> 它属于**团队名册的这一行**（`TeamMemberInfo.prompt`，团队范围），派单期建执行档时作为
> `customPrompt` 初值。这也正好符合本方案的取舍：同一员工在两支队的人设本来就该不同
> （一支写代码、一支做审查），所以它既不属于员工档案，也不属于「目录」那一份配置。

### 3.5 派单失败（blocked 卡）：分类码 + 一颗主行动

群内卡片，全群可见；1:1 会话里是同构的单行提示。**不再是一句「未配置」。**

```
┌──────────────────────────────────────────────────┐
│ ⚠ 没派出去 · NO_DIRECTORY                        │  ← 分类码 chip（warn）
│ 这个群还没绑项目目录，不知道它该在哪个仓里干活。 │  ← 一句人话
│ [ 选项目目录 ]        其余原因 ▾                 │  ← 主行动 + 折叠
└──────────────────────────────────────────────────┘
```

| 分类码 | chip 色 | 一句人话（中） | 主行动 | 次行动 |
|---|---|---|---|---|
| `NO_DRIVER` | warn | 这个员工用哪个运行时跑，定不下来 | 去群编制指派 | 看员工档案 |
| `NO_DIRECTORY` | warn | 这个群还没绑项目目录 | 选项目目录 | — |
| `DIR_NOT_ALLOWED` | error | 这台电脑没被授权访问这个目录 | 去授权 | 看设备 |
| `NOT_AUTHORIZED` | error | 你没有调用它的权限 | 申请授权 | — |
| `TEAM_NOT_IN_GROUP` | warn | 这支队伍还没加进这个群 | 把队加进这个群 | 看团队档案 |
| `TARGET_MISSING` | warn | 这个名字已经不在了（可能刚改名或注销） | 刷新名录 | — |
| `DRIVER_MISSING` | error | 这个运行时不在这台电脑上 | 去安装 | 换一个运行时 |

**这七条码不是互斥的，必须定顺序。** 现在 `TeamExecutionResolver.Target.NotConfigured(seat, reason)`
里 `reason` 是一句**自由文本**，于是「群没目录」和「驱动派生不出」可以同时成立、却只能说一句话。
改成结构化：`NotConfigured(seat, code: DispatchBlockedCode, reason: String)`（`reason` 只进折叠区
和日志，**不上卡面**），UI 按 `code` 选文案与主行动。判定顺序 = 首个命中即用：

| 序 | 码 | 为什么排在这 |
|---|---|---|
| 1 | `TARGET_MISSING` | 先确认「有没有这个人」—— 给一个不存在的席位开药方是纯噪声。**判据要排除下一档**：token 命中本机团队档案但该群没席位时，报 `TEAM_NOT_IN_GROUP` 而不是这条 |
| 2 | `TEAM_NOT_IN_GROUP` | 「人还在、只是没进这个群」—— 主行动是加进来（一次性），与「刷新名录」是两件事。排在权限前：还没进门时谈权限没有意义 |
| 3 | `NOT_AUTHORIZED` | 再确认「你能不能调用它」—— 没权限时后面所有配置建议都是白搭 |
| 4 | `NO_DIRECTORY` | 再看「在哪干活」—— 目录是执行档主键的一半，缺它时 `profileOf` 根本调不了 |
| 5 | `DIR_NOT_ALLOWED` | 有目录但不被授权，与上一条是两个动作（选目录 / 去授权） |
| 6 | `NO_DRIVER` | 目录齐了才谈「用谁跑」；判据 = 该目录下没有执行档 **∧** 员工档案 `driverKey` 为空（老数据再试一次 `resolveKey`，解不出才算） |
| 7 | `DRIVER_MISSING` | 最后才是「配的那个键不在位」—— 这是唯一一条「装上就能好」的 |

顺序的总原则：**先人、再权、后配置**。越靠前的问题越不由当前这一屏解决，把它放在前面才不会
让用户按卡上的建议改了三处、最后还是被第一条挡住。

规则：**一行 chip、一句话、一颗主行动**，三者缺一就算没做完；折叠区里才放原始错误与日志。
chip 上的码是给排查用的，人话是给用户的 —— 两个都要，不给码等于断掉支持链路。

### 3.7 交互与状态（所有屏共用）

| 项 | 规格 |
|---|---|

> **零迁移的两个前提（必须先看，否则「零迁移」是假的）**
>
> `EmployeeProfile` 加字段确实是零迁移 —— 但**只在这两条同时成立时**：
>
> 1. **新字段必须带默认值**（`driverKey: String = ""`，不能是裸 `String`）。
>    kotlinx.serialization 里**没有默认值的字段是必需的**：老 `settings.json` 里没有这个键 ⇒
>    反序列化抛 `MissingFieldException` ⇒ `SettingsStore.load()` 的 `runCatching{}.getOrNull()`
>    把它吞成 `null` ⇒ `RelayController` 落到 `RelaySettings.firstRun()` ⇒ **重新分配 `nodeId`**。
>    症状不是崩，是**这台设备的身份被静默换成新的**（对端全掉、消息历史与它断链）。
>    既有先例：`AutomationTaskSettingsTest.testLegacySettingsCompatDefaults` 断言的就是
>    「旧 JSON 缺字段 ⇒ 取新默认」，而它成立的唯一原因是那些字段**都有默认值**。
>    → **守卫测试**：一条 `{"nodeId":"old-node","nick":"old-nick"}` 的老 JSON 解码后，
>    `nodeId` 仍是 `old-node`、`driverKey == ""`。
> 2. **「双向兼容」只到解码为止，不等于写回兼容**。旧构建读新 JSON 没问题
>    （`ignoreUnknownKeys = true`）；但它下一次 `save()` 会按旧类重新序列化，
>    **把 `driverKey`/`model` 静默抹掉**。Debug 与 Release 同机共存（AGENTS §2.9）时这是可达的：
>    在 Release 版建好的员工，被 Debug 旧包打开一次就丢了运行时配置。
>    → 所以 `driverKey` 为空时要**如实回落**（试 `resolveKey`，失败报 `NO_DRIVER`），
>    而不是当成「这个员工没有运行时」永久坏掉 —— 用户回新版本重新选一次即可恢复。

> 接检测时**两处注释会变成假的**，必须同一提交内改：`AgentExecutionConfigDialog` 里
> 「这座页不预检、不代替 / 没有登录状态、没有补凭证命令」那段，以及
> `TeamExecutionPort.driverAuthStates()` 的 KDoc。留一句「别接回配置页」在那儿，
> 下一个人就会以为接按钮是违规的。

### 3.10 视觉红线（出现即打回）

1. 恒亮的绿点 —— 状态点必须能落在至少两档。
2. 未装的运行时从界面消失 —— 七家全画，否则「装不了」这件事无从表达。
3. 空态把「本机没有」说成「对方没有」。
4. 远端卡上出现编辑/注销/换运行时 —— 档案与执行档只在本机。
5. 远端卡上写运行时名、模型或登录态（「对方在用 Codex」「对方没登录」）—— 那是本机事实嫁接到别人身上；远端副行只写目录数。
6. 厂商 logo 被改色、拉伸、加投影，或被当成应用主视觉 —— 单色 tint、24dp、原比例、只用于识别对应产品；缺资产回落首字色块。
7. 承诺「一键登录」—— 登录是交互式终端行为，只给命令 + 复制。
8. 窄列塞第三行文字 —— 268dp 里两行是上限。
9. 一颗按钮两个标签（「保存并广播」这类把内部行为写进用户动作的）。
10. 只给「去看看节点」的空态 —— 必须有一个能改变当前判据的主行动。
11. AI 建队把已有员工**复制**成新编制行（名字像、`agentId` 却是 `m-…`）—— 那会让「我的人」
    在团队里变成陌生人，且换运行时不会跟随。复用行就带 `employeeId`（§3.4.1）。
12. 复用行就地改名 —— 名字属于员工档案；团队里改一次，档案里还是旧 token，`@` 立刻分叉。
13. **在员工行或团队行上画「它绑了哪些群」「几个群」** —— 群归属是引用关系（席位住 `GroupMeta`），
    画在这里等于把群的视角搬进名录：一队进 3 个群就变成 3 行，用户以为编了 3 支队。群的事去群页看。
14. **建队表单里出现「进哪些群」** —— 那是把「入驻动作」画成「团队属性」，且会逼用户替还没用过的队
    预测未来（猜错的代价是静默丢配置）。入驻在群里做（添加团队），执行档在派单期按目录建。

## 5. 三条不变量

1. **不猜底座**。任何一条路径上，拿不到明确底座就拒绝并说明，绝不回落默认驱动。
   **改法（C 模型）**：底座是员工档案的**显式字段** `driverKey`，建档时选择并当场校验
   「必须在该机 `driverCatalog()` 里」；派单期**直接读这个字段**，不再从任何键反解。
   优先级：执行档（按目录、按队伍，更具体）> 员工档案 > **拒绝**。
   `AgentProfiles.resolveKey` 的「按前缀反解」从此只服务**老数据兼容**（档案还没有 `driverKey`
   字段的旧记录），且解不出照样拒绝。原句写成「底座只从实例键前缀派生」，那是把
   一个已有的实例键当成了真理来源 —— 而它恰恰是「猜」的来源。
2. **不静默**。拒绝、跳过、降级都要有一个可见落点（blocked 卡 / 会话内提示 / 空态）。
   「什么都没发生」是缺陷，不是状态。
3. **能力缺失不画按钮**。手机端没有写通路（`onSaveTeam == null`、`port == null`）就整段不画，
   而不是画一颗点了没反应的按钮。

**顺序理由**：
- P1a 必须最先，且**身份与配置先于一切 UI** —— 撞名还按前缀全并时「同底座建第二个人」做不到
  （`SameDriverSecondEmployeeTest` 必红），后面「运行时 ≠ 员工」的产品承诺全是空话。
  原方案把这一整块与复用、盘面、检测塞在一个 P1 里，任何一环卡住都会拖住全局，且 E2E 红了
  无法定位是哪一站。拆开后 P1a 红就是身份/配置问题，P1b 红就是入口问题。
- **P1a 是「简化项」，不是「扩张项」**。它的净增只有 **2 个字段**（`driverKey` / `model`）+ **1 个
  三行函数**（`sameEmployee`），其余五步全是「字段到位后必须跟着改」的**推论**，且方向都是
  **删与收口**：删撞名检查里的 `sameAgent`、删两处身份兜底、把 `resolveKey` 的「按前缀反解」
  从唯一来源降为老数据兼容。
  为什么必须先把字段加上：没有它，「用哪家跑」就只能从实例键反解，而同底座两人的实例键在语义上
  不可区分 —— 那正是洞 E 的来源，也是本方案前四版反复打补丁的原因。
  一句话判据：**加完这两个字段，旧模型里那些「猜」就没有存在理由了。**
- **P1a 不含协议帧**（§2② 已裁定走本机投影链）：因此它的验收全是域层测试，不依赖 UI、不依赖
  真机，能当天跑；也正因如此，它绿了才有资格谈「入口」。
- **风险集中在一处，且已有既定做法**：`EmployeeProfile` 是
  `settings.json` 的一部分，加字段的唯一真风险是老库解码失败导致 `nodeId` 重置（§3.9「零迁移的
  两个前提」）。做法照既有先例（默认值 + 老 JSON 解码测试），不需要迁移脚本、不动数据库。
  除此之外 P1a 没有跨端风险：不改帧、不改 `.sq`、不改端口。
- **P1b 的第一条判据是「建完人立刻能复用」**：这是上一版漏掉的死循环（新人没有席位 ⇒ 不进名录 ⇒
  `canLead=false` ⇒ 空态又劝他建人）。`canLead` 不再要求卡片（§3.4.1）之后，这条才成立 ——
  它是 P1b 是否真的解开了「先有人」的判据，别用「预览里出现一行」代替。
- P1b 不先做，P2 的分类码有一半永远触发不到（`NO_DRIVER` 得先有「人可以被建出来」这回事，
  `DRIVER_MISSING` 得先有盘面检测）。

## 7. 验收

两条 E2E（P1a 建人闭环、P1b 复用与盘面）。**P1a 的验收全是域层/投影测试**（不依赖 UI、不依赖
真机）；**P1b 的验收面是桌面 debug 包 + 一台真机 Android**。**手机端不跑建人链路** —— 它没有本机
agent（§2.0），对它唯一成立的验收是「读不到就不画」（§4 第 11 条）；把手机写成与桌面同等要求，
等于造一条永远过不了的验收。P1a 未绿之前不进 P1b 的验收。

**P1a（域层，全部可在 `:app` 测试里跑完；不依赖 UI、不依赖真机、不依赖任何进程在跑）**

- **A1** 干净数据目录 + 台账为空：`MINT` 建档成功，档案带 **`employeeId` / `driverKey` / `token`**
  三个非空值，`agentId` **为空**（MINT 不绑实例，还没派过单）、`model` 为空（跟随默认）；
  `REGISTER_EXISTING` 档则反之：`agentId` 非空（登记的实例），`driverKey` 由该实例反解或用户选；
- **A2** **在已经跑过一个 agent 的机器上**再建第二个（`MINT` 不受台账非空影响 —— 最容易漏的一档）；
- **A3** **同底座建两个人成功**：两人 `employeeId` 不同、`driverKey` 相同，**允许 `model` 不同**；
  撞名只在 `employeeId` 或 token 重复时发生，**不在 `driverKey` 相同的时候发生**；
- **A4** 同底座两人**同进一个群**：各占一条席位、各带自己的 `employeeId`（这条就是上一版标
  `@Ignore` 的那个用例）。**修法不是「给两人不同的实例键」**（那是假身份，§2② 已否决），而是
  席位 `employeeId` 精确归属 —— 两条测试把这一点钉死：
  (a) 两人 `agentId` **不同**时各自成席；(b) 两人 `agentId` **相同**（同一实例接入）时，
  仍按 `employeeId` 各归各档、不猜；
- **A5** 派单只用档案的 `driverKey` + `model`：执行档存在时以其为准；两处都没有 ⇒ 拒绝，
  **不回落默认驱动**（不变量 1）；
- **A6** **进程上报不同实例键后，档案 `employeeId` / `driverKey` 一个字都不变**（`agentId` 可被
  回填为观测值，但它是路由线索，改了也不影响任何身份判定）；
- **A7** 老数据兼容：档案无 `driverKey` 时用 `resolveKey(agentId)` 反解一次，解得出照常、
  解不出则不进候选池并提示「给它补一个运行时」；
- **A8** `sameAgent` **源码指纹未变**（守卫测试钉住：它永久只做路由聚类）。

**P1b（桌面 debug 包为主，末两条上真机）**

1. 清空数据目录启动 ⇒ 智能体页空态 ⇒ 主行动是「新建员工」；
2. 打开执行配置 ⇒ **七张卡都在**（含未装的，带 vendor logo）⇒ 点「全部检测」⇒ 未登录那家
   在**派单之前**就显示「需要登录」+ 命令原文，「复制命令」可用；把某家 CLI 从 PATH 移走后
   **重启应用**再查 ⇒ 变「未安装」，**不写成「需登录」**（本页不做运行时重扫，口径见 §3.2）；
3. 建员工（下拉选一个在位运行时 + 名字 + `@` 名 + 职责，不填目录）⇒ 档案行出现，`@` 名就是
   表单里显示的那个（中文名时是回落的 `运行时-职责`，用户可以改）；
4. 建团队（领队 = 刚建的人，**不选群**）⇒ 团队行出现；**该群此刻还没有执行档**；
   在这个群 `@队名` ⇒ 第一次被 `TEAM_NOT_IN_GROUP` 拦住 ⇒ 点「把队加进这个群」⇒ 再派一次成功，
   执行档按该群的项目目录建出来（初值：第一名 worker、其余 reviewer）；
   换一个**没设项目目录**的群重复一次 ⇒ 被 `NO_DIRECTORY` 拦住，主行动是「选项目目录」；
4b. **本机已有 2 个员工时，用 AI 建队**：输入一句需求 ⇒ 预览里至少有 1 行标「已有员工」，

   运行时等于该员工的 `driverKey`（不是从键反解出来的）；这一行**没有名字输入框**；重建一支队 ⇒ 那行仍能被复用

   换了一个在位驱动；
5. **真机**：群内 `@员工 一句话` ⇒ 会话卡出现，状态从 queued → working → done；
6. **真机**：断开目录授权再派一次 ⇒ blocked 卡带 `DIR_NOT_ALLOWED` + 「去授权」，点进去落位正确。

## 8. 取舍与风险

- **团队与群解耦（本轮取舍，不是遗漏）**：建队不选群；入驻（`attachTeamToGroup`）与执行档留到
  派单期。换来的是**一整类静默缺陷消失** —— 「群没设目录」不再在 `mapNotNull` 里被丢掉，
  `TeamProfile` 不需要群字段，员工/团队页也不必画群。代价三条，都要认：
  ①`saveTeamProfile` 的契约从「至少一个群」改成「可 0 个」（`:app` 接口 + 两端壳 + 既有测试）；
  ②`@队名` 的解析面要多一档：先查本机团队档案，再看该群有没有它的席位；
  ③第一次在一个新群里 `@` 它会被 `TEAM_NOT_IN_GROUP` 拦一次（一次性，点一下就过）。
  旧口径的代价是常年的「我明明配过」—— 那比一次拦截贵得多。
- **不做常驻 daemon**。multica 有一套常驻 agent 进程（心跳注册、任务 claim），本项目是
  「按任务 spawn 一次 CLI」—— 这里的「运行时」指的是**被 spawn 的程序**，不是一个长活进程，
  两者别混。常驻能换来「登录态一次到位、启动更快」，代价是进程生命周期、僵尸进程、
  升级一致性三座山。现在不划算；等派单频率上来再单独评估。
- **复制厂商 logo（单色、品牌色一档）**。理由不是好看，是识别：七家里六家是单个英文词，
  首字块（C / C / A / O / C / Z）在扫视时几乎不可分。合规做法写进 §3.2：一 vendor 一份单色 path、
  固定 24dp、原比例、不叠效果、不改形，只用于标识对应产品，不当应用主视觉；缺失回落首字块，
  所以「多养一份商标资产」不会变成上线阻塞。**成本是新增一家 CLI 要同时补一个资产** ——
  这条加进「新增驱动必须改的七处」清单（原六处 + 本次资产）。
- **不自动预检，但提供按需检测**。要分开三件事：
  自动预检（启动时探 7 家）**不做** —— 冷启动背 10s+，多数人当天用不上；
  按需检测（用户点「全部检测 / 重查」）**做** —— 这是「不等派单才发现」的唯一兑现方式，
  底层 `driverAuthStates()` 早就装配好了，缺的只是入口；
  常驻登录表**不做** —— 一张永远挂着的「未判定 × 7」既吵又没动作，是被摒弃的形态。
  检测必须并发（agy 首次 ≈6s），否则点一次要等一轮接力。
- **取舍：员工级配置（`driverKey` + `model`）成为必需，不再是「以后再说」**。上一版把它列为
  P3、理由是「引入它会与执行档打架」。C 模型证明这个理由站不住：**它是「不猜底座」的唯一落地
  方式** —— 没有它就只能从实例键反解，而同底座两人的实例键在语义上不可区分（洞 E 的来源）。
  优先级已定死：**执行档（按目录、按队伍，更具体）> 员工档案（默认值）> 拒绝**。
  这不是加一张表，是给 `EmployeeProfile` 加两个字段；打架的问题用「更具体者优先」这一条解决，
  不需要第二个存储。
- **取舍：`agentId` 降级为空串表示「尚无」的路由线索**（用 `String = ""` 而不是 nullable：与 `byAgentId` 的 `isNotEmpty` 判据一致，也免掉一档 null 传播）。代价是「这个人现在跑在哪个实例上」不再能从档案直接
  读出（要等它第一次派单/上报后回填）。收益是**身份不再依赖任何进程的生命周期** —— 这是洞 A 的
  根治。界面上如果要显示「正在跑」，读的是实时会话/工作区台账（那本来就是事实来源），不是档案。
- **风险：一支队跨多个目录会各存一份执行档**。用户在群 A 里换了底座，群 B（另一个目录）
  不会跟着变。这是对的（工作副本不同），但界面上必须写清楚「这一份属于这个目录」，
  否则「我明明改过」会变成常年投诉。
- **AI 建队的复用是「引用」不是「快照」**。组员 `agentId` 直接用 `employeeId`，于是「这个人是谁」
  只有一份答案：改名跟着档案走（团队名册在下一次编辑团队时重建快照）、换运行时跟着档案 `driverKey` 走、
  `groupsReferencingEmployee` 能数到它。代价是**名册行与员工档案耦合**：员工注销后名册里会留下
  一行指向不存在的档案（§4 第 16 条如实标出，不静默改 token）。若改成「复制一份独立的编制行」，
  代价换成了三处静默分叉，更贵。
- **不做「员工级 prompt」**。人设属于**团队名册的一行**（`TeamMemberInfo.prompt`），派单期建
  执行档时作为 `customPrompt` 初值浇进去，**不回写员工档案** —— 同一员工在两支队伍的人设本来
  就该不同（一支要它写代码、一支要它做审查）；而把它挂在员工上，就会造出「一处人设、两队抢用」。
  要不要「每个员工一份默认人设」是另一个问题，得先解决它与团队人设的优先级，不在本轮。
- **风险：身份锚选错（洞 A，review 全程追问后定稿）**。把「类型 + 实例」拼进 `dsh-029bbbf3`
  当身份，hex 归进程、可变——进程重启就换，拿它当身份锚必然漂移。终案三层正交：**身份只认
  `employeeId`**（本机持久化、跨重启稳定），hex 退回路由线索，driverKey 退回配置。任何
  「用 hex 精确配对」「用底座当身份」的改法都是把可变的东西当身份，不要做。
- **风险：同底座建第二个人被路由尺堵死（洞 E，当前最硬）**。撞名与配对用 `sameAgent`（同 head
  全并）做身份判定 ⇒ 同底座第二员工撞 `EMPLOYEE_EXISTS`、两张卡并一份档。修法已在 §2② 定稿为
  **撞名 / 配对改按 `employeeId` 精确**（「一个底座一个员工」的产品收口路已否决——它砍掉「同一
  运行时多席位人设不同」的核心卖点；「拿 hex 精确配对」也已否决——hex 可变）。不许「先建一个
  试试」或「只改判据」蒙过去。
- **风险：宿主级重启后工单不可恢复（review 全程追问新增，P3）**。`activeTickets` 纯内存、无
  init 回填，`TeamExecutionStore` 只存执行档配置不存工单 ⇒ 宿主重启后「同一员工接着干」断。
  进程级崩溃由自愈循环覆盖（工单在内存、卡靠 `employeeId` 归位），这条只在宿主机级重启触发。
  列为 P3 独立缺口（工单持久化回填），不阻塞 P1a 建人闭环。
- **风险：AI 建队零员工档被误读成可用（洞 B）**。生成层在 leaderKeys 为空时返回 null 是契约必然，
  不是待修缺陷；但若 UI 文案仍暗示「全新建照常可用」，用户会卡在第一步。§3.4.1 / §4 第 13 条
  已统一口径为「先建人」，不要为「显得功能全」再放开虚拟领队。
- **~~风险：品牌色基线重记与门禁纪律冲突~~（洞 D；二轮已核销，不是风险）**。上一版担心路径 (a)
  要刷 `designTokenUsageBaseline`、违反棘轮。实测不成立：`design_contract.iter_source_files` 默认
  跳过 `ui/theme/`，`Color(0x…)` 欠债不数主题内的定义；采用面只增不减；`spec ↔ code` 漂移的正规
  修法是 `:designSpecProject` 重投影。所以它既不需要评审人批准，也不构成阻塞。**唯一保留的纪律**：
  品牌色只写 `ui/theme/DriverBrand.kt`，**不进 feature 层** —— 那才是会被记成欠债的写法。
- **风险：名字与 `@` 用的 `token` 被当成一个东西（二轮新增，产品面）**。`@` 打的是 token，而
  token 由 `slug(名字)` 派生；中文名的 slug 为空 ⇒ token 回落成 `运行时-职责`（`claude-coder`）。
  不把最终 token 显示给用户，就会出现「我起了名字、却 `@` 不到」；而名册行又必须以 token 为准
  （席位名就是匹配面），于是「档案名」只能当副标签。落点：§3.3 表单加 token 一格，§3.4.1 预览
  同时画 token 与档案名。
- **风险：把「运行时实例键」当成身份（本方案自己踩过两次）**。第一次是把 `dsh-029bbbf3` 整串当
  身份（洞 A）；第二次是「给 MINT 铸一个假 `<driverKey>-<8hex>`」（§2② 已否决）。两次同源：
  想让一个**可变的路由线索**承担**身份**。守住的判据只有一条：**身份 = `employeeId`，配置 =
  `driverKey` + `model`，实例键只做路由**；任何新代码想「从实例键反推是谁」或「造一个实例键」，
  都在这条判据外。守卫测试：A6（上报不同实例键后 `employeeId`/`driverKey` 一字不变）。
