# luciola 0.5.0 引擎在 Android 真机上的验证（换 uniffi 0.29.4 后）

日期：2026-10-27。goal 第 (2) 步的前置检查：0.5.0 换了 uniffi 版本、重编了 `.so`，
JVM 测试覆盖不到"APK 里那份库能不能加载、握手是否正常"，所以必须在真机上验一遍。

## 1. 引擎身份（先证"跑的确实是新引擎"）

```
APK 内 lib/arm64-v8a/libluciola_uniffi.so   097b6032030ef82453d9a024bbafd53114d75fab503f3e0f019111e9d89925e7
AAR 0.5.0 内 jni/arm64-v8a/libluciola_uniffi.so  同上（逐字节一致）
```

0.4.6 那份是 `201eab4d…`，与本次不同 —— 符合"换了 uniffi 版本就该换库"的预期。

## 2. 运行时（Pixel 6 / Android 15 ↔ macOS）

| 项 | 读数 |
|---|---|
| 启动 | 无 FATAL、无 UnsatisfiedLinkError、无 luciola 报错 |
| 发现 | 宿主 `/v1/peers` 看到 `Pixel 6 / 192.168.2.22 online=true` |
| 手机监听 | UDP 17871/17878；TCP 17880/17888 |
| 宿主监听 | TCP *:17878 / *:17880 / *:17888 |
| **1MB 传输** | `[chunk] chunksSent=16 waitMs=165`（16 = 1MB/64KiB，零重传放大） |
| **sha256** | 手机 `8a60d7c2…75ed6` = 宿主 `8a60d7c2…75ed6` |
| 路径 | `[luciola] accept-in … push=true` ⇒ 走的是加密信道，不是 legacy |

## 3. 一个容易误判的观察（记下来省下次）

手机上 **17878 只有 UDP，没有 TCP**；宿主上 17878 是 TCP 监听。
第一次看到"手机少了 17878 TCP"以为是监听退化了，实际是**角色不对称**：
宿主做服务端监听 TCP 17878，手机作为客户端拨出去。
**判据是功能而不是端口清单** —— 1MB 传输 sha256 一致就说明这条链路是通的。

## 4. 结论

0.5.0（uniffi 0.29.4 + gobley 生成的 KMP 绑定）在 Android 真机上功能正常，
之前"只验了 JVM 绿"的空缺已补上。可以进入 iOS 的实现阶段。
