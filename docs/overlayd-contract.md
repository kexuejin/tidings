# overlayd 契约（嵌入式 overlay 的插件控制协议）

> 状态：**契约草案 v1，待评审**。这是**跨产品契约**：任何产品接这个插件只依赖本文件，不依赖实现语言。
> 形态与取舍见 [overlay-transport-design.md](overlay-transport-design.md) §3.5；产品侧怎么用见 [overlay-product-plan.md](overlay-product-plan.md) §8。

## 0. 一页纸

**一句话**：主程序通过**本机回环 TCP + 一次性 token** 驱动一个 overlay 守护进程；数据面是**另一个回环端口**，上层照旧跑 TLS + 双向 pin。

| | |
|---|---|
| **是什么** | 一个可执行/可加载的能力组件（`overlayd`），对外只暴露两个回环端口：一个控制、N 个数据 |
| **不是什么** | 不是 VPN 客户端（不建 TUN、不接管系统流量）、不是代理服务器（不转发他人流量）、不是代码下载器 |
| **不做的** | 不做 UDP 代理、不做多租户、不做内容审计、不记录消息内容 |
| **判据** | 契约级测试全绿（§11）；主程序不链接 Go 也能用（进程形态） |

## 1. 职责边界

| | 主程序（产品） | overlayd（插件） |
|---|---|---|
| 决定什么时候启动 | ✅ | ❌ |
| 持有用户账号与授权 | ✅（浏览器授权在宿主侧发起） | ❌（只把 authUrl 交出来） |
| 决定连哪台设备、连什么端口 | ✅ | ❌（只执行 `proxy`） |
| 传输加密与对端身份 | ✅（TLS + 双向 pin，见技术设计 §5.6） | ❌（WireGuard 只管到节点，不管到应用） |
| 状态与错误如实上报 | — | ✅ |
| 空闲回收 | 通知 `shutdown` | ✅ 自己也会超时退出（双保险） |

> **一句话记住**：overlayd 只回答「路通不通」，**永远不回答「对面是不是那台电脑」**。

## 2. 传输与鉴权

1. **只绑 `127.0.0.1`**，端口由内核分配；启动后向 stdout 打一行：
   `READY {"port":54321,"proto":1,"pid":12345}`
2. **token 由主程序生成**（32 字节随机，base64url，不带填充），通过**子进程 stdin 的第一行**交给它；
   不放进 argv、不放进环境变量（两者都可能被同机其他进程读到）；
3. 连接建立后 **2 秒内**必须发 `hello` 并带对 token，否则守护进程直接断开；
4. 同一时刻最多 **4 条**控制连接，超出即拒；
5. 进程形态下，**数据面端口也是回环**，且不做额外鉴权 —— 鉴权在上层 TLS + pin（技术设计 §5.6）。

## 3. 帧格式

- **NDJSON**：一行一个 JSON 对象，UTF-8，**单行 ≤ 8 KiB**（控制面只传状态与命令，数据不走这里）；
- 每个请求必须带 `id`（客户端自增整数），响应**必须原样回带** `id`；
- **未知字段必须忽略**（向前兼容）；**未知命令必须回 `E_UNSUPPORTED`**（不许静默丢弃）；
- 事件（推送）没有 `id`，用 `ev` 字段区分；
- **响应与事件共用同一条流**：客户端读到的对象若是 `ev`（无 `id`），必须**跳过并继续读**，
  直到拿到 `id` 与请求匹配的那条。**不许假设「下一条就是响应」** —— 验收时这条会被事件打断（实测踩过）。

## 4. 命令

### 4.1 hello（必须第一条）

```json
{"id":1,"cmd":"hello","token":"<base64url>","proto":1,"client":"relay/0.1.0"}
{"id":1,"ok":true,"proto":1,"version":"overlayd/0.1.0","features":["tcp_proxy"]}
```

`proto` 不匹配 ⇒ `E_PROTO` 并断开（**fail-closed**，不做兼容猜测）。

### 4.2 status（拉状态）

```json
{"id":2,"cmd":"status"}
{"id":2,"ok":true,"state":"up","selfIps":["100.107.134.95"],"dns":"tail30b85b.ts.net","peers":[{"host":"MacBook","online":true,"ips":["100.64.0.5"],"os":"macOS"}],"lastError":null}
```

### 4.3 proxy（开一条数据通道）

```json
{"id":3,"cmd":"proxy","target":"100.64.0.5:17879"}
{"id":3,"ok":true,"port":54322}
```

- 返回的 `port` 只绑 `127.0.0.1`；主程序连它，字节被送进 overlay 的 `target`；
- **一个 `proxy` 一个监听器**，可接受多条连接，每条各自 `Dial` 到 target；
- target 未就绪（state ≠ up）⇒ `E_NOT_READY`（**不许挂起等**）；
- 主程序必须能接受「监听器一直空着」（overlay 可能长时间没人连）。

### 4.4 close（关掉一条数据通道）

```json
{"id":4,"cmd":"close","port":54322}
{"id":4,"ok":true}
```

### 4.5 shutdown（主程序要求退出）

```json
{"id":5,"cmd":"shutdown"}
{"id":5,"ok":true}
```

回应后**立刻**释放所有端口并退出（退出码 0）。

### 4.6 ping（保活，可选）

```json
{"id":6,"cmd":"ping"}
{"id":6,"ok":true,"t":1761100000}
```

## 5. 状态模型

| state | 含义 | 主程序该做什么 |
|---|---|---|
| `stopped` | 没启动 | 需要时启动 |
| `starting` | 进程/库已起，还没连上控制面 | 等事件，不要重试启动 |
| `needs_auth` | 需要人授权 | 把 `authUrl` 交给用户（**这是人的动作**） |
| `up` | 已入网 | 可以 `proxy` |
| `backoff` | 掉线重试中 | 展示「正在重试」，**同时**提示其他路径仍可用 |
| `error` | 起不来/被拒 | 读 `lastError`，按 §6 给出路 |

**事件推送**（状态变化时主动发，避免主程序轮询）：

```json
{"ev":"state","state":"needs_auth","authUrl":"https://login.tailscale.com/a/xxxx"}
{"ev":"state","state":"up","selfIps":["100.107.134.95"],"peers":[]}
```

**两条硬纪律**：

1. **`status` 与事件必须一致** —— 同一时刻只允许一个真相；出现矛盾读数按缺陷处理；
2. **`lastError` 在进入 `up` 时必须清空** —— 否则会出现「已连接 + 上次超时」的自相矛盾（`AGENTS.md` §2.5）。

## 6. 错误码

| code | 含义 | 可重试 | 文案 key（产品侧） |
|---|---|---|---|
| `E_BAD_TOKEN` | token 缺失/错误 | ❌ | `overlay_error_auth_local` |
| `E_PROTO` | 协议版本不匹配 | ❌ | `overlay_error_version` |
| `E_UNSUPPORTED` | 未知命令/能力 | ❌ | `overlay_error_version` |
| `E_NOT_READY` | 尚未入网 | ✅ 稍后 | `overlay_error_not_ready` |
| `E_DIAL_FAILED` | 到目标拨不通 | ✅ | `overlay_error_peer_unreachable` |
| `E_BUSY` | 并发超限 | ✅ | `overlay_error_busy` |
| `E_CONTROL_DOWN` | 控制面不可达 | ✅ 退避 | `overlay_error_control_unreachable` |
| `E_INTERNAL` | 其他 | ⚠️ | `overlay_error_internal` |

> 错误码是**契约**：产品侧只按 code 分支，**不许解析 message**。message 只给人看。

## 7. 生命周期

```
主程序需要 → spawn/load → READY → hello → status/事件
                                      │
                    空闲（无 proxy 且无连接）超时 120s → 自行退出
                                      │
                          主程序要退出 → shutdown → 端口释放
```

- **谁拉起**：主程序（进程形态）或加载（库形态）；overlayd **从不自启动**；
- **崩溃**：主程序看到进程退出即重建（退避 1s/2s/4s，上限 60s，±20% 抖动）；
- **双保险**：即使主程序忘了 `shutdown`，overlayd 也会空闲超时退出（**不许常驻**）。

## 8. 安全

1. 只绑 `127.0.0.1`（守护测试：从同网段另一台机器连必须失败）；
2. **token 永不入日志**；日志里出现一律按缺陷处理；
3. 数据面**不记录内容**，只允许记录「字节数/耗时」这类计量；
4. 目标地址属元数据：可以记 debug 日志，但**默认关闭**；
5. 不接受任何「从网络下载并执行」的指令 —— 契约里**没有**这种命令。

## 9. 版本与演进

- `proto` 是**整数**，只在**语义**变化时 +1；加可选字段**不** bump；
- 新增能力用 `features` 数组协商（未知项忽略）；
- 删除/改变已有字段含义 = 破坏性变更 ⇒ bump `proto` + 两端同时升级；
- **老主程序 + 新 overlayd**：新字段被忽略，必须仍能工作；**反之亦然**（各自测一遍）。

## 10. 与产品五状态的映射

| 产品状态（§4.2） | overlayd state | 说明 |
|---|---|---|
| 未加入 | `stopped` | 不启动 |
| 加入中 | `starting` / `needs_auth` | 后者要把 authUrl 给用户 |
| 已加入 | `up` | 显示设备数 |
| 需重新确认 | `needs_auth`（且此前是 up） | 保留配对，只重做授权 |
| 不可用 | `backoff` / `error` | 同时提示局域网与公网直连仍可用 |

## 11. 契约级验收（每条都能判红）

1. **错 token** ⇒ `E_BAD_TOKEN`，且不泄露任何状态字段；
2. **proto 不匹配** ⇒ `E_PROTO` 并断开（不许「尽力兼容」）；
3. **未 up 时 proxy** ⇒ `E_NOT_READY`（断言**不挂起**，2 秒内返回）；
4. **只绑回环**：从同网段另一机连控制端口必须失败；
5. **空闲退出**：无 proxy、无连接 120s 后进程退出，端口消失；
6. **status 与事件一致**：连续 50 次状态变化里，两者不许出现矛盾；
7. **lastError 清空**：从 `backoff` 恢复到 `up` 后，`lastError` 必须为 null；
8. **未知命令** ⇒ `E_UNSUPPORTED`（不许静默丢弃、不许断开连接）；
9. **未知字段** ⇒ 忽略且正常响应（向前兼容）；
10. **token 不入日志**：注入一个特征串当 token，断言日志里搜不到。

> 反向验证纪律：每条都要能「把旧行为放回去就变红」。

**已验证（本机 darwin arm64，原型实现）**：17 条断言全过，覆盖上表 1/2/3/4/5/8/9/10 与完整生命周期
（hello → status → proxy → close → shutdown → 端口释放 → 空闲自行退出）。

**未验证**：`proxy` 里真正跑字节（端到端数据面）—— 需要第二个节点，当前 tailnet 里只有一台设备（`peers=0`）。

**验收过程中抓到的契约缺口（已补进 §3）**：

> 响应与事件**共用一条流**。第一版客户端假设「下一条就是响应」，结果 `shutdown` 的响应被一条
> 状态事件顶掉，解出来的 `id` 是 0、`code` 是空 —— **看起来像服务端没回，其实是客户端读错了**。
> 现在契约写明：读到 `ev` 必须跳过继续读，直到 `id` 匹配。

> 这条是典型的「静默错位」：两端都以为成功了，只有字段对不上。写客户端的人如果不看契约，一定会踩。

## 12. 目录骨架

```
kapp-overlay/
├── core/                     契约客户端（commonMain）
│   ├── Contract.kt           命令/事件/错误码的常量与 DTO（与本文逐字对应）
│   ├── ControlClient.kt      NDJSON 收发 + id 配对 + 超时
│   ├── OverlayRuntime.kt     expect 接口：start/stop/proxy/close/state
│   └── OverlayState.kt       六状态 + 错误码 → 文案 key 映射
├── runtime-process/          进程形态（jvm + android）
│   ├── ProcessLauncher.kt    拉起、stdin 交 token、读 READY、守护与退避
│   └── AndroidLauncher.kt    nativeLibraryDir + LD_LIBRARY_PATH（技术设计 §3.5）
├── runtime-inprocess/        库形态（android + ios + jvm）
│   └── InProcessRuntime.kt   System.load / cinterop，起同一套回环控制端口
└── native/                   Go 构建产物（一份代码四个构建）
```

**依赖方向**：产品 → `core` → 一个 runtime 实现。**`core` 不许依赖任何 runtime**，否则换形态要改业务代码。

## 13. 未决

1. **要不要 Unix domain socket**（macOS/Linux 可用文件权限代替 token）？现在统一走回环 TCP，简单但多一个 token 环节；
2. **要不要支持 UDP 代理**？现在只 TCP；本仓的发现走 UDP，但跨网发现不依赖它（技术设计 §3.4）；
3. **空闲超时默认 120s** 是否合适（对「换网后立刻回来」的场景会不会太短）？
4. **多实例**：同一台机器上两个产品各起一个 overlayd，要不要共享节点状态？现在设计为**各自独立**（简单、隔离），代价是各自登录一次。

## 14. 能力路线：哪些能进契约，哪些永远不进

契约只有四个原语：**地址**（selfIps）、**成员**（peers）、**代理**（proxy/close）、**状态**（state/事件）。
其余能力都是这四个的组合，按代价分三档。

### 14.1 不改契约就能做的（只加命令，`proto` 不变）

| 能力 | 怎么落 | 代价 |
|---|---|---|
| **按名字访问** | `proxy` 的 `target` 接受主机名（MagicDNS），而不是只接 IP | 低 |
| **连接质量** | `status` 加 `direct: true/false`（直连还是经中继）+ `rttMs` | 低，但要真值 |
| **流量计量** | `status` 加 `bytesIn/bytesOut`，让中继成本可见 | 低 |
| **多目标代理池** | 已有 `proxy` 多次调用即可，无需新命令 | 零 |
| **保活/唤醒** | 主程序按需 `proxy` + `close`，空闲即回收 | 零 |

### 14.2 要 `proto` bump 的（新命令/新语义）

| 能力 | 说明 | 代价 |
|---|---|---|
| **反向监听** | `listen(port)`：让对端能主动连进来（现在只能主程序往外拨）。手机被桌面连、桌面推送到手机都靠它 | 中 |
| **UDP 代理** | `proxyUDP(target)`：单播 UDP；**广播/组播做不到**（overlay 不转发，见技术设计 §3.4） | 中 |
| **服务发布** | 把本机某个端口发布成对端可访问的名字（tsnet 的 `Listen`/Service 已具备，主要是契约与策略） | 中 |
| **子网路由** | 访问整个 `192.168.x/24`；必须**显式批准**（等于把家里内网开放给这张网） | 高 |
| **出口节点** | 全部流量走某台设备；**这已经接近 VPN**，与本产品立场冲突 | 高 |
| **多网络** | 一个进程同时加入多张网 | 高（状态目录、身份、UI 全要改） |

### 14.3 永远不进契约的

| 不做 | 原因 |
|---|---|
| 接管系统流量（TUN / VpnService） | 那就不是插件了，是 VPN 客户端；本产品的立身之本正是「不接管」 |
| 转发他人流量（公网代理） | 合规与滥用风险，且我们不愿为他人的流量付带宽 |
| 广播/组播转发 | overlay 是点对点链路，平台不支持（技术设计 §3.4） |
| 下载并执行代码 | 移动端被平台禁止；桌面也不给这个口子 |
| 内容审计/解密 | 内容在上层 TLS 里，插件看不到也不该看到 |

### 14.4 判断标准（加能力前先问）

1. **它需要看到内容吗**？需要 ⇒ 不该进插件（插件只搬字节）；
2. **它会让插件变成「网络接管」吗**？会 ⇒ 不做（那是另一个产品）；
3. **它能在契约里用四个原语表达吗**？能 ⇒ 只加命令，不 bump `proto`；
4. **它有可判红的验收吗**？没有 ⇒ 先别加（加进去就再也测不掉）。
