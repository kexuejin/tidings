## 0. 结论速览（TL;DR）

1. **要解决的问题只有一个**：手机与本机不在同一张网、对端又没有**可入站的公网 IPv6** 时，
   今天的两条路（LAN 直连 / `public_v6` 直连）同时失效。产品上表现为"路由器没放行就是连不上"，
   而用户不知道什么叫"放行 IPv6 入站"。
2. **方案**：把 overlay（WireGuard 用户态网络栈）**嵌进 App 进程**，而不是让用户装 Tailscale/ZeroTier。
   用户态 ⇒ **不建 TUN 设备、不申请 `VpnService`、不弹 VPN 授权、状态栏没有 VPN 图标**，
   也**不与其他 VPN 抢那唯一一个 VPN 槽位**。对外只暴露 `127.0.0.1:<kernel 分配端口>`，
   业务代码连 localhost 即可。它给的是**地址平面**（每台设备一个稳定虚拟 IP），
   **不是广播域**（overlay 不转发广播/组播）——这条差别决定发现机制要不要改，见 §3.4。
3. **它不替代任何现有承载，只新增一档**。候选顺序：
   `lan_v4 → lan_v6 → public_v6 → 嵌入式 overlay → 中继`。局域网的明文长连接**逐字节不变**。
4. **必须付出的一笔代价：一个控制面（rendezvous）和一个可达的中继**。
   overlay 能省掉"你家公网 IP、路由器入站放行、CGNAT 限制"，**省不掉**"有一个服务器帮你交换地址"。
   这一条必须写进产品话术，不能让"无需服务器"这句话把用户骗进来。
5. **安全边界不降级**：overlay 端点**永远按公网对待**（强制 TLS + 双向 pin）。
   回环地址今天被判成局域网（`IpAddressUtils.isPrivateOrLocal` 显式含 `127/8`），
   直接接进拨号裁决会**在公网上开出一条明文长连接** —— 这是本方案最危险的一个陷阱（§5）。
6. **分期**：O0 裁决 → O1 桌面端嵌入（最小改动、零包体代价给手机端）→ O2 Android 嵌入 → O3 路由接入候选
   → O4 iOS。**每一期单独可回滚**，任何一期失败都不影响现有 LAN/IPv6 路径。

## 1. 背景：今天到底卡在哪

### 1.1 现状（事实，来自代码与既有文档）

| 承载 | 触发条件 | 加密 | 谁可达 |
|---|---|---|---|
| UDP 单播/广播 | 局域网发现、`presence`/`entry` | 明文（LAN） | 同网段 |
| TCP `17879` 明文长连接（K1） | 对端在局域网（`isLanAddress`） | 明文 | 同网段 |
| TCP 明文短连接 | 超长文本回退、文件 `file-ctl`/`pull` | 局域网明文 / 公网 TLS | 见下 |
| `public_v6` 直连（K2） | 对端有 GUA 且**路由器放行入站** | TLS + 双向 SPKI pin，fail-closed | 有公网 IPv6 且愿意开入站的家庭 |

最后一行是本文件的出发点：**它不是"配置麻烦"，而是一个多数家庭不满足的前提**
（CGNAT、IPv4-only、运营商封 443 之外的入站、公司/酒店网络）。

### 1.2 用户视角的三句话

1. "在外面连不上家里的电脑"——因为家里没有可入站的公网地址；
2. "那我在手机上开个 VPN？"——系统级 VPN 会接管**所有** App，用户不一定愿意；
3. "我不想装两个 App"——这是嵌入式 overlay 存在的理由。

## 2. 方案总览

### 2.1 三个必要组成部分（缺一不成立）

```
        ┌──────────── 手机 App（用户态 overlay 栈）────────────┐
        │  WireGuard 密钥 · netstack · 127.0.0.1:<port> 代理     │
        └──────┬──────────────────────────────┬───────────────┘
               │ ①控制面：交换"我在哪"            │ ②数据面：直连 / 中继
               ▼                              ▼
        控制面（自建或托管）              打洞 UDP ──失败──▶ 中继（只转发密文）
               ▲                              ▲
        ┌──────┴──────────────────────────────┴───────────────┐
        │  局域网电脑：桌面端 App（同进程 agentNode）或常开小机      │
        └─────────────────────────────────────────────────────┘
```

| 组成 | 作用 | 能不能省 |
|---|---|---|
| **控制面** | 登记每台设备的公钥与观察到的出口地址，把对端当前地址分发给双方；
跨网还要发 NAT 打洞的协调信息 | **不能** |
| **数据面直连** | 双方同时发 UDP 穿 NAT（多数家用 NAT 可成） | 成功即省掉中继 |
| **数据面中继** | 打洞失败时的兜底（对称 NAT、企业防火墙）。中继只转发
**已加密**的包，无对端私钥，解不开 | 只在保证"永不失败"时才可省 |

### 2.2 嵌入式 overlay 到底嵌的是什么

不是"一个 VPN 客户端"，而是**一个用户态网络栈 + 一个本地回环代理**：

- `tailscale.com/tsnet`：嵌入式 Tailscale 节点。`Server.Dial` / `Server.Listen` 返回标准
  `net.Conn` / `net.Listener`，**只走 tailnet**，不碰系统路由表；
- 它可以直接以 C 库形态编进别的程序（`libtailscale`：`go build -buildmode=c-archive|c-shared`）；
- 移动端已有可对照的成熟形态：Go `.so` + FFI（Android）/ 静态库 + 桥接（iOS），
  对外只暴露 `startProxy(远端虚拟IP, 端口) → 本地端口`，明确不需要 VPN entitlement。

**换用 ZeroTier 也是同一种形态**（`libzt` 提供 `zts_bsd_socket / zts_bsd_connect` 这类用户态 socket，
并可产出 Android AAR）。**差别在运维与许可，不在架构**。

### 2.3 为什么不是"让用户装个 Tailscale"

| 做法 | 手机上有 VPN 图标 | 影响其他 App | 能否只让本 App 走 |
|---|---|---|---|
| 装 Tailscale App（默认模式） | 有 | 会（全局接管或排除法） | 否 |
| 装 Tailscale App（Android app-based split tunneling） | **有** | 可配排除 | **需要 MDM 才能用“只包含”模式** |
| 嵌入式用户态栈（本方案） | **没有** | **完全不影响** | 天然只影响本 App |
| iOS per-app VPN | — | 有 | **需要 MDM + 受管设备**，公众 App 用不了 |

另外 Android **同时只允许一个 `VpnService`**：让用户装 Tailscale，就等于抢走他公司 VPN 的槽位。

### 2.4 同类形态与替代底座（选型前先看许可）

| 项目 | 嵌入形态 | 许可 | 结论 |
|---|---|---|---|
| tailscale `tsnet` / `libtailscale` | 用户态 netstack，可编成 C 库 | 代码 BSD-3；**托管服务受其服务条款约束** | 生态最成熟；分发见 §4.4 |
| ZeroTier `libzt` | 用户态 socket（`zts_bsd_*`），可出 Android AAR | **BSL 1.1：禁止「链入非 OSI 许可的商业产品」** | **排除**（除非买商业授权） |
| OpenZiti `ziti-sdk-c` | 应用内嵌 + socket 接口 | **Apache-2.0**，可完全自托管 | 许可最干净，形态更重 |
| NetBird `client/embed` | 用户态（`wireguard/tun/netstack`） | 客户端 BSD-3；**management/signal/relay 是 AGPL-3.0** | 自建控制面要评估 AGPL 义务 |
| Nebula | 有 iOS/Android 源码，lighthouse 架构 | 开源 | 移动端需自己移植 |
| EasyTier | Rust，支持 Android | LGPL-3.0 | 动态链接可行，需评估 |

同形态的**商业先例**：Larktun 公开写明"把网络放进 App、不要系统 VPN 权限"，并支持
Tailscale 账号 / 自建控制面 / 自家账号三种登录。但它的控制面与 iOS 端闭源，
Android 端自称已开源、**公开渠道未找到仓库**。所以它是**可行性证据**，不是**实现参考**。

> 纪律：**"别人也在做"不是"条款允许"的证据**。先例只用来证明技术可通。

## 3. 接缝：接到本仓的哪里

### 3.1 现有接缝（已经在，不必新造）

`core/.../transport/Link.kt` 已经把"怎么拿到一条字节流"抽干净了：

- `LinkTransport.connect(host, port, expectedPin, timeoutMs)` / `accept(...)`；
- `LinkConnection` 只承诺"写一帧、读一帧"，分帧（`4 字节大端长度 + JSON`，`TcpFrame`）在它下面；
- `isSecure` / `isPlaintext` / `peerPin` / `canServeTls` / `localPin` 是安全判定的入参；
- 文件是**另一条连接**（`file-ctl` / `pull` / 裸流 / 断点续传），不在长连接上做多路复用。

**结论：overlay 只是"又一个连接来源"，不是又一个协议。** 信封、ACK、去重、队列、分页、
断点续传、屏幕流控**全部不动**——这与 `cross-network-file-screen-design.md` 选项 B 的结论一致。

### 3.2 需要新增的三样东西

| 新增 | 形态 | 说明 |
|---|---|---|
| `OverlayTransport` | 一个新的 `LinkTransport` 实现（`isSecure = true`） | `connect()` 先确保 overlay 节点已启动，再连 `127.0.0.1:<本地代理端口>`，**再在它上面照常做 TLS + 双向 pin** |
| `OverlayRuntime` | 平台接缝（`expect/actual`，实现落在 `jvmSharedMain` 与 `iosMain`） | `start() / stop() / localEndpoint(remoteVirtualIp, port) / state` |
| `ovl1` 能力位 | `MessageTypes.CAP_*` 家族 | 本机**能经 overlay 被拨**（由主机声明）；不声明 = 老端，**一个 overlay 连接都不发** |

> `ovl1` 必须同时进 `caps()`。本仓已经栽过两次"只加进清单、没进 `caps()`"（`lnk1` / `att1`），
> 加能力位时把这条当检查项。

### 3.3 为什么不像 K1 那样"明文"复用

`LinkTransport` 里已经写死了一条边界：**明文只允许局域网**（`plaintextLinkForbidden` 走
`isLanAddress`）。overlay 的端点在**本机回环**上，但它的**另一端在公网**——
这不是"局域网"，而是"一条经过公网中继/打洞、内容已在 WireGuard 里加密、但我们无法验证对端身份"的通道。

所以 overlay 连接**必须**再叠一层 TLS + 双向 pin：
**WireGuard 保护"中间人看不到"，TLS + pin 保护"对面那个人确实是它"。**
两者不是重复——前者防旁观，后者防冒充（控制面被掉包时尤其重要）。

### 3.4 overlay 给的是「地址平面」，不是「广播域」

这是"它到底算不算局域网"的正确答案，也是本方案最容易被误解的一处。

| 维度 | overlay 成立吗 | 后果 |
|---|---|---|
| **寻址**：每台设备一个稳定的虚拟 IP（`100.64.0.0/10`） | ✅ | 对端地址不再依赖 NAT、IPv6 前缀、DDNS ——"局域网的感觉"正来自这里 |
| **成员可见性**：这张网里有谁 | ✅（问控制面） | `tsnet.Server.Up()` / `LocalClient().Status()` 返回成员表与虚拟 IP |
| **广播域**：`255.255.255.255` 能不能到对端 | ❌ | 现有 UDP 广播发现**不会**跨 overlay |

overlay 的链路是**点对点**的，官方对广播/组播的答复是"**不创建一个广播域**"。
所以本仓 `Discovery` 的广播路径（`broadcastHost = 255.255.255.255`）在 overlay 上**不会响** ——
这是性质，不是 bug。

替代只有两条：

1. **把"发现"换成"问控制面"**：`Status()` 给出成员与虚拟 IP，等价于"我在这张网里看到了谁"；
2. **配对码/手动添加带上虚拟 IP**（候选池新增一种类型，见 §6.4）。

**判据**：实现里若出现"监听广播等 overlay 对端"，那就是设计错了 —— 它永远不会响。

### 3.5 交付形态：一个契约，两种实现（进程 / 库）

原型已经证明同一份 Go 代码可以有两种落地形态，而**产品侧只认一套契约**：

| | 桌面（macOS / Windows / Linux） | Android | iOS |
|---|---|---|---|
| 形态 | **独立守护进程**（overlayd） | **也可以是独立进程**（打成 lib*.so 放 jniLibs）或进程内库 | **只能进程内库**（沙箱无子进程） |
| 为什么 | 可独立升级、崩溃隔离 | W^X 禁的是**可写目录**，native lib 目录是**只读且可执行**的（见下） | iOS 没有子进程 |
| 升级 | 换二进制，不重发 App | 随 App 发版（进程形态可独立替换文件） | 随 App 发版 |

**Android 上的进程形态怎么做（实测路径，不是传闻）**：

1. 把 overlayd 命名为 `liboverlayd.so` 放进 `jniLibs/<abi>/`（**必须 `lib` 前缀 + `.so` 后缀**，否则打包工具直接忽略）；
2. `android:extractNativeLibs="true"`（bundle 默认是 false）—— 恰好与包体决策里的 `useLegacyPackaging = true` 是同一件事，不用额外改；
3. 运行时从 `applicationInfo.nativeLibraryDir` 取绝对路径执行，**不要硬编码**；
4. 传 `LD_LIBRARY_PATH=<nativeLibraryDir>`（`exec` 不像 `System.loadLibrary` 会帮你解析）；
5. 二进制不能有未满足的动态依赖 —— Go 用 `CGO_ENABLED=0` 静态链接天然满足。

> **但这是「利用打包机制」，不是平台承诺的能力**：Google 随时可能收紧。
> 所以**进程内库形态必须同时保留**（同一份代码的 `c-shared` 构建），一旦被封就切过去 —— 契约不变。

**「插件包」的边界（三个层级，别混）**：

| 层级 | 形态 | 主程序怎么加载 | 能否独立升级 |
|---|---|---|---|
| **L1 编译期模块** | AAR / xcframework / klib | Gradle 依赖 + `System.load` | 否（随 App 发版） |
| **L2 随包进程** | `lib*.so`（lib 目录）+ `exec` | 起进程 + 连本地 socket | 桌面可换文件；Android 要重装包 |
| **L3 运行时下载** | 从网络下二进制再执行 | ❌ **Android 禁可写目录执行、iOS 禁加载外来代码** | **不可行**（移动端） |

**所以「插件」在本方案里的准确含义是「可替换、可独立升级的组件」，不是「运行时下载的模块」。**
移动端最高只能到 L2（且二进制必须随包分发）；桌面可以到 L3。

**产物布局（一份代码，四个构建）**：

```
kapp-overlay/
├── core/                   契约客户端（commonMain）：控制协议 + 回环代理 + 状态模型
├── runtime-process/        进程形态：拉起、健康检查、崩溃重启、空闲回收（jvm + android）
├── runtime-inprocess/      库形态：System.load / cinterop（android + ios + jvm）
└── native/
    ├── overlayd-darwin-arm64        可执行（桌面进程）
    ├── overlayd-windows-x64.exe     可执行（桌面进程）
    ├── liboverlayd-android-arm64.so 进程形态（lib 前缀，随包分发）
    └── liboverlay-android-arm64.so  库形态（c-shared）
```

**主程序只依赖 `core` + 一个 runtime 实现**；换形态只改依赖，业务代码一行不动。

**契约（两端必须逐字一致，Kotlin 侧只认它）—— 逐字段规范见 [overlayd-contract.md](overlayd-contract.md)**：

| 通道 | 形态 | 内容 |
|---|---|---|
| 控制 | 本机 JSON 行协议（桌面走 Unix socket / 移动走回环 TCP） | status → {state, selfIps, peers[], lastError}；proxy(host, port) → 本地端口 |
| 数据 | 127.0.0.1:<内核分配端口> 的普通 TCP | 上层继续跑现有的 TLS + 双向 pin，**不变** |

三条纪律：

1. **只绑 127.0.0.1**，端口由内核分配、进程退出即消失（§5.4）；
2. **控制通道带一次性 token**：同机其他 App 不该能驱动它改配置；数据面不额外加鉴权，
   因为真正的鉴权是上层的 TLS + pin（§5.6）；
3. **状态字段如实**：lastError 成功时必须清空，否则会出现"已连接 + 上次超时"的自相矛盾读数。

**这条路线的价值**：桌面端可以独立替换/升级，同一个二进制能被其他产品直接复用；
移动端退回库形态，但**契约不变**，所以上层代码一行都不用分叉。

## 4. 控制面与中继：必须做的取舍

### 4.1 三个选项

| | 官方托管控制面 | 自建控制面（开源自托管实现） | 完全自研 rendezvous |
|---|---|---|---|
| 工作量 | 最小（只需嵌入客户端） | 中（多一台 VPS + 运维 + 证书/DNS） | 大（协议、NAT 类型探测、打洞策略全自己写） |
| 数据主权 | ❌ 控制面在别人家（它知道设备公钥与出口地址，**不知道内容**） | ✅ | ✅ |
| 与 README 的"无需公网服务端"口径 | 冲突（我方零部署，但产品依赖第三方服务） | 冲突（可控、可说明） | 冲突（全在我们） |
| 可靠性 | 高 | 取决于自己的 VPS | 取决于自己 |
| 能否离线自建（无公网） | ❌ | ❌（控制面必须公网可达） | ❌ |

**"零服务端"在这个方案里做不到。** 能省的是：家里的公网 IP、路由器入站放行、CGNAT 限制；
不能省的是：一个帮双方交换地址的地方（IPv6 前缀会变、NAT 映射会过期，没有 rendezvous
就只能靠用户手填地址——那正是今天 `public_v6` 的痛点）。

### 4.2 认证形态三选一（同一份代码，`ControlURL` 一个字段切换）

| 形态 | 谁部署 | 谁付费 | 用户要做什么 | 风险 |
|---|---|---|---|---|
| **A. 用户自带账号（BYO）** | 谁都不用 | 用户自己的额度 | 浏览器登录一次并批准这台设备 | 分发合规待法务（§4.4） |
| **B. 用户自带控制面（自建）** | 用户自己 | 用户 | 填一个地址 | 无第三方条款 |
| **C. 我们托管** | **我们**（一台公网机器） | 我们 | 无 | 需部署 + 带宽成本 |

**默认走 A**：它是唯一"零部署 + 零商务 + 有账号就能用"的形态，也与"用户已经装了 Tailscale"的现状重合。

**B 是逃生门**：`ControlURL` 是 `tsnet.Server` 的字段（"optionally specifies the coordination
server URL"），所以 A/B/C 是**同一个二进制的三份配置**，不是三条产品线。

**C 只兜底**：它要一台公网可达的机器（自建控制面要求公网 IP + HTTPS 443），
并且会立刻撞上两条硬上限——官方个人版**最多 6 个用户**，程序化建网接口**仍是 alpha 且每组织
最多 10 张网**（超额需签商务合同）。所以 C 不是"最省事"，只是"最可控"。

形态选择**不设开关**：A/B/C 是"这张网是谁的"，不是"要不要连"；用户只需要知道"用我自己的账号"，
不需要理解"控制面"是什么。

### 4.3 中继的成本要说成人话

中继是**兜底**，不是默认路径：

- 文本/控制：几十 KB/天，可以忽略；
- 文件：**中继会替用户吃掉同等流量**。所以文件在 overlay 上要有和 `cross-network-file-screen-design.md` §3
  一样的量级提示；
- 屏幕：**继续只允许局域网**（跨网屏幕在本仓本来就没做，overlay 不能顺手把它打开，
  那是 5MB/s 的持续流，中继上不成立）。

### 4.4 必须留档的一条：BYO 分发是否被条款覆盖

**事实（原文引用，不是转述）**：其服务条款 §2.3 禁止"commercially exploit any part of the Services"、
禁止"frame, mirror, sell, resell, rent or lease use of the Services"；§1.9 又把"把功能嵌进第三方产品"
定义为 Integrations。而 §1.17 的 "Tailscale Solution" 明确包含 **Hosted Software（协调服务器）**。

**推理边界**：BYO 形态下，用户用的是**自己的账号、自己的额度**，我们既不转卖也不代收费，
也没有把它的服务包装成我们的产品 —— 从文本看，§2.3 针对的是"转卖/商业利用**它的服务**"。
但"我们是否构成商业利用"要靠外部事实（是否收费、是否作为主推路径、是否有品牌暗示）综合判断，
**这是法律结论，不是代码或文档能给出的**。

**留档结论**：技术路径已通、部署成本为零；**"能否随产品分发"待法务书面意见**。
在此之前 BYO 只能作为**内测与自选入口**，不能作为唯一路径 —— 这正是 §4.2 的 B 形态必须同时可用的原因。

**降险设计（不依赖法务结论就能做的）**：

1. 产品默认路径不依赖它（LAN / IPv6 仍是主路径）；
2. 界面写"使用你自己的账号"并指向官方，**不暗示合作**、不做品牌混用；
3. 不代收费、不代管账号；
4. **B 形态随时可切**（同一个 `ControlURL` 字段）—— 这个"随时能走开"的能力本身就是对冲。

## 5. 安全模型（本方案最容易翻车的地方）

### 5.1 陷阱：回环地址 ≠ 局域网

今天的判据 `IpAddressUtils.isPrivateOrLocal` **显式把 `127.0.0.0/8` 判成局域网**，
因为 K1 的明文长连接需要一个"本机可达"的兜底。而 overlay 的端点恰好就在 `127.0.0.1`。

**如果只是"多一个地址让 `isLanAddress` 判"**，后果是：
> 手机上一切本该被 fail-closed 拒掉的明文长连接，会因为"对端是本机回环"而被放行，
> 而那条回环背后是一条真的走公网的隧道。

这直接违反 `AGENTS.md` §2.5 与 `public-transport-security.md` 的裁决。

### 5.2 修法：判据按「承载」而不是按「地址」

| 判据 | 今天 | 本方案 |
|---|---|---|
| 明文允不允许 | `isLanAddress(peer)` | **不变**（overlay 端点一律返回 false 或干脆不进这条路） |
| overlay 连接怎么建 | — | `OverlayTransport` 的 `isSecure = true`，走 TLS + 双向 pin，**fail-closed** |
| 拨号诊断 | `lastError` | 新增 `overlay-state`（`off / starting / up / unreachable`），**成功时清空、失败时如实写** |

落地纪律（写成测试，不是写成文档）：

1. **源码级守卫**：`expect/actual` 的 overlay 端点不得出现在任何明文路径的判定里；
   一旦出现，守卫红。理由与 `AGENTS.md` §4 的"多处必须一致"同类。
2. **反向验证**：把 `127.0.0.1` 的回环特权放回去，新测试必须变红（否则这条测试没在测东西）。
3. **不给用户一个"用 overlay 走明文"的选项**——没有这个开关，就没有这条后门。

### 5.3 威胁模型（写清楚，而不是只说"加密了"）

| 对手 | 能做什么 | 本方案挡不挡 |
|---|---|---|
| 网络旁观者（运营商/公共 Wi-Fi） | 抓包 | ✅ WireGuard 加密，看得到"在跟某中继说话"，看不到内容 |
| 中继/控制面运维方 | 转发流量、看到设备公钥与出口地址、看到通信元数据 | ✅ 内容解不开；✅ TLS+pin 保证对端身份；❌ **元数据可见** |
| 拿到控制面账号的人 | 往 tailnet 里塞一台设备 | ⚠️ 能塞进来，但**没有对端 pin 就过不了 TLS 校验**（fail-closed） |
| 同网段攻击者 | 冒充对端 IP | ✅ 双向 SPKI pin |
| 本机恶意 App | 读 `127.0.0.1` 代理端口 | ⚠️ 回环端口默认对同机所有 App 可见；见 §5.4 |

### 5.4 回环代理的本地暴露面

本地代理端口一旦起来，**同机的任何 App 都能连它**。缓解：

- 端口由内核分配（不固定），进程退出即消失；
- 代理本身**不做鉴权**，真正的鉴权在上层 TLS + pin——所以即使被本地 App 连上，它也连不到对端；
- 不监听 `0.0.0.0`，只 `127.0.0.1`（守护测试：绑定地址断言）。

### 5.5 密钥与状态的存放

overlay 的节点私钥与状态目录**必须进平台的受保护存储**（Android keystore / iOS Keychain，
与现有 `link-key` 同一套落点），不能以明文躺在 `files/` 里再被备份同步走。

### 5.6 一条必须先钉死的概念：overlay 不是信任边界

"局域网"在本仓是有**安全含义**的（`isLanAddress` 为真 ⇒ 允许明文长连接）。所以把三件事分开：

| 层 | 由谁保证 | 能不能当"局域网"用 |
|---|---|---|
| 地址（谁在哪） | overlay 控制面 | ✅ 当地址用 |
| 传输加密（旁观者看不到） | WireGuard | ✅ 当加密用 |
| **对端身份（它是不是那台电脑）** | **只由配对时的 SPKI pin 保证** | ❌ **绝不能** |

理由：overlay 的节点身份是**控制面签发**的。控制面被入侵、或有人拿到控制面账号，
就能让一台陌生设备顶着一个"看起来对"的虚拟 IP。只有二维码带过来的 pin 能挡住它。

**所以 `100.64.0.0/10` 必须继续被判成"公网"。** 今天 `isPrivateOrLocal` 的 IPv4 分支不含它，
这是**对的**，不要"顺手补上"——补上它等于在 overlay 上开一条明文通道。

## 6. 路由与策略：它只该在"不通"时出场

### 6.1 候选顺序

```
lan_v4 / lan_v6   （同网段，明文，最快最省电）
      ↓ 不同网段
public_v6         （直连，TLS + pin）
      ↓ 对端没有可入站地址 / 打不通
overlay           （用户态栈，TLS + pin，可能经中继）
      ↓ overlay 起不来或控制面不可达
离线队列（今天的行为）
```

### 6.2 不许做的事

1. **不要做成开关。** 产品立场是"用户只关心哪张网都能无感连上"；overlay 是路由表里的一档，
   不是设置页里的复选框。
2. **不要在局域网默认启用 overlay。** 那会白白多一跳、多耗电、多一条要维护的长连接。
   局域网已经有一条明文长连接（K1），更快。
3. **不要让 overlay 接管文件与屏幕的全部流量。** 文件要限大小/给提示；屏幕仍只允许局域网。
4. **不要让 overlay 成为唯一路径。** 控制面挂了、中继挂了，现有 LAN/IPv6 必须照常工作。

### 6.3 与 K1（长连接）的关系

overlay 自带保活（WireGuard 的 NAT 映射由 overlay 自己维护），所以：

- 经 overlay 建的那条长连接**不需要再叠 15s 心跳**（省电）；
- 但 **Android 的 Doze 问题一分没少**：前台服务那条（task-15）依然是前提，overlay 不是保活方案。

### 6.4 候选池要新增一种类型，而不是复用 `lan_v4`

今天的 `peerCandidateTypeOf` **明确把 `100.64.0.0/10` 判成 null**（隧道 CGNAT），
理由是"Clash fake-IP 与 Tailscale CGNAT"混在网卡列表里，进码就是垃圾候选。这条**仍然正确**。

但装了 overlay 之后，`100.x` 恰恰是**唯一跨网可达**的地址。所以不能改判，只能**新增一档**：

| 候选类型 | 来源 | 何时进入候选池 |
|---|---|---|
| `lan_v4` / `lan_v6` / `public_v6` | 本机网卡 | 今天的行为，**不变** |
| `overlay`（新增） | overlay 会话自己的虚拟 IP | **仅当本机 overlay 节点已启动并在线**时 |

两条纪律：

1. **没启动 overlay 就绝不产出 `overlay` 候选** —— 否则二维码会把一个永远连不上的地址发出去
   （本仓已有同类教训：候选写了但端点不存在，手机一直 connect-timeout）；
2. **`peerCandidateTypeOf` 的既有判定不动** —— 它服务的是"网卡枚举"这条路径，
   与"overlay 会话"是**两个来源**，混在一起就没人能说清某个 `100.x` 到底是谁。

## 7. 工程代价（如实报数，不报"大概"）

| 项 | 代价 | 备注 |
|---|---|---|
| **包体（实测）** | Android arm64 `.so` **20.7MB**（strip 后）、gzip 后 **7.3MB**；桌面 c-archive 26.8MB | 原估计 +8~12MB **偏低约一倍**（见 §10.1）。打包方式决定用户实际付出：未压缩进 APK ≈ 21MB，压缩 ≈ 7.3MB |
| **构建链** | Android：Go → `.so`（NDK toolchain）；iOS：Go → `.a` → `xcframework`；桌面：本机架构 | **进 CI 是真实工程量**，且三端版本必须锁死。实测：tsnet v1.104.2 要求 **Go ≥ 1.27.3**，本机 1.26.1 不够，需要 CI 显式装新版工具链 |
| **版本一致性** | 三端 native 库同一版本 | 不同版本会重演"两端必须同版本"的坑（`AGENTS.md` §2.2） |
| **性能（实测）** | netstack 自拨 **177.6 MB/s**；经 `proxy` 走完控制面+数据面 **200.7 MB/s**（50MB 回环） | 都是**同机自环**，不含 WireGuard 与真实链路；跨机吞吐仍待第二节点。结论：netstack 与代理层都不是瓶颈 |
| **启动时间（实测）** | 节点启动 **20~22ms**（本机 darwin arm64） | 首次加入网络还要等人在浏览器里授权，那一步是**人的时间**，不是进程时间；所以"惰性启动"依然成立，但不能把授权等待算进启动耗时 |
| **内存（实测）** | 未入网 **Sys 18.9MB**；入网空转 **19.6MB**；**50MB 突发传输时峰值 47.9MB** | 空转离 50MB 放弃线很远，但**突发时只差 2MB** —— 这条要在实现里做缓冲/背压调优，不能等上线才发现 |
| **可执行体积（实测）** | 桌面 sidecar 二进制 **20MB**（strip 后） | 桌面端不敏感，但说明"一个 overlay 节点"的最小成本 |
| **协议无关性** | 无 | 信封、分帧、ACK、队列全不改 |

## 10. POC 清单（每一项都必须能判红）

> 纪律：**先让判据失败，再让它通过**。以下每一项都要有"把旧行为放回去就变红"的反向验证。

1. **连通性**：关闭路由器的 IPv6 入站放行，手机在蜂窝网下仍能经 overlay 连到桌面端的 `17879`。
   反向：关掉 overlay，同一场景必须失败（否则测试没在测 overlay）。
2. **无 VPN 痕迹**：Android 上 `VpnService` 数量不变、状态栏无 VPN 图标、另一个 VPN 应用不被顶掉。
3. **本地代理边界**：代理只绑 `127.0.0.1`（断言绑定地址；试图从同网段另一台机器连必须失败）。
4. **明文后门守卫**：删掉 TLS 层、只剩 overlay 时，连接必须被拒（`plaintextLinkForbidden` 生效）。
   反向：把回环特权放回去 → 必须**被放行**（证明这条测试真的在守 §5.1）。
5. **惰性启动**：局域网场景下，overlay 进程/线程数不增加（断言"没有启动过"）。
6. **性能基线**：≥50MB 文件续传一轮，记吞吐与耗电；与 `public_v6` 直连对比给百分比（**实测数字才写进文档**）。
7. **失败如实**：控制面不可达时，UI 不能显示"在线"，`link.json` 必须写 `overlay-state = unreachable`
   （`AGENTS.md` §2.5：诊断字段要么如实、要么不存在）。
8. **发现不走广播**：overlay 场景下成员来自 `Status()` / 配对码，而不是广播。
   反向：把广播发现打开并断言"收不到"——若真收到了，说明我们对 overlay 的假设错了，必须先查清。
9. **候选不产出幽灵**：overlay 未启动时 `overlay` 候选必须为空（断言数量为 0），
   否则二维码会发一个永远连不上的地址。
10. **回滚**：删掉 `ovl1` 能力位，全部测试回到今天的行为。

### 10.1 包体与构建代价怎么量（可复现）

§7 的 +8~12MB 是**估计值**，必须在真机产物上量。三步，任一人可复现：

```bash
# 0) 准备：一个只引用 tsnet 的最小 Go 包（不做产品功能，只量链接体积）
mkdir -p /tmp/overlay-probe && cd /tmp/overlay-probe
go mod init probe && go get tailscale.com@latest

# 1) 桌面（c-archive）
CGO_ENABLED=1 GOOS=darwin GOARCH=arm64 go build -buildmode=c-archive -o libprobe.a .
ls -lh libprobe.a

# 2) Android arm64（c-shared；NDK 版本按本机实际）
NDK=$HOME/Library/Android/sdk/ndk/27.0.12077973
CC=$NDK/toolchains/llvm/prebuilt/darwin-x86_64/bin/aarch64-linux-android21-clang
CGO_ENABLED=1 GOOS=android GOARCH=arm64 CC=$CC \
  go build -buildmode=c-shared -ldflags='-s -w' -o libprobe.so .
ls -lh libprobe.so

# 3) iOS arm64（c-archive）
CGO_ENABLED=1 GOOS=ios GOARCH=arm64 CC=$NDK/../.. >/dev/null 2>&1 || true
```

**判据（三条都要记）**：

1. **原始体积**：`.so` / `.a` 大小（上面 ls 的输出）；
2. **装进 App 后的真实增量**：加上 ABI 拆分前后各打一个 APK，取 **AAB/APK 字节差**（这才是用户下载要付的）；
3. **剥离后体积**：`-ldflags='-s -w'` 前后各一次，差值决定要不要上 strip。

> 只有第 2 条能写进商店说明。第 1、3 条是给工程看的。
> 量不出来就写"未实测"，**不许把估计值写成结论**。

**已实测（离线部分，可复现）**：

| 项 | 读数 | 说明 |
|---|---|---|
| NDK clang（aarch64-linux-android21-clang） | 可用 | 交叉编译链本身没有坑 |
| Go 运行时地板（Android arm64，c-shared，-s -w） | **2.7 MB** | 只含标准库（crypto/json/net），**不含 tsnet** |
| 同上（darwin arm64，c-archive，-s -w） | **3.2 MB** | 桌面端不敏感 |
| 未 strip（darwin arm64） | **6.7 MB** | strip 后 3.2 MB ⇒ **必须开 -s -w** |

**已实测（tsnet 真实链接，可复现）**：

**按 ABI 分开量（每个数字都是「单个 ABI」，不是三份之和）**：

| ABI | `.so`（strip） | gzip -9 |
|---|---|---|
| `arm64-v8a` | **20.7 MB** | 7.3 MB |
| `armeabi-v7a` | 20.0 MB | 7.6 MB |
| `x86_64` | 22.2 MB | 7.9 MB |
| **三份全打（通用 APK）** | **62.9 MB** | 22.8 MB |

| 其他产物 | 体积 | 说明 |
|---|---|---|
| darwin arm64 `.a`（strip） | 26.8 MB | 桌面端不敏感 |
| darwin arm64 `.a`（未 strip） | 54.9 MB | strip 差 2 倍，**必须开** |

> **别把单个 ABI 当成总增量**：20.7MB 是 `arm64-v8a` 一份。
> 走 AAB / ABI 拆分时每个用户只拿自己那一份；打通用 APK 才是 62.9MB。
> 用户真实下载量必须在**真 AAB/APK** 上量（§10.1 判据第 2 条），gzip 只能当参考。

**结论（修正原估计）**：Go 运行时地板 2.7MB，tsnet 净增量约 **18MB**，合计 **20.7MB**。
§7 原来的 +8~12MB **低了约一倍**。这条不是"工程细节"，它直接影响用户下载体积，见产品方案 §9.1 第 2 条。

**三个降体积方向（按代价从低到高）**：

1. **压缩 native 库**（本产品不在 Play 分发，动态功能模块用不了）：
   `packaging { jniLibs { useLegacyPackaging = true } }` ⇒ APK 里压缩存放，**下载增量 20.7 → 7.3MB**，
   安装后仍是 20.7MB。这是非 Play 渠道下最划算的一档；
2. **ABI 拆分**：只发 `arm64-v8a`（+ 可选 `armeabi-v7a`），避免一份包塞两种架构；
3. **换更小的栈**：不用 tsnet，改用 `wireguard-go + gvisor netstack` 自己搭（体积可能降到 6~8MB），
   但**丢掉控制面与 DERP 回退** —— 等于把 rendezvous 自己做回来（技术方案 §4.1 的"完全自研"那一列）。

## 12. 一句话总结

> 嵌入式 overlay 解决的是"对端没有可入站地址"这一个问题，代价是"必须有一个 rendezvous 和一个可达中继"。
> 它给的是**地址平面**（每台设备一个稳定虚拟 IP，所以像局域网），**不是广播域**（广播发现不会跨过去），
> 更**不是信任边界**（对端身份只由配对时的 pin 保证）。
> 所以它可以进候选池当第四档，但`100.64/10` 永远按公网对待，TLS 与双向 pin 一步都不能省。
