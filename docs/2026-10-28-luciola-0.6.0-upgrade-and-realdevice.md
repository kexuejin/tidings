# luciola 0.6.0 升级与真机验收

日期：2026-10-28。luciola 0.5.1 → **0.6.0**（mavenLocal，`io.github.kexuejin:luciola-*`）。

## 0.6.0 带来的破坏性变更（本仓适配点）

| 变更 | 本仓适配 |
| :--- | :--- |
| `SecureSessionListener.on_message` 三参化（+ `peerFingerprint`、`remoteAddr`） | `SecureChannelTransport` 两处监听器同步签名；入站二进制帧归属改为「引擎确权指纹 → socket 真实来源」优先，不再依赖会话状态机反查 |
| `DiscoverySession::new` 新增 `nodeId / tcpPort / publicKey` | `LuciolaDiscoveryEngine` 新增三个可空构造参并透传；`LuciolaTransportFactory.createDiscovery` 传 `channelTcpPort = channelListenPort`、`publicKey = identity.publicKey`——**信标身份与零信任体系完全对齐**（nodeId 取 Tidings 自己的 nodeId） |
| 信标 `Profile` 新增 `public_key`（serde 双向兼容） | 无需适配，自动生效 |
| 僵尸 accept 修复（listen 的 bind/accept 可被 shutdown 打断） | 无需适配，`stop()` 后端口立即释放（真机验收里的端口释放断言回归） |

依赖：`gradle/libs.versions.toml` `luciola = "0.6.0"`。门禁：`compileKotlinJvm` / `compileAndroidMain` / `compileKotlinIosArm64` / `compileKotlinIosSimulatorArm64` / `:core:jvmTest`（全量）/ `:core:jvmAcceptanceTest`（50MB + SHA + 端口释放）全部通过。

## 真机验收（Pixel 6 ↔ Mac，真实 Wi-Fi）

桌面宿主用 release 引擎（`TIDINGS_LUCIOLA_NATIVE=<cargo-target>/release`），
手机装 debug APK（0.6.0 AAR 内嵌 `.so`）。

```
# 配对（桌面 → 手机，走加密信道自证帧）
POST /v1/dev/pair {"host":"192.0.2.22","port":17878}   → {"ok":true}

# 文本消息（luciola 加密信道）
POST /v1/send {"to":"b2c3d4e5-…","text":"…"}
→ status=sent, outcome=sent-via-udp elapsed=123ms
  endpoints=[192.0.2.22:17878 acked 123ms]     # 对方已 ACK

# 18MB 文件（purpose=image 触发自动接收，20MB 上限内）
POST /v1/send-file … img18.bin
桌面源:   4d19bfcc787698477f8db9f675e1a0429207e5bfab4f6dde4acefa25ea9779e4
手机落盘: files/relay/downloads/img18.bin/img18.bin
          18,874,368 字节整, sha256 一致 ✓
```

## 途中定位并修掉的环境问题：桌面身份密钥轮换

真机 50MB 复跑第一次全军覆没（`no-ack` + `tcp Connection refused`）。根因**不在
luciola**：桌面数据目录迁移后 Ed25519 种子重新生成，而手机 `state.json` 的
`endpoints["192.0.2.82:17878"]` 里存的还是 10/26 的旧公钥——deny-by-default
之下信道握手全被拒。把手机存的桌面公钥更新为当前密钥后全链路恢复。

**教训**：桌面侧身份种子一旦轮换，所有已配对对端的信任全部失效，且症状是
「沉默的拒绝」（对端不报错，只是不 ACK）。后续考虑：配对失败时在两端各打一行
「pin mismatch：对方宣告指纹 = X，本地信任表无此指纹」。

## 应用层遗留（非 luciola 问题，待办）

1. **50MB 文件需要 UI 点「接收」**：`autoAcceptsFile` 只放行 `purpose=image`
   且 ≤20MB；真机 UI 因「桌面显示离线」（见下条）看不到 offer 卡片。
2. **手机 UI 把桌面宿主显示为「离线」**：桌面对端身份轮换后，手机端 registry
   的在线记录绑定在旧 nodeId 上；新旧两个会话条目并存。
3. **投递管道对纯 luciola 对端的适配**：手机不声明 `lnk1`（挂在
   `advertiseAgent` 下），legacy TCP 17879 已退役但桌面投递路径仍在尝试它；
   50MB 级推送依赖这条路径就位。

## iOS 模拟器（iPhone 17 Pro）状态

- 构建/安装/启动 ✓（gobley 0.6.0 Kotlin/Native 绑定 + 双架构静态库重建）；
- 信标跨网到达桌面并入册 ✓（`iPhone 17 Pro online, udp 17978`）；
- 信道一跳未通，两个环境根因（与 luciola 无关）：
  1. **无签名构建（`CODE_SIGNING_ALLOWED=NO`）→ 钥匙串被拒** → 每次启动
     重新生成身份，配对材料旋即过期。**签名构建后身份跨启动稳定**（已实测
     两次重启同一密钥）。模拟器联调必须用默认 ad-hoc 签名构建。
  2. **新版 Xcode 模拟器 socket 不再出现在宿主 `lsof`**（旧文档「lsof 里
     Tidings *:17978」的判据失效），宿主直拨 `192.0.2.82:17978` refused。
     待按 2026-10-27 runbook 交互式联调或改用真机验证。

## 顺带修复（luciola 0.6.0 内）

- 僵尸 accept 循环：`disconnect()` 到达时引擎若阻塞在 `accept_secure`，
  旧代码没人消费 shutdown → 监听端口永不释放。0.6.0 起 bind/accept 均可被
  shutdown 打断，Rust 层有 `port_release_e2e.rs` 钉死；本仓 `jvmAcceptanceTest`
  的「stop() 之后端口必须释放」断言随之恢复。
