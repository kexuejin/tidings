## 0. 一页纸

**一句话**：让"我的设备"在任意网络下彼此可见、可达 —— 而且**只在 App 内生效**，不接管手机的网络。

| | |
|---|---|
| **是什么** | 给每台已授权设备一个稳定的私有地址，于是"换到蜂窝网还能连上家里电脑"变成默认行为 |
| **不是什么** | 不是 VPN（不接管系统流量、没有 VPN 图标、不抢别人的 VPN 槽位）；不是中继（内容不经我们转发）；不是"开一个开关" |
| **给谁** | ① 已有私人网络账号的技术型用户（P1）；② 以后所有用户（P2 我们提供） |
| **不给谁** | 期待"装完什么都不用做"的用户（P1 阶段如实说明，见 §3.4） |
| **成功判据** | ① 关闭路由器 IPv6 入站后，跨网文本 30 秒内可达；② 局域网场景 overlay **零流量、零启动**；③ 无 VPN 图标、不打断其他 VPN |
| **明确不做** | 不做公网中继转发我们的服务、不做跨网屏幕、不做"连接方式"设置项 |

## 1. 为什么现在做

### 1.1 今天的三条路，各有明确的失败面

| 路径 | 覆盖率 | 失败时的用户感受 |
|---|---|---|
| 局域网直连 | 在家/同网时 | 无 |
| 公网 IPv6 直连 | 家里有 GUA **且路由器放行入站** | "在外面就连不上"，且不知道为什么 |
| 离线队列 | 以上都不通时 | 消息发了没回音，用户以为对方没回 |

第二条的失败面不是"配置麻烦"，是**多数家庭不满足前提**（CGNAT、只给 IPv4、运营商封入站、公司/酒店网络）。
而"放行 IPv6 入站"这句话，普通用户听不懂，也不该被要求懂。

### 1.2 同类产品怎么解的，以及我们不照抄什么

同类产品（手机连自己电脑）给的方案是：VPS + 域名反代、HTTPS 隧道、装 Tailscale 开 VPN、局域网。
**四种里有三种要求用户自己弄一台服务器或开 VPN**，第四种只在同一个 Wi-Fi 内有效。

它们的可选方案多，是因为它们的手机通道是 **HTTPS/WebSocket**，任何 HTTP 隧道都能套；
本产品的通道是**自定义帧协议**，套不上那批现成方案。这是技术前提的差别，不是我们漏做（技术文档 §2.4 有对照）。

**我们照抄的只有一件事**：把网络栈放进 App 进程里（已有商业产品验证可行），
**不照抄**的是"我们自己建一套 SaaS 控制面"——那会带来部署、带宽与商务成本（技术文档 §4）。

## 2. 产品定位与心智

### 2.1 名字与用词

| 内部术语 | 用户看到的词 | 原因 |
|---|---|---|
| overlay / tailnet / control plane | **私人网络** | 用户不需要理解控制面是什么 |
| 100.64.0.0/10 / 虚拟 IP | **设备**（只显示名字，不显示地址） | 地址是实现细节 |
| 加入 tailnet | **把设备加入私人网络** | 动作可理解 |
| auth key / 登录 URL | **授权**（"在浏览器里确认一次"） | 一次性动作 |

**界面上永远不出现**：tailnet、控制面、CGNAT、虚拟 IP、DERP。

### 2.2 三句话讲清价值

1. **换网不断**：从家里 Wi-Fi 切到 4G，连着的那台电脑不会掉；
2. **只影响这个 App**：不用开 VPN，不接管手机其他流量，不占用系统唯一的 VPN 位置；
3. **不用配路由器**：不需要懂"放行入站"，也不需要公网地址。

### 2.3 与「局域网」的关系（对用户与对实现，是两套话）

- **对用户**：像局域网 —— 设备之间"直接可见"；
- **对实现**：只是**地址平面**像，**广播域与信任边界都不像**（技术文档 §3.4 / §5.6）。

这条差别**必须写进实现纪律**，但不能写进 UI：
用户不需要知道"overlay 不转发广播"，他只需要看到"我的设备都在列表里"。

### 2.4 与「配对」的关系

本产品有两个正交概念，**界面上要合并成一次操作**：

| 概念 | 回答的问题 | 谁保证 |
|---|---|---|
| **配对** | "这台设备是不是它自己" | 二维码里的 SPKI pin（信任根） |
| **私人网络** | "我现在能不能够到它" | 私有地址 + 打洞/中继（可达性） |

**合并不等于混淆**：流程上合并（一次扫码两件事都办完），概念上严格分开
（可达性出问题**不许**降级成"少验一道 pin"）。

## 3. 用户旅程

### J1 · 首次加入（主流程，一次扫码）

| 步骤 | 用户 | 系统 | 失败时用户看到 |
|---|---|---|---|
| 1 | 桌面端点「手机连接」→「让手机在外网也能连」 | 生成邀请（二维码）+ 启动本机节点 | — |
| 2 | 手机扫码 | 解析邀请：地址、pin、是否含私人网络 | "二维码不认识/已过期" |
| 3 | 手机弹「在浏览器里确认一次」 | 打开授权页 | "授权页打不开"→ 给重试与手动粘贴入口 |
| 4 | 用户在浏览器点允许 | 节点入网，拿到私有地址 | "等待确认中…"（有进度，不装死） |
| 5 | 回到 App | 建立链路、校验 pin、显示"已连接" | "已入网但连不上"→ 见 J5 |

**关键**：第 4 步是**人的动作**，界面必须**明确说明"这一步要在浏览器完成"**，
并显示"正在等待确认"，而不是转圈到超时（用户问卷里最常见的抱怨是"它卡住了"）。

### J2 · 日常使用（无感）

- 打开 App → 自动按 局域网 → 公网 IPv6 → 私人网络 顺序尝试 → 用户只看到"已连接"；
- **没有"连接"按钮**，也没有"用哪种方式"的选择。

### J3 · 同一 Wi-Fi（零开销）

- 局域网直连成功 ⇒ **私人网络不启动**（不建节点、不耗电、不占连接）；
- 判据：技术文档 §10 第 5 条（断言"没有启动过"）。

### J4 · 授权过期 / 换手机 / 移除设备

| 场景 | 用户看到 | 出路 |
|---|---|---|
| 授权过期 | "私人网络需要重新确认"（一句话，不吓人） | 点一下重新授权 |
| 换手机 | 新设备走 J1 | — |
| 移除某台设备 | 桌面端「设备」列表里「移除」 | 移除后该设备立刻不可达（如实） |

### J5 · 私人网络不可用（必须如实，不许假装在线）

| 原因 | 用户看到 | 出路 |
|---|---|---|
| 控制面不可达 | "私人网络暂时不可用，正在重试" | 局域网/IPv6 仍可用（**同时显示**） |
| 已入网但连不上对端 | "已加入私人网络，但暂时连不上这台电脑" | 重试 / 检查对端是否开机 |
| 平台不支持（未签名 iOS 等） | "这台设备暂不支持" | 说明原因，不画一个注定失败的入口 |

**纪律**：失败时**不许**显示"在线"，也**不许**把原因写成"网络异常"这类废话
（AGENTS.md §2.5：诊断字段要么如实、要么不存在）。

## 4. 界面设计

### 4.1 信息架构（只加三处，不新增一级入口）

| 位置 | 内容 |
|---|---|
| **设置 → 私人网络** | 状态、设备列表、加入/退出、诊断入口 |
| **节点列表** | 每个节点一个**承载徽标**（局域网 / 外网 / 私人网络） |
| **加入流程** | 三个屏：扫码 → 等待确认 → 结果 |

### 4.2 设置 → 私人网络（五种状态）

| 状态 | 主文案 | 主行动 |
|---|---|---|
| 未加入 | "还没有加入私人网络。加入后，在外面也能连上家里的电脑。" | **加入**（扫码） |
| 加入中 | "正在等待你在浏览器里确认（还剩 4 分钟）" | 重新打开 / 取消 |
| 已加入 | "已加入 · N 台设备" | 设备 / 网络诊断 |
| 需重新确认 | "私人网络需要你重新确认一次" | **重新确认** |
| 不可用 | "私人网络暂时不可用，正在重试。局域网和公网直连仍然有效。" | 重试 / 诊断 |

**已加入**状态下显示设备列表（名字 + 平台），例如：

    私人网络
    ● 已加入                 2 台设备
      MacBook（这台） · Pixel 8
      [ 设备 ]      [ 网络诊断 ]

**空态必须有出路**：未加入 = 主行动；不可用 = 同时显示"另外两条路还通着"。

### 4.3 节点列表的承载徽标

| 徽标 | 含义 | 视觉 |
|---|---|---|
| 局域网 | 同一张网，最快 | 实心绿点 |
| 外网直连 | 经公网 IPv6 | 空心绿点 |
| 私人网络 | 经私有地址 | 茶绿描边 + 小锁 |
| 离线 | 现在够不到 | 灰点 + "上次在线 …" |

**只显示结论，不显示地址**。技术细节进「网络诊断」。

### 4.4 加入流程（三屏）

1. **扫码**：复用现有扫码页，识别到邀请里带私人网络时多一行"加入你的私人网络：<网络名>"；
2. **等待确认**：一句话说清"接下来要在浏览器里点允许"，配一个"重新打开授权页"按钮 + 倒计时；
3. **结果**：成功 = "已加入，2 台设备"；失败 = 一条具体原因 + 一条出路。

### 4.5 网络诊断（把"为什么连不上"变成可读的一句话）

    私人网络      已加入 · 2 台设备
    本机地址      已分配
    对端可达      是（直连） / 经中继 / 否
    最近错误      无 / <一句人话>
    [ 复制诊断信息 ]

对应 link.json 新增字段（技术文档 §5.2）：overlay-state / overlay-peer / overlay-last-error。
**成功时必须清空 last-error**，否则会出现 connected=true + lastError=timeout 这种自相矛盾读数。

### 4.6 文案表（每一条都要能回答"然后呢"）

| 场景 | 文案 | 下一步 |
|---|---|---|
| 未加入 | 还没有加入私人网络。加入后，在外面也能连上家里的电脑。 | 加入 |
| 等待确认 | 请在浏览器里完成确认，这一步只能由你来做。 | 重新打开 / 取消 |
| 授权过期 | 私人网络需要你重新确认一次（这是安全设置，不是你操作错了）。 | 重新确认 |
| 控制面不可达 | 私人网络暂时不可用，正在重试。局域网和公网直连仍然有效。 | 重试 / 诊断 |
| 已入网连不上 | 已加入私人网络，但暂时连不上这台电脑。可能是对方关机或网络受限。 | 重试 |
| 平台不支持 | 这台设备暂不支持私人网络（原因：<如实>）。局域网与公网直连不受影响。 | 关闭 |

> 所有文案进 composeResources/values*/strings.xml，**不许硬编码**（cjkLiteralGate）。

### 4.7 明确不做的界面

1. **不做"开启私人网络"的开关** —— 它不是一个连接方式选择器，加入即生效；
2. **不显示虚拟 IP** —— 用户不关心，泄露了还得解释；
3. **不做"优先走私人网络"的选项** —— 路由由代码裁决（局域网优先），不由用户选；
4. **不把"加入"做成新手弹窗** —— 它是自选能力，不打断首次使用。

## 5. 交互模型：一次扫码，办两件事

### 5.1 邀请载荷

复用现有配对载荷，**新增一个可选的私人网络段**（不认识的旧端会忽略，但要按能力位协商）：

    { nodeId, port, pin, candidates[], overlay? { control, join, name } }

- control：控制面地址（BYO 时为空 = 用官方默认）；
- join：一次性加入凭据（短期有效，用后即焚）；
- name：网络展示名（"我的设备"）。

### 5.2 为什么合并成一次

| 分两步 | 一次 |
|---|---|
| 用户要理解"先加网络、再配对" | 一个动作 |
| 两次二维码、两次等待 | 一次 |
| 容易只做一半（加了网络没配对 → 连上但被拒） | 原子完成 |

**但载荷里的 pin 仍然独立校验** —— 合并流程不等于合并信任。

### 5.3 老端与降级

- 邀请里没有 overlay 段 ⇒ 走今天的行为（一个字节都不变）；
- 手机不支持（能力位 ovl1 未声明）⇒ 桌面端不展示"让手机在外网连"的入口，**不画注定失败的按钮**。

## 6. 状态机

    未加入 --加入--> 等待确认 --批准--> 已加入 --失效--> 需重新确认
       ^              |                 |                 |
       +----取消------+                 +----被移除-------+
                                        +----不可达--> 不可用 --恢复--> 已加入

| 状态 | 用户可做的动作 | 系统行为 |
|---|---|---|
| 未加入 | 加入 | 不启动任何节点（零开销） |
| 等待确认 | 重新打开授权页 / 取消 | 轮询入网状态，有超时 |
| 已加入 | 设备 / 诊断 / 退出 | 按需启停传输，空闲释放 |
| 需重新确认 | 重新确认 | 保留配对（pin 不变），只重做授权 |
| 不可用 | 重试 / 诊断 | 退避重试，**不影响其他两条路径** |

**与节点状态的关系**：overlay 状态**不是**"在线/离线"。节点离线仍可能经局域网可达 ——
两个状态必须分开存、分开显示（否则会出现"私人网络不可用"却"局域网连着"的自相矛盾界面）。

## 7. 安全的产品表达（说人话，但不撒谎）

用户需要知道的三件事，写在「私人网络」页的可展开说明里：

1. **它只影响捎话**：不开 VPN、不接管其他 App、不占用系统 VPN 位置；
2. **我们看不到你的内容**：内容端到端加密；如果经中继转发，中继只能看到"有数据在流动"，看不到内容；
3. **它知道哪些设备属于你**：控制面能看到设备公钥与网络地址，**看不到消息与文件内容**。

第 3 条必须写 —— 这是这个方案唯一说不掉的让步（技术文档 §5.3 威胁模型）。
写清楚不会流失用户，藏起来才会在出问题时变成信任危机。

## 8. 可复制形态（其他产品也能用）

| 层 | 放哪 | 内容 |
|---|---|---|
| **守护进程** | 独立产物 overlayd（Go，一份代码） | 桌面直接跑；**Android 也能跑**（打成 lib*.so + extractNativeLibs，见技术设计 §3.5）；iOS 只能进程内库 |
| **能力模块** | kapp-lib（新模块 kapp-overlay） | 契约客户端（控制协议 + 回环代理）、expect/actual 运行时、状态机、诊断数据结构；**桌面/移动只差一个 Runtime 实现** |
| **UI 组件** | kapp-lib 的 ui/ | 「私人网络」状态卡、承载徽标、诊断面板（**参数接原语，不接产品模型**） |
| **每产品配置** | 各产品一份 | 控制面默认地址、能力位名、网络展示名、文案 key、是否允许 BYO |
| **产品侧接线** | 本仓 core | 候选池新增 overlay 类型、OverlayTransport、ovl1 能力位 |

契约逐字段规范见 [overlayd-contract.md](overlayd-contract.md)（命令、状态、错误码、生命周期、契约级验收）。

判据（AGENTS.md §2.6 的同一套）：**改一处，所有接入产品都变** —— 如果做不到，说明复制成了多份。

## 9. 分期

| 期 | 范围 | 用户可见 | 验收 | 放弃条件 |
|---|---|---|---|---|
| **P0 技术验证** | 桌面端 sidecar 跑通跨网连接 | 不可见（内部） | 关掉 IPv6 入站后仍能连上；记录吞吐/内存/启动耗时 | 吞吐低于直连 50% 或常驻内存 > 50MB |
| **P1 BYO 高级项** | 桌面端 + Android，用户自带账号 | 设置页出现「私人网络」 | §10 的判据全绿；加入成功率 ≥ 80% | 加入成功率 < 50%（用户搞不定浏览器授权） |
| **P2 可托管** | 加"用我们的网络"选项 | 默认路径 | 法务书面意见 + 每用户带宽成本可承受 | 法务不允许分发 |
| **P3 iOS** | iOS 嵌入 | 同上 | 未签名构建如实报不可用 | — |

**P1 的定位必须写清**：这是**自选能力**，不是默认路径。默认仍是局域网 / IPv6。

### 9.1 已确认的产品裁决

| # | 问题 | 裁决 | 影响 |
|---|---|---|---|
| 1 | P1 只服务"已有账号"的用户，能否接受？ | **接受** | P1 不改产品文案去掩盖门槛，如实写"需要你自己的账号"；P2 才面向所有人 |
| 2 | 手机端包体能否接受？ | **定案：单 APK + 压缩 native 库 + 只发 arm64** | 实测 `.so` 20.7MB / gzip 7.3MB（技术设计 §10.1）。下载增量 **+7.3MB**（47MB → ~54MB），安装增量 +20.7MB；**不支持 32 位**，`x86_64` 与 `armeabi-v7a` 都不进发布包 |
| 3 | 一次扫码合并"加入网络 + 配对"？ | **同意** | 邀请载荷新增可选段 ⇒ **两端必须同版本**（AGENTS.md §2.2 的硬约束，提交信息要写清） |
| 4 | 灰度与回滚用远端功能位（不是用户开关）？ | **可以** | 回滚 = 运维动作；仍不新增任何面向用户的"连接方式"开关 |

> 这四条只解锁 P0/P1。P2（我们托管）仍卡在 §11 的"条款/分发合规"一条上，
> 不在本次裁决范围内。

**第 2 条需要重议的原因**：裁决时用的是"约 8~12MB"的估计，实测是 **20.7MB/ABI**（gzip 7.3MB）。
这不是同一个量级，不能沿用旧裁决。

**而且前提变了：本产品目前不在 Google Play 分发**（走 GitHub Releases / 官网 APK）。
这一条直接作废了"按需分发"方案 —— **Play Feature Delivery / 动态功能模块只在 Play 渠道可用**，
侧载安装的 App 无法下载模块。剩下的是：

| 方案 | 下载增量 | 安装增量 | 代价 |
|---|---|---|---|
| **单 APK + 压缩 native 库**（推荐） | **+7.3MB** | +20.7MB | 首次启动解压；改一行 `useLegacyPackaging = true` |
| 单 APK + 不压缩（AGP 默认） | +20.7MB | +20.7MB | 启动略快，但用户下载多付 13MB |
| 双包制（基础包 / 增强包） | 基础包不变 | 用户装第二个 APK | 要装两次；商店/用户都会困惑 |
| 换更小的栈 | +6~8MB | 同左 | 丢掉控制面/DERP，等于自己重做 rendezvous |

**只发 `arm64-v8a`（已定案：不支持 32 位）**：三份全打是 62.9MB，而 `x86_64` 只服务模拟器、
`armeabi-v7a` 只服务老旧机型。因此发布包只含一份 `.so`，且**不提供 armv7 变体**。

这条决定的连带影响，实施时必须一起做：

1. **`ndk { abiFilters += "arm64-v8a" }`**，否则依赖里的 32 位 `.so` 仍会被打进包；
2. **商店/下载页如实写"需要 64 位设备"**——32 位设备装了会 `INSTALL_FAILED_NO_MATCHING_ABIS`，
   这不是崩溃，是装不上，用户会以为是包坏了；
3. **README 的安装要求**按产品口径写（不写平台独占措辞，但位数要求可以写）；
4. **测试矩阵**去掉 32 位真机，CI 只构建 arm64。

> 结论：**单 APK、只打 arm64、开 `useLegacyPackaging`**。用户下载只多 7.3MB，
> 这是非 Play 渠道下代价最小的一条；"自选能力不该让所有人多付"这个原则，
> 在没有动态分发能力时只能让步为"尽量少付"。

## 10. 度量与灰度

| 指标 | 看什么 | 红线 |
|---|---|---|
| 加入成功率 | 扫码 → 已加入 | < 80% 说明流程有坑 |
| overlay 使用占比 | 跨网会话里经 overlay 的比例 | — |
| 失败原因分布 | 控制面不可达 / 授权失败 / 连不上对端 | 单一原因 > 40% 要查 |
| 局域网误启动 | 局域网友好场景下 overlay 启动次数 | **必须为 0** |
| 耗电 | 前台服务 + overlay 的 24h 耗电 | 显著高于今天则回退 |
| 链路稳定性 | closeCount | 必须为 0 |

**灰度**：按设备或按账号放量；**回滚用远端功能位**（运维手段），
不是给用户一个开关（AGENTS.md §2.5：产品缺陷不该让用户选）。

## 11. 风险与不做

| 风险 | 影响 | 处置 |
|---|---|---|
| 用户没有账号 | P1 只能服务技术型用户 | 如实写"需要你自己的账号"；P2 补 |
| 条款/分发合规 | P1 可能不能公开发布 | 只做内测；P2 前必须有书面意见（技术文档 §4.4） |
| 包体 +8~12MB | 安装转化 | ABI 拆分；按需下载 native 包 |
| 授权流程复杂 | 加入成功率低 | 三屏流程 + 明确"在浏览器完成"；失败可重入 |
| 与系统 VPN 冲突 | 用户开了公司 VPN | 用户态栈**不占用** VPN 槽位 —— 这是相对"装 Tailscale"的核心优势，验收必须验 |

**明确不做**：跨网屏幕、公网中继转发、连接方式设置项、把 overlay 当卖点写进首屏。

## 12. 一句话

> 私人网络给的是**地址**，不是**接管**：设备之间像局域网一样彼此可见，
> 但广播不跨、信任不降 —— 用户看到的是"换网还连着"，实现守住的是"没有一处可以少验 pin"。
