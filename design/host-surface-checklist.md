# 宿主面人工清单（host surface checklist）

> 这份清单管的是**只有真人坐在真窗口前才能判**的东西：输入法、显示缩放、系统托盘、
> 拖放、深链、多窗口、休眠唤醒。它们全都跨出了 Compose 的边界，落进 AWT / Skiko /
> 窗口管理器 / 输入法框架，CI 里没有可复现的等价物 —— 无头容器没有候选窗，也没有
> 托盘，Layoutlib 渲染截图**根本走不到**这些代码路径。

## 1. 怎么跑

```bash
cd scaffold
JAVA_HOME=/opt/homebrew/opt/openjdk@21 ./gradlew :desktopApp:run
```

进设置窗（托盘菜单 → 设置…，或主窗内的设置入口），顶部有三个分段：
**应用设置 / 桌面 / 输入法自检**。A 节全部在「输入法自检」里做。

> **入口只有托盘菜单一条路。** 设置窗本身只能从系统托盘菜单打开（没有菜单栏、没有
> 快捷键、没有命令行开关）。所以「输入法自检」在没有系统托盘的环境（某些 Linux 窗口
> 管理器、纯 SSH）里**够不到**。这是设置窗整体的既有限制，不是这一页引入的；真要在
> 那种环境跑 A 节，得先给主窗加一个设置入口。

那一页的代码在 `scaffold/composeApp/src/commonMain/kotlin/app/relay/ui/desktop/ImeSmokePane.kt`
（与其它桌面 Compose 界面同处 `ui/desktop`），它自己的布局有截图门禁兜底
（`desk-ime-smoke` / `desk-ime-smoke-dark` 两帧，尺寸取真实设置窗 720×560）——
**那只保证仪器没坏，不保证输入法行为**：无头渲染里没有输入法，渲出来是空框 + 空观测台。

### 证据怎么记

每条结果写进 `scaffold/design/runtime-evidence/host-<编号>-<平台>.txt`，格式与其它
真机证据一致（前三行是环境，其后是逐条 `$ 做了什么` + 观察到的原话/数字）：

```
# 宿主面人工验收证据（macOS 15.x, MacBook Pro M?, 内置屏 3024×1964 @2x）
# 应用: 捎话桌面端, HEAD <sha>
# 取证时间: <ISO8601>
# 输入法: 系统拼音（macOS 自带）, 版本 <…>
```

**截图不进仓库**（与真机验收同一条规矩）：图放 `/tmp`，txt 里写路径与一句话结论。

## 2. A 节：输入法六项

这一节用「输入法自检」页。它把 Compose 真正持有的三样东西显示出来 ——
`TextFieldValue.text`、`.composition`、`.selection` —— 于是"感觉不对"能落成可复述的事实。

页上有**三个**输入框，不是凑数：产品里两种输入原语都在用，桥接层对它们的处理可能不同。

| 框 | 对应产品里的谁 |
| --- | --- |
| 单行（`OutlinedTextField`） | 设置页、节点页、桌面输入栏 |
| 多行（`OutlinedTextField`） | 设置页的多行字段；换行与 `singleLine` 在 IME 上走不同分支 |
| 无边框（`BasicTextField`） | 聊天输入栏 `ui/components/MessageComposer.kt` |

观测台只显示**当前焦点所在**那个框的记账（点进哪个框，读的就是哪个框）。

### A1 候选窗跟随光标

- **场景**：单行框里把光标分别放到①行首 ②行尾 ③中间（方向键与鼠标点击各做一次）；
  再在多行框第二行做一次；再把页面滚到下方、在一个靠近窗口底部的框里做一次。
- **看什么**：系统候选窗是否**紧贴光标**，而不是贴在输入框左上角、也不是停在上一处。
- **通过**：五种位置候选窗都跟着光标。
- **不通过**：候选窗固定不动 / 漂移 / 出现在屏幕另一角。
- **仪器的边界**：观测台读不到候选窗坐标 —— 这一项**只能人眼**。观测台的「选区」行
  只能证明光标确实动了（`12..12` → `0..0`），不能证明候选窗跟了。

### A2 内联预编辑

- **场景**：中文输入法打 `nihao`，**不要选词**。
- **看什么**：(a) 框内是否**内联**显示 `nihao`（而不是只出现在候选窗里）；
  (b) 观测台「组合区间」是否变成非空（形如 `5..10（正在预编辑）`），且「当前文本」里
  也确实有那串拼音。
- **通过**：(a)(b) 同时成立。
- **不通过**：框内不显示拼音（预编辑只活在候选窗里）—— 这是 Compose Desktop 的典型缺陷；
  或「组合区间」显示 `无（未在预编辑）`（说明预编辑根本没到 Compose 层）。
- **三个框都要做**。

### A3 上屏进回调

- **场景**：承接 A2 的状态，从候选窗选「你好」。
- **看什么**：三条同时发生 ——「上屏回调次数」+1；「最后一次上屏后的文本」变成 `你好`；
  「组合区间」回到 `无（未在预编辑）`。
- **通过**：三条都成立。
- **不通过**：「次数」不动 —— 文本进了框却没进 `onValueChange`。这一条**最要命**：
  产品里的发送按钮读的就是回调里的值，回调不来 = 发出去的是空消息。
- **三个框都要做**。

### A4 中英切换

- **场景**：切到英文（macOS 默认 Caps Lock 或 Ctrl+Space），打 `abc`；切回中文，打 `你好`。
- **看什么**：两次都让「上屏回调次数」+1；`abc` 那次「组合区间」**全程为空**，
  `你好` 那次中途非空。
- **通过**：两种输入都进回调，且组合区间的有无与当前语言一致。
- **不通过**：切换后第一次输入丢失；或切回中文后卡在预编辑态不落定。

### A5 退格删拼音

- **场景**：打 `nihao` 不选词，连按四次退格。
- **看什么**：「当前文本」逐次变短，且「组合区间」的区间**同步缩短**
  （不是只缩文本、区间不动）。退到底后回到 `无（未在预编辑）` 且文本为空。
- **通过**：区间与文本一起缩；退到底干净归零。
- **不通过**：文本缩了区间没缩（后续选词会插到错位置）；或一次退格清空整串拼音
  而不是逐字删。
- **三个框都要做**。

### A6 失焦 commit 还是丢弃

- **场景**：打 `nihao` 不选词，点页面上的「移走焦点」按钮。
- **看什么**：观测台「失焦前 → 失焦后」那一行。三种结果，各有各的说法：

  | 显示 | 含义 |
  | --- | --- |
  | `nihao → nihao` | 预编辑被**提交**（留在文本里） |
  | `nihao → （空）` | 预编辑被**丢弃**（但走了 `onValueChange`） |
  | `nihao → 失焦后没有回调（预编辑被丢掉，且没进 onValueChange）` | **静默丢弃** |

- **通过**：判据**不是"必须提交"**，而是**必须确定**——三种里任何一种都能接受，但必须
  能在报告里写清是哪一种，且产品侧行为与之一致（聊天输入栏失焦时不该悄悄丢字）。
- **不通过**：结果每次都不同（不可复现）。
- **为什么要专门等 600ms**：失焦后不再有回调时，那一行不能永远停在"等失焦后的值"——
  那是把"没有"显示成"还没来"。等一小会儿就收掉待定期，如实变成第三种。

## 3. B 节：其余宿主面

### B1 HiDPI / 显示缩放

- **场景**：系统显示缩放切到 100%，把窗口拖到 1100×720 逻辑像素，记下判定档位；
  再切到 200%（或外接一台不同 DPI 的显示器）重启应用，把窗口物理尺寸调成同样大小。
- **看什么**：断点判定读的是 `LocalWindowInfo.containerSize` + `LocalDensity`
  （`ui/desktop/DesktopLayout.kt` 的 `rememberDesktopWindowSizeDp`），所以判据必须是
  **逻辑 dp** 而不是物理像素：200% 下 1100×720 **物理**窗口应仍判为 Compact
  （因为它只有 550×360 逻辑像素），而 1100×720 **逻辑**窗口在两种缩放下都应是 Expanded。
- **通过**：同一逻辑尺寸在两种缩放下得到同一档；文字不糊；1dp 发丝线不消失。
- **不通过**：200% 下窗口档位变了（说明哪里用了物理像素）；或发丝线整条不见。

### B2 系统托盘

- **场景**：点主窗关闭按钮（不是退出）。
- **看什么**：进程是否还在；托盘图标是否出现；托盘菜单是否显示未读数 / 新文件数 /
  Agent 运行态。
- **通过**：关窗不杀进程；菜单条目与 `DesktopTrayMenu` 模型一致。
- **不通过**：关窗即退出；托盘图标空白；菜单里出现永远点不动的条目。

### B3 拖放

- **场景**：从 Finder 拖一个文件进会话窗口；再拖一个 `.sha256` 旁车文件；再从浏览器
  拖一段**文字**。
- **看什么**：文件是否进传输；`.sha256` 是否被忽略（`CHECKSUM_SUFFIX`）；非文件拖动
  是否既不亮层也不崩。
- **通过**：三件事分别如上。
- **不通过**：拖文字时抛异常 —— AWT 的异常会顺着事件队列带塌后续所有 UI 事件，
  这是这条最要紧的失败形态。

### B4 深链

- **场景**：① 应用**已运行**时，在浏览器地址栏打开 `relay://<host>:<port>`；
  ② 应用**未运行**时，双击一个 `.relaymsg` 文件。
- **看什么**：是否切到节点视图并预填地址。
- **通过**：两条路都通。
- **不通过**：只有已运行的那条通 —— 冷启动走命令行参数（`main(args)`）、已运行走系统
  回调（`installDesktopOpenHandlers`），是**两条独立的代码路径**，只测一条等于没测。
- **另需**：确认 `relay://` 优先于后缀判断（`relay://x.relaymsg` 这类怪路径不该被两种
  规则各解释一次）。

### B5 多窗口

- **场景**：打开两个 peer 独立窗口，各自滚动到不同位置，然后切主题。
- **看什么**：滚动位置是否各自独立；主题是否同时生效。
- **通过**：独立滚动 + 同时换肤。
- **不通过**：两个窗口共享滚动状态；或设置窗不跟随主题（设置窗**不自己套 `AppTheme`**，
  它靠窗口层包，套第二层会退回系统主题）。

### B6 休眠唤醒

- **场景**：合盖 / 睡眠 5 分钟以上，唤醒。
- **看什么**：对端是否在离线判定窗口内重新出现；是否需要手动重启应用。
- **通过**：唤醒后无需重启自动恢复在线（心跳与广播自愈）。
- **不通过**：一直显示离线直到重启 —— 那说明唤醒后定时器没恢复。

### B7 截图（原型 d-capture / d-capture-tools 两屏）

> 为什么在这里而不是截图门禁：`CaptureOverlayView` 在 **desktopApp** 模块，androidApp
> 的截图源集看不见它；而且它挂 `undecorated + alwaysOnTop` 的**全屏覆盖窗**
> （`DesktopWindow.kt:376-396`，bounds = 刚抓到的整屏），Layoutlib 既加载不了这个
> 窗口类、也没有"刚抓的那一帧"可喂。这两屏只能真窗验。

- **场景**：会话工具栏「截图」按钮（`DesktopComposer.kt:222`，Crop 图标）或快捷键
  **⌘⇧A**。⚠️ 菜单栏 Edit 里那条同名项只是跳回会话视图的占位，**不是**触发器 ——
  从菜单进会误判"没反应"。
- **看什么（d-capture 帧）**：全屏冻结画面出现、框选提示在；拖拽有虚线选区；
  未选定前工具条**不**出现。
- **看什么（d-capture-tools 帧）**：选区确定后工具条出现，五个工具
  （`Select / Rect / Arrow / Text / Mosaic`，`CaptureOverlayView.kt:92`）逐个可用；
  按钮文案 = 「取消 (Esc)」「复制到剪贴板」「发送到聊天 (Enter)」；Text 工具在选区内
  点击出输入（`:213`）；撤销能回退标注。
- **通过**：Esc 后 overlay 消失且主窗可交互；Enter 后图片以气泡进**当前**会话；
  复制后粘贴板里是 PNG。
- **不通过**（按要紧程度）：
  1. macOS 未授予屏幕录制权限时白屏 / 只拿到壁纸 —— 必须给可行动的提示，
     静默截一张错的是本节最要紧的失败形态；
  2. HiDPI（@2x）下选区与画面错位 —— overlay 用的是逻辑像素，raw 没换算就会错；
  3. 多显示器只盖主屏、或抓到另一块屏。

## 5. 已经在兜底的单测，以及它们为什么不够

`scaffold/desktopApp/src/test/kotlin/app/relay/desktop/`：

| 文件 | 兜住了什么 | 为什么不够 |
| --- | --- | --- |
| `DesktopTrayMenuTest.kt` | 托盘菜单的**模型**：未读优先于新文件、零消息不崩、每个可点条目都带动作、Agent 运行态如实反映 | 只验"该显示什么"，不验 AWT 是否真把图标放进系统托盘（无头环境没有托盘） |
| `DesktopDeepLinkTest.kt` | URI 解析、`relay://` 与后缀的优先级 | 不验冷启动参数路径与系统回调路径**都**接上了 |
| `DesktopDragOutTest.kt` | 拖出时的文件与 MIME 组装 | 不验**拖入**（`DropTarget` 是 AWT 事件，无头跑不了） |
| `DesktopPeerWindowTest.kt` | 多窗口的模型（哪个 peer、标题） | 不验两个真实窗口的滚动状态是否独立 |
| `DesktopBackgroundTest.kt` | 后台/托盘态下的行为模型 | 不验真实关窗按钮是否真的只收进托盘 |
| `DesktopReceivedFilesTest.kt` | "收到的文件"计数口径（只数已完成的入站文件） | 不验托盘里点它能不能打开目录 |

**输入法一项都没有单测**，而且**不可能有**：`TextFieldValue.composition` 的内容由平台
输入法框架决定，无头环境里没有输入法。所以 A 节只能人工，没有第二条路。
