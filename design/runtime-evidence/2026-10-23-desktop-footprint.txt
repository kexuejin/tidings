4. 「进程退出」这条路径的实测证据
------------------------------------------------------------------
为什么要测这条：进程在采样中途消失时，最容易出现的坏量具行为是**照常输出空值或上一帧
的残影**，让报告看起来「有数」。本脚本必须在发现进程消失的当下停止、明确报「进程已退出」、
并以非 0 退出码结束（本脚本用 6），而不是把空字符串当读数写进汇总。

复现方法（完整命令见下）：起唯一实例 → 用 --pid 附着 → 采样中途把它 kill 掉。
  /Applications/Tidings.app/Contents/MacOS/Tidings --background &     # 唯一实例
  ( sleep 8; kill -TERM <pid> ) &                                 # 让它在采样中途死掉
  tools/measure-desktop-footprint.sh --pid <pid> --samples 4 --interval 5 ...
实测退出码：6（脚本约定：采样过程中目标进程消失）

5. 读数方差：为什么必须连负载一起报
------------------------------------------------------------------
同一份产物、同一份数据、同一组 JVM 参数，Physical footprint 不是常数。本次与同批实测：
  * 本证据第 3 节（load ≈ 3.7）：586.5M / 516.7M / 511.4M，组内跨度 75.1M
  * 同机并发构建（Gradle / jpackage）在跑时，同一产物单点读数见过 422M–620M 的跨度
    （并发期间一组 3 样本实测 488.3M / 427.2M / 422.0M；另一组 611.3M / 542.3M / 537.9M）
  * 差值主要落在 VM_ALLOCATE（进程内 GPU/图形映射）与 IOSurface 区域上；
    GC 堆 committed 始终是 371.3M。也就是说这不是脚本量错了，是这块内存在动。

结论：
  (a) 报读数必须同时给出样本数、间隔、系统负载与产物指纹，否则无法复现；
  (b) 不要拿两次不同负载下的单点值互相比较，也不要从一组样本里挑最小的那个当结论。

坑 3 · vmmap 不可用
  本次取证没有触发（vmmap 全程可用，汇总里「vmmap 不可用次数 : 0」）。
  代码行为：vmmap 非 0 退出时只记一行，footprint 记 n/a，继续采 RSS 与堆，
  让整次测量仍然可用。这条路径未在本机实证，所以这里只写行为、不写读数。

另修掉的两个真实边角（都已实测）：
  * 僵尸进程：ps -p 对 Z 状态进程仍然成功，但读数是上一瞬间的残影。判活改为排除 Z 状态；
    读不到 RSS 时给 n/a 而不是 0。
  * SIGPIPE：被 head / grep -m1 之类下游关掉 stdout 时 bash 会收到 SIGPIPE 直接退出，
    EXIT 陷阱不跑 ⇒ 自己拉起的进程会残留。现在显式接住 PIPE，并让收尾先清理临时文件
    再 emit；实测「管道截断之后」实例数与临时文件都回到 0。

8. 复用到本机其它 KMP/CMP 产品
------------------------------------------------------------------
脚本不写死本机个人路径（没有 /Users/ 前缀、没有硬编码 JDK 路径）：JDK 按
--jdk → JAVA_HOME → PATH → /opt/homebrew/opt/openjdk* 依次查找；临时日志走 ${TMPDIR:-/tmp}。
换产品只需改两处：--app 指向那个 .app（或 jar / 裸可执行文件），--out 指向该产品的证据文件。
自动拉起模式（--app）保留可用；本次取证为了不污染同机其它会话的读数，特意改用
--pid 附着 + 只起一个实例，并在测完立即收尾。
