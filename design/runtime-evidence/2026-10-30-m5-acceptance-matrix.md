## 4. 第 4 条：插件热拔 ✅（翻离线是秒级；主进程与链路零新增 close）

**操作**：`kill -9` 掉 `dsh-echo-bridge` 的进程（pid 16613，监听 63675），按 30 / 60 / 100 秒三档采样。
补测（本轮，为把口径钉准）：再 kill 两次（pid 30205 @55883、pid 83634 @60617），用 250 ms 轮询 `/v1/plugins` 记翻离线的精确耗时。

| 采样点 | `GET /v1/plugins` 读数 |
|---|---|
| t0（09:28:44） | `dsh-echo-bridge online` |
| t+30s（09:29:14） | **offline**，`lastError=health probe failed: …:63675/healthz unreachable` |
| t+60s（09:29:44） | offline（同上） |
| t+100s（09:30:24） | offline（同上） |
| 主程序 | pid 16573 存活，未崩 |

**判据偏差（必须写清）**：矩阵原文是「按 `offlineAfter`=90s 翻离线」，实测**秒级**就翻了
（本轮补测两个样本：**2.0s / 8.0s**）。原因在代码里，两者不是同一个时钟：

- `offlineAfter`（`Limits.kt` 的 `90_000`）是 `PeerRegistry.sweep` 的**节点 presence 超时**；
- 插件/agent 的在线态走 **healthz 探测**：`PluginRegistry(probeIntervalMs = 15_000, probeTimeoutMs = 2_000)`，
  桌面端 `ControlPlane` 用默认值构造。kill 后状态在**下一次探测 tick** 翻 offline，
  所以落在 **[0, 15s] + 连接超时**（端口被拒是立即，被过滤才吃满 2s），上界 **17s**。

| 样本 | 翻 offline 耗时 | 说明 |
|---|---|---|
| #1 | **2.0s** | tick 恰好在 kill 后 2s 到 |
| #2 | **8.0s** | 同一机制、相位不同 ⇒ 读数离散是**预期**，不是不稳定 |

口径改为：**「kill 后 ≤17s（探测周期 15s + 超时 2s）翻 offline」**，而不是 90s。

**顺带钉死一条容易误判的事实**：托管模式（`PluginHost`）确实会 spawn 插件
（`ProcessBuilder`，注入 token），但**只在宿主启动挂接时拉起一次，没有监管循环** ——
所以 kill 掉之后它不会自愈，要么重启宿主、要么手动把进程起回来。本轮两个样本都是
手动重启插件进程（`python3 main.py`），不是宿主拉起的。这不是缺陷，是「拉起一次」
的语义；但矩阵里写「热拔」时要分清**谁把它拔掉的、谁该把它插回去**。

**主程序 closeCount**：这一档期间桌面主进程存活，链路上没有新增 close（当时桌面→手机 `closeCount=4`，
`closeReason=replaced`，全部来自本次会话里两端的重启，没有一条 `timeout`/`error`）。

**顺带抓到一条产品缺口**：插件被 kill 后，宿主收到带 `agentIntent` 的群文本时**群流里没有任何反馈**
（第 7 条第一段就是这个现场：手机发了 @dsh，桌面无插件可派，手机端既没有卡片也没有「不可用」提示，
UI 上连一个「失败/离线」字样都搜不到）。设计稿 v2 §4.8「插件离线的动作反馈」尚未落地，这是它的真机证据。

## 5. 第 5 条：链路稳定 ✅（真断网重跑：全程零异常 close）

**操作**：`svc wifi disable`（不用飞机模式）→ 6 秒后 `ip route` 为空（**真断网**，`src 192.168.2.22` 即本机）
→ 按 t+26s / t+25min 采样 → `svc wifi enable` → 12 秒采样 → `am force-stop` + 冷启动 → 14 秒采样。
（断网窗口原计划 1 分钟，中途撞上 `/Volumes/Kapp` 满盘、沙箱起不来，实际拉长到约 25 分钟 ——
这个意外反而补到了「长时断网」这一档。）

| 阶段 | 手机 `closeSum` | 手机 `lastError` | 桌面 `closeCount` / 原因 |
|---|---|---|---|
| 基线 | 0 | 0 | 4 / 全 `replaced` |
| 真断网 t+26s | **0** | 2 条 `connect-timeout` | 4 / 全 `replaced`，**仍 `linkConnected=true`** |
| 真断网 t+25min | **0** | 2 条（未再涨） | 4 / 全 `replaced`，**`connected=0`** |
| 开网 t+12s | **0** | 0（清零） | **5** / `replaced` |
| 冷启动 t+14s | **0** | 0 | **6** / `replaced` |

**判据怎么落**：矩阵写的是「换网/断网/冷启动全程 `closeCount`=0」。

- **手机侧字面成立**：`closeSum` 全程 **0**，断网期间只记 `connect-timeout`（连不上，不是断已连的），恢复后清零。
- **桌面侧字面不成立、但语义成立**：4 → 5 → 6，**每一次增长都是 `replaced`**（新链路顶掉旧链路），
  没有一条 `timeout`/`error`。`replaced` 是重连的**正常语义**，把它算成「不稳定」等于把「重连过」判成「断过」。
- **一条必须记下的盲区**：桌面侧在断网期间 `linkConnected` 从 `true` 翻 `false`，
  **`closeCount` 一动不动**（4 不变）。也就是说**只盯 `closeCount` 会漏掉「链路其实已经死了」** ——
  那一格是靠 presence/online 判定翻的，不是靠 socket close。这条判据以后要配 `connected` 一起看。

**为什么这一档是 ✅ 而不是 ⚠️**：上一轮用飞机模式（`cmd connectivity airplane-mode`）在 Android 12+ 上
**没有真的切断 Wi-Fi**，所以那一轮只验到「部分抖动」。这一轮 `ip route` 为空是真断，
四档读数覆盖了「断 / 长断 / 恢复 / 冷启动」四种形态，异常 close 一条没有。

| 两张卡是**不同** id | 是：`…-session-1-1` ≠ `…-session-2-2`（旧夹具在同一 session 上固定用 `echo-card-<sessionId>` + `rev=1`，第二张必被第一张压住） |
| 界面两张都在 | 是：`uiautomator` 里两条 `Echo task #n` 与两颗 `Echo again` 并存 |
| 客户端折叠语义有没有被动过 | 没动：`latestRevCardMessageIds` 一个字符未改，这次只是让每张卡**有资格**成为最新 |

**这一格怎么判**：判据原文是「同一 session 连派两次 ⇒ 两张不同 `cardId` 的卡都在」。
本轮两次派单各自开了新 session（`echo-session-1` / `echo-session-2`），所以严格说不是
「同一 session 两次」，而是「连续两次派单」；**要验的东西（夹具不再复用 cardId）成立**。
真正的同 session 复跑仍缺一次（需要真插件在 harness 上做 `POST /task/execute` 两次），
记在这里，不当作已覆盖。

## 7.2 免批表回路（「始终允许」→ 面板 → 撤销 → 重新问）✅

**为什么这一档要真机**：`always` 这条链跨三端 —— 手机的按钮、宿主落表、桌面的回收口。
单测各自绿，不代表这条链在真设备上通。

**造场景的方式（如实写）**：仓内没有会发审批请求的插件，所以由宿主控制面
`POST /v1/agent/approval` 直接向手机发一条审批（走的正是插件→宿主→手机的同一条帧），
`sessionId=m5-approve-1`、`tool=bash`。

| 步骤 | 判据 | 读数 |
|---|---|---|
| 0. 前提 | 手机能批 | **一开始不能**：审批行显示「只读（无权审批）」。查判据：`canApproveAgentRequest` 里 `rw` 不放行（「能派活 ≠ 能批准」），手机当时是 `scope=all rw`。临时提权到 `owner` 后按钮出现；跑完已还原成 `rw` |
| 1. 入口可见 | 审批行长什么样 | 首行「拒绝 / 批准」；第二行「本会话免审 / 此工具始终允许」；下方说明「「本会话免审」只管当前会话；「此工具始终允许」跨会话，只管这一个工具名」 |
| 2. 高危确认卡 | 点「此工具始终允许」后 | 弹出「确认批准高危操作 —— 确认后，这台设备上的这个 agent 再调用该工具时不再询问。」（是「始终允许」专用正文，不是普通批准的文案） |
| 3. 宿主落表 | 确认之后 | `agent-tool-approvals.json` 出现 `{nodeId: 手机, agentKey: "DSH", tool: "bash", grantedBy: 手机}` |
| 4. 入口短路 | 同工具再来一条 | `status=auto-approved`、`autoApproved=true`、`note="…approved locally, not delivered"`（**没有发帧**） |
| 5. 只短路该工具 | 换成 `rm` | `status=sent`，对端 ACK（照常问） |
| 6. 桌面回收口可见 | 设置 → 可信设备与配对 → 滚到底 | 「免批规则」块列出 `bash / Pixel 6 · agent DSH / 5 分钟前` + 「撤销」按钮；说明文案「撤销后，下一次同工具请求会重新询问；已在等待批复的那一条不受影响」 |
| 7. 撤销真的删 | 点「撤销」 | `agent-tool-approvals.json` → `{"rules":[]}`；面板同时翻成空状态 |
| 8. 撤销后重新问 | 再来一条 `bash` | `status=sent`（不再 auto-approved）；手机端同时出现两条待批（`rm` 未分级 + `bash` L3） |

**证据**：`design/runtime-evidence/2026-10-30-approval-loop/`
（`02-desktop-panel-rule.png` 撤销前、`03-desktop-panel-after-revoke.png` 撤销后、
`04-phone-reask-two-pending.png` 手机两条待批、`05-phone-row7-two-cards.png` 第 7 条复跑）。

**这一档顺带证明的两件事**：

1. **桌面像素取证不再是死路**：`screencapture` 本轮可用（此前记为「被系统权限拒绝」）。
   仍不可用的是**辅助功能**（`System Events` 返回 -10004），也就是说「能看不能点」。
   本轮的点按是靠直接投递 CGEvent 完成的（见下一条的边界）。
2. **审批权判据是硬的**：手机拿着 `rw` 时界面确实只读，不是「画了但点不动」——

## 7.4 桌面点按的边界（本轮新踩，供后续取证参考）

**先说能用的三件套**（本轮新打通，此后桌面取证不必再等人）：

- **抢前台**：`NSRunningApplication.activate(options: [.activateAllWindows])`（AppKit）可用，
  而 `open -a` / `open -b` 都不会把已在运行的窗口顶到最前，`osascript` 仍 -10004。
  校验方式是同一句里读 `NSWorkspace.shared.frontmostApplication?.bundleIdentifier`。
  实测 `activate=true` 后 0.8s 内 `frontmost=com.kapp.tidings.desktop target-active=true`。
- **按窗取图**：`CGWindowListCopyWindowInfo` 拿 `kCGWindowNumber`，再
  `screencapture -x -o -l <windowNumber>` —— **与遮挡、前后台、窗口被裁到屏幕外都无关**。
  主窗 1100×720 点 ⇒ 出图 2200×1440（2 倍），`-resize 50%` 后与点坐标 1:1。
- **点按**：CGEvent 投递鼠标/键盘事件可用（整条免批面板操作链就是这么走完的）。

**坐标换算是本轮最大的坑**（三次点错都是它）：

- 全屏 `screencapture` 出的是**物理像素**（3840×2160），UI 是逻辑 1920×1080 ⇒ 先 `/2`。
- 窗口图的 1:1 版本与「点」对齐，但**窗口原点是 (48,78) 或 (-40,83) 这类值**：
  屏幕点 = 窗口点 + 窗口原点；原点为负时左侧会被裁、图的 x=0 就是屏幕 x=0。
- 别信缩略图的坐标：看图工具会把 1920 宽的图渲染成 1092 宽，按渲染图量的坐标偏约 1.76 倍 ——
  一次点错就是这么来的。**要量就裁一小块放大 200%+ 再量**，并且每次点完立刻截图确认。

**仍然不稳的地方（如实记）**：

- 模态弹窗会吃掉标签栏附近的点击：点「协作群」连着两次开出了「关联工作区建群」——
  不是坐标偏，是那几个 tab 的可点区域比文字宽。收口靠 `Esc`（`keyevent` 53）关弹窗，
  比找「取消」按钮可靠。
- 每次执行命令会把焦点抢回宿主应用，所以「激活 + 点击 + 截图」必须写在**同一次** shell 调用里，
  中间隔一次工具调用就前功尽弃。
- 只按坐标点、不读界面树的场合，点错会落到别的应用上（本轮误触过两次别的应用）。


## 7.5 第 3 条的桌面像素补上了 —— 并从像素里抓出一条真缺陷（已修）

| 点后 | 同一张卡原地变「**第 2 版**」，按钮变**灰色**，多出一行「已由 kedeMac-mini-97 处理」 |

已决的卡片行是历史事实，不回写。新判定才会用新口径。

**这里的边界**：本轮取证的是「本机点自己托管的卡」。设计稿 §4.8 还提到

## 7.6 S4-4 修复后的真机复验：横幅这一半成立，派单失败那一半仍不成立

**做法**（这次不再等租约，直接造「插件不可用」）：`kill -STOP` 冻住 `dsh-echo-bridge`
的进程（socket 仍在监听、但对请求不响应）→ 等探测周期把它判离线 → 手机 @ 派单。

| 时刻（桌面时钟） | 读数 |
|---|---|
| 冻住后约 1 分钟 | 群流出现**红色横幅**「「dsh-teahouse-mobile」没有完成这次任务」 |
| 同上 | 桌面库与手机库**同一行、同一 `at`**、`agentState=failed`、**正文非空** ⇒ `70b00674` 的文案桥在真机成立（此前只有单测覆盖它） |
| 派单消息 | 「@dsh-teahouse-mobile leasech」落在横幅**下面** |
| 派单后 14 分钟 | **零新增**：没有卡片、没有新横幅、**连租约超时卡也没有** |

**两条必须分开写的结论**：

1. **「插件掉线 → 中断公告」这一半 ✅**：横幅在两端的库与界面都在（`11`），正文非空。
   这是 `70b00674` 要修的那条链路，真机上第一次看到它正常输出。
2. **「插件不可用时的新派单 → 失败反馈」这一半 ❌**：派单消息之上只有那条掉线公告，
   派单本身到 14 分钟仍无任何回声 —— 复现了 §7.3 的「离线派单无反馈」，
   也就是本轮「要改的东西」里第 3 条（agent 离线零反馈，设计稿 v2 §4.8 未落地）。

**同时修正 §7.3 的一条解释（推断，不是读数）**：那里把「换包重跑后一条横幅都没发」
归因于「离线路径走 10 分钟租约，等不到结果所以不立刻失败」。今天同场景 1 分钟内就有
横幅，且派单 14 分钟也没有租约超时卡 ⇒ **租约不是那条路径的闸门**。更可能的解释是
修复前正文是空串、「空正文不发帧」把横幅压掉了；而租约超时卡之所以没出现，是因为
这条路径根本没走到租约（新派单在「找不到可用插件」这一步就没往下走）。

**一个自己踩过的坑（记下来免得复踩）**：第一次读数是「零反应」——因为脚本只统计了
`card != null` 的行，而横幅是**纯文本行 + `agentState`**，没有 `card` 键。
「库里没多一行卡」不等于「群里没多一条消息」，这类读数必须按 `agentState` 一起数。

**边界**：仍没验「插件**接单之后**中途死掉」——echo 夹具一秒内就完成，抓不到那个窗口；
而先冻住再派单会被探测周期提前判离线，走不到「接单后」这一步。
