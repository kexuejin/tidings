## 1. 结论

链路在 0.9.0 上**通了**，而且这一轮把「通了但用户看不见」的三处缺口逐个钉死了：

| # | 现象 | 根因 | 处置 | 真机复验 |
|---|---|---|---|---|
| P1 | 产物 `patch.diff` 到不了手机，卡上「传输失败：网络连接中断」 | `fch1` 为压 caps 到 16 项已停止广播，协商仍要求对端声明 `fch1` ⇒ 新端之间恒 false，回退到已退役的 legacy 17879 | `FileChannelNegotiation` 认「对端已用信道推过来」为能力证据 | ✅ 见 §4 |

## 3. D-NEW-1：滞留卡如实翻面（含新根因与修复）

**现场**：宿主 14:07 重启后，手机上仍挂着 11-02 的「进行中 · 立即执行/取消」旧卡。

**修复前（13:53，点「合并此补丁」）**：宿主判失败并如实打出

```
[RELAY-INVOKE] patch merge FAILED (card chain-tmvz6b7y3): no sandbox patch recorded for card chain-tmvz6b7y3
```

但卡面停在「待合并」。对两端库取值发现真因：

```
手机 messages.log
20002  ts=1793685204072  rev=6  state=review_ready  title=list files
20003  ts=1793685204072  rev=6  state=blocked       title=没能合并这次改动
```

两张卡同 `cardId`、同毫秒、**同 rev 6**。手机端只认严格递增 rev，后到的诚实翻面被当旧帧丢弃。
rev 由 `broadcastDecision`（判定帧，「已由…处理」）与终态翻面帧**并发**从同一个 `_state` 快照算出。

**修复**（`RelayControllerAgentInvokeComponent.kt`）：
1. `cardBroadcastMutex` 把「读既有 rev → 算新 rev → 落库」变成原子段落；
2. 有槽位时 `finalRev = max(passedRev, existingRev + 1)`，任何两帧不可能同号；
3. `broadcastDecision` 移到 `onHostCardAction` **之前**，保证终态翻面永远拿更大的 rev。
   回归钉子：`BoardCardLocalPersistenceTest.theDecisionFrameAndTheTerminalFlipNeverShareARev`（1→2→3，3 例全绿）。

**修复后真机（14:00，点旧点将卡「立即执行」）**：

```
宿主：[RELAY-INVOKE] start-task had nothing to start (card chain-tmvz63zog)
      [RELAY-INVOKE] stale card flipped to aborted (card chain-tmvz63zog)
手机：工单任务 / 已停止 / rename app to demo / 该工单已结束或宿主已重启，此操作未生效 / 进展 0%
```

按钮已摘，横幅如实，不再「点了有反应但什么都没发生」。**D-NEW-1 通过。**

## 5. D-NEW-2：活跃期滚动与「停止」按钮

- **滚动**：工单「进行中」期间连续 swipe，列表内容从 23 项变 26 项、翻到更早的卡，「回到最新」可一键回底 ⇒ 原症状**不再复现**（reverseLayout 重构生效）。
- **「停止」按钮（P3）**：修复前工单卡（`chain-*`）在 working 态**整卡没有任何动作**（只有 `进展 40%`）——
  `StageChain.cardOf` 只写 `options`，`abort-task` 仅由 `SandboxedCliDriver.runningCardJson` 发给 `diff-*` 卡。
  「卡底部停止按钮不可达」的真实形态是**按钮不存在**。

  **修法两层**：
  1. `StageChain.cardOf` 在 `state == "working"` 时补 `actions=[{actionId:"abort-task"}]`（文案由客户端
     `SYSTEM_ACTION_ABORT_TASK` 本地化成「停止」）。只给 working：proposed 有「立即执行/取消」，
     blocked 在等人给方向，终态更不该出现「停止」。钉子 `aWorkingTicketCardOffersStopAndNothingElseDoes`。
  2. 新增 `DesktopWorkerOrchestrator.abortByCard`：与群里打 `stop`（`abortIfRequested`）**同一套收尾**
     （定态 aborted、移出活跃表、补「已停止」卡、取消工单协程）。宿主 `abort-task` 分支优先走它。
     不复用 `abortRunningSandboxes` 的原因：那条只摘进程，CLI 以非零码退出后自愈会把它当「本轮失败」
     再跑两轮 —— 用户按了「停止」，等来的是又跑两轮加一张受阻卡。

  **真机（14:25 派单 `add jsdoc to forecast.js`，8s 后点卡上「停止」）**：

  ```
  宿主：[RELAY-INVOKE] abort by card action e4bd7b99-… (card chain-tmw0b0h29), ticket closed as aborted
        [sandbox] task t-1-2e3a4349 teardown (timedOut=false): killed 2/2 pid(s) in 57ms
  手机：工单任务 / 已停止 / add jsdoc to forecast.js / Aborted by user request / 进展 0%（按钮已摘）
  ```

  进程树 57ms 摘净、无后续自愈轮次。**P3 收口。**

## 6. 阶段 C：自愈与验收门（P4）

**(a) 修前：产物不合格根本不会触发自愈。**
在 `~/weather-relay` 注入 `test/zz-injected-failure.test.js`（`npm test` 实测 87 pass / **1 fail**），
派单 `document temperature.js`。第 2 轮的 patch **只改 `src/utils/temperature.js`**、`grep zz-injected` = 0，
工单照样走到**待合并**，红灯被原样带进工作区。根因：判据只有
`if (status == "finished" && patchPath != null)`（`DesktopWorkerOrchestrator.kt:1356`）——
**只看有没有补丁，不跑验收**。卡上那根「自愈验证」棒显示的是 CLI 自己跑测试的**自述**。

**(b) 修法：验收门 `TicketVerification`。**
在一份**临时 worktree**（基线 + 本轮补丁）里跑仓库自己的测试：

- 基线取 `MergeBaseRef.baseFor(repo)`，再 `git apply` 本轮 patch —— 与用户点合并会得到的
  是同一份结果；
- 判定：退出码非 0 ⇒ 返回 `Failure(原因含退出码与输出尾部)`，自愈循环把它当本轮失败，
  下一轮提示词变成「Previous attempt failed: verification failed: npm test … ensure npm test passes」；
- **刻意不跳过两件事**：① 不调 `DesktopPatchMerge.apply`（它会推进滚动基线，那只能发生在
  用户真点合并时）；② 跑不起来（无 test 脚本 / 命令不在 PATH / worktree 建不出来）一律**跳过**
  并打日志 —— 环境问题不许判成产物不合格（PATH 缺 node 那次的教训）；
- 宿主仓零变化：临时 worktree 用完即删。

**(c) 真机复验（15:14 派单，同一个注入现场）**：

```
[sandbox] harvest t-1-71af9cc2: +75 -6 in 1 file(s), patch=5843 B
[verify] FAILED exit=1 (npm test --silent)
[sandbox] harvest t-2-e39ca2c9: +63 -5 in 1 file(s), patch=5324 B
[verify] FAILED exit=1 (npm test --silent)
[sandbox] harvest t-3-8bb1ce61: +0 -5 in 1 file(s), patch=425 B
[verify] passed in 418ms (npm test --silent)
```

第 3 轮那份 425 B 的补丁正是**删掉那个恒失败的测试**（prompt 里带着上一轮的失败原因），
验收随之转绿、工单才翻「待合并」。**「产物不合格 → 反思重跑」这条链路第一次在真机上成立。**

> 如实说明两点：① 这一单的「修法」是删掉注入的诱饵测试 —— 机制（门 + 带原因进下一轮）验到了，
> 「修真实缺陷」的质量仍取决于模型；② 验收基线是**滚动基线快照**，用户在仓库里的手工改动
> 不在其中（第一次注入后门判 passed 就是因为它不在基线里）；这点与沙箱自身一致，不算缺陷，
> 但要知道。

注入文件已在仓内删除并提交（`b221f7d`），工作区恢复 87 pass / 0 fail。

## 7. 环境陷阱（这轮踩到、会重复踩）

1. **宿主 PATH 必须带 node**：本机 homebrew 的 `node` 链接缺失（`/opt/homebrew/bin/node` 不存在，Cellar 空），
   唯一可用的是 `/Users/developer/.workbuddy/binaries/node/versions/22.22.2-6/bin`。缺了就是 `cli exit=127`。
2. **UDP 17878 会被别的 luciola 产品占**：本轮是 `examples/web-radar-demo/server.js`（luciola 仓库 demo）。
   0.9.0 取消临时端口回退 ⇒ 直接 `bind_failed: discovery port 17878 occupied`，host 静默无发现。
   `product_filter` 只挡对端信标，挡不住端口被占本身。
3. **`adb shell input tap` 会打崩系统**：Pixel 6 / Android 15 上 `input tap` 与 Taskbar 叠加，
   触发 system_server `InputDispatcher` 的 `addPointers - overlap with incoming pointers` abort，
   连锁 `DeadSystemException: The system died`，全部 App 被杀。本机改用 `input tap` 的低频点击仍偶发；
   `input motionevent` 不崩但不产生有效点击（`mServedInputConnection` 仍为 null）。**注入坐标一律按设备像素**（1080×2400），
   截图给模型看是 480×1080 的缩放版，差 2.25 倍。
4. **@ 候选菜单有缓存**：宿主重启后若群页面是旧的，候选里会缺 `@codex-e2e`；
   返回列表重进（或重启 App）即恢复。

## 9. 多 agent 交互（本轮首次触达：结构通、交接未通过）

前面的 P1–P4 与 D-NEW 全部是**单 agent、单棒**（`@codex-e2e` 一个席位跑完）。本节是第一次
触达多 agent，结论必须分开看。

### 9.1 结构：通了

派单文本 `dev(codex): jsdoc forecast.js; qa(claude): test unitSymbol`（`StageChain.parseStages`
按 `角色(agentKey): 任务` 解析）。真机读数：

- 手机消息带 `agentIntent={agentId:codex, wsId:ws-weather-e2e, mode:auto}`；
- 卡面立刻变成两棒并列：`dev` / `qa`，横幅「dev 开跑（第 1/2 棒）」，状态 `进行中 / 进展 0%`；
- 宿主建链分支 `chain/cmw0dlu9h`，收尾打 `[CHAIN] … finished on branch …`。

所以「多棒声明 → 逐棒换 agent」这条链路是接上的（`DesktopStageChain.runOneStage` 用
`stage.agentKey` 起 CLI，不同棒可以是不同 agent）。

### 9.2 第一版现场：交接没走通（第 2 棒从未执行）

同一单在两分钟内以 `受阻` 收尾，原因两次都是同一条：

```
第 1 棒失败，链条已停：Escaped write: sandbox worktree had zero changes but
host repo was modified - artifacts did not enter chain; continuing would verify the wrong baseline
```

对现场取证：

- `~/weather-relay` 的 HEAD 变成 `chain/cmw0dqn6y`（**链分支检出在宿主仓里**），
  `git worktree list` 里没有本次的 worktree 条目；
- 第 1 棒（codex）的写入落在**宿主仓**：第一次是 `src/utils/forecast.js`（+15 −1），
  第二次是新增未跟踪 `note-dev.md`；而 `patchPath`（沙箱产物）始终为 null；
- 于是 `DesktopStageChain` 的越界写守卫必然触发 → 链条停在 1/2 棒 → **`qa` 那棒的 claude 一次都没跑**。

机制与那份 KDoc 记的完全一致：「worktree 隔离只是 cwd，不是强制面 —— codex 从 worktree 的
`.git` 文件里读到 `gitdir: …/weather-relay/.git/worktrees/xxx`，顺着它认出主干仓，用绝对路径
直接改」。

### 9.3 修法 P5：一链一 worktree + 就地收割

两处改动（`DesktopStageChain`）：

1. **链分支检出在自己的 worktree**（`/tmp/tidings-chains/<chainId>`），不再在宿主仓 `checkout -b`。
   跑完删 worktree、**留分支**（机主要看就是 `chain/<id>`）。
2. **判据换向**：链工作树脏了不再是「越界」，而是「它真的干了活」—— 沙箱又套了一层 worktree，
   codex 再往上一层写，落点正好是链工作树。这种改动由 `landStage` 就地 `add -A && commit`，
   不再绕 patch → apply。真正的越界只剩一条：**机主的主干仓被动过**。

### 9.4 第二版现场：交接成立，卡在第 2 个 agent 的登录态

同一提示词重跑（`chain/cmw0e4hyc`）：

- 宿主仓**全程停在 `main`、工作树干净**（P5 的第一条目标达成），worktree 跑完自动清理；
- 第 1 棒（codex）**成功**：链分支上出现提交 `chain(cmw0e4hyc) 1/2 dev: stop`，
  `git show chain/cmw0e4hyc:note-dev.md` = `hi`；
- **第 2 棒（claude）被真实拉起**：卡面「第 2 棒失败 / 进展 50%」，两棒 `dev`/`qa` 都亮过；
  失败原因是它自己的 CLI 报的：

```
{"error":"authentication_failed","result":"Not logged in · Please run /login"}
[sandbox] task t-1-db90aee3 failed: cli exit=1
```

所以**交接机制成立**：第 2 个 agent（不同的 CLI、不同的 driver）确实拿到了控制权与上一棒的产物，
失败不是编排问题，是 claude 未登录。

### 9.5 结论

- **多 agent 交互：交接已验证到「第 2 个 agent 真实接手」**（卡面 2 棒、链分支上有第 1 棒提交、
  第 2 棒独立的 CLI 启动并报自己的错）。**完整跑通（第 2 棒产出并合流）仍差一步：claude 登录。**
- 已修掉的阻塞：链在宿主仓里切分支 + 越界写守卫把「就地改动」误判成越界（P5）。
- 仍需注意：`TIDINGS_CODEX_SANDBOX=danger-full-access` 下 CLI 会按绝对路径穿越 `.git` 的 gitdir，
  隔离面只能靠「链工作树」这一层兜住；换其它 CLI 要重新验一次它的路径行为。

```
链分支：11a4fa8 chain(cmw0e9oa7) 1/2 dev: 基线 `b221f7d` 已核对一致…
```

**先纠一处误判**：上一版把 `[sandbox] harvest t-2-dc6cff01: +1 -0 / patch=133 B` 记成了
「opencode 的产物」。重新逐件核对后是反的 ——

- `t-2-dc6cff01/task.log` 是 **codex 的**格式（`Reading additional input from stdin...` +
  `{"type":"thread.started",…}`），自述「基线 `b221f7d`…现在只新增要求的 `note-dev.md`」；
- 那正是**第 1 棒 codex** 的产物，`11a4fa8` 就是它的落地提交（`1/2 dev`）；
- 该窗口只有这一个 sandbox 任务，**第 2 棒一个任务都没起**。

根因：宿主只注册三只 CLI 驱动 —— `claude-cli` / `codex-cli` / `agy-cli`
（`CliSubprocessDriver.cliDriverRegistrations`）。没有 `opencode-cli`，于是
`resolveCliDriver("opencode")` 回 null，`executeCliTask` 直接返回
`(null, "error", "no cli driver for \"opencode\"")` —— 第 2 棒连沙箱都没开就失败了。
（`CliProviderEnv.forOpencode` / `"opencode-cli"` 的凭证白名单**已经写了**，缺的是
`CliDiscovery` 的解析器与驱动注册这两截。）

**顺带否掉一条上一版的推断**：「每棒沙箱仍从主干 HEAD 起步」是错的。把 `MergeBaseRef.baseFor`
的三条 git 调用在 `chain/cmw0e9oa7` 的 worktree 里原样复算：

```
snap=98feef64  base^=83d35327  HEAD=11a4fa8   ⇒ parent ≠ HEAD ⇒ baseRef=HEAD = 11a4fa8
```

也就是说 `baseFor` 会正确取到链分支 HEAD。**交接基线目前是「未验证」，不是「已知不通」** ——
差别很大：前者只需要一个能跑的第二只 agent，后者要先改代码。

**opencode 为什么仍然用不了（实测两条）**：

1. `opencode run --standalone --auto --format json "…"` 能起、能建会话，但模型调用直接
   `{"type":"error",…"provider.transport","message":"ECONNREFUSED"}` —— `~/.config/opencode/opencode.json`
   把 provider 指向 `http://127.0.0.1:48760/v1`，那个本地网关没在跑；
2. 沙箱会把 `HOME` 换成隔离目录，`~/.config/opencode` 根本不可见 ⇒ 即使网关起来，宿主也必须
   用 `OPENCODE_CONFIG` 显式递一份配置进去（这条在白名单里，但没有任何代码去填它）。

结论更新：**多 agent 交互 = 结构通过、第 1 棒产物落地、第 2 只 agent 仍缺（claude 未登录 /
agy 上游不可达 / opencode 无驱动+无可用上游）**。交接机制本身待验，验法见 §9.7。

### 9.7 给 opencode 接上驱动：两次「环境不像它」的坑

opencode 没有驱动可接，于是补齐（全部真机/真 CLI 实测定参数）：

- **发现**：它装在 `$HOME/.opencode/bin`，不在 `$PATH` 正路 —— `CliDiscovery` 补这条约定目录；
- **装配**：`opencode-cli`，headless 参数 `run --standalone --auto --format json`（实测 v2.2.5）；
- **配置**：沙箱换 `HOME` 后机主的 `~/.config/opencode` 不可见，宿主用 `OPENCODE_CONFIG`
  递一份**零密文**的指针配置（`apiKey` 用 `{env:OPENCODE_API_KEY}` 占位）。

两次「症状长得像别的问题」的坑，都是同一分钟内的对照实验钉死的：

1. **代理**：沙箱白名单不递 `HTTPS_PROXY` ⇒ opencode 直连网关回
   `Model is unavailable`；递进去就 200。它自己不读系统代理设置。
2. **`OPENCODE_BASE_URL`**：把它也递进子进程 ⇒ opencode 按它重建内置 provider、
   丢掉配置里的 `headers` ⇒ 还是 `Model is unavailable`；设成空串也不行（存在即盖）。
   ⇒ 它只留在宿主侧，由 [OpenCodeConfig] 写进配置文件；同时配置改用**自建 provider id**
   （`tidings`），彻底绕开内置 provider 的 env 覆盖路径 —— 宿主环境是继承下去的，
   白名单只管「额外注入」，管不了「别带进来」。
