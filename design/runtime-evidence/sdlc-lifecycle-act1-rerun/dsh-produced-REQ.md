# 紫外线出行建议 · 需求说明（SDLC-HARNESS-REQ）

| 项目 | 内容 |
|---|---|
| 特性编号 | F7 |
| 特性名称 | 紫外线出行建议（UV Index & Travel Advice） |
| 文档状态 | 待实现 / 待验收 |
| 交付范围 | 仅新增本文档；不修改 `src/`、`index.html`、`test/` 等既有实现与测试 |
| 上游文档 | `docs/PRD.md`、`docs/DESIGN.md` |

## 1. 背景与目标

天气应用已经展示当前天气、7 天预报与空气质量。用户出行前除了温度和空气质量，
还需要知道**当前紫外线强度**以及**应该采取什么防护措施**。

本特性在成功态新增「紫外线出行建议」模块，用一句可执行的建议替代单纯的数值展示：

- 用户不点击、不展开，即可看到当前 UV 指数、等级和出行建议；
- 等级与建议必须稳定、可预期，不因文案润色而改变分级语义；
- 数据缺失或非法时明确降级为「暂无数据」，不得抛错、不得白屏、不得伪造数值；
- 分级与建议的纯逻辑与 DOM 解耦，可由 `node --test` 直接覆盖。

明确不做：逐小时 UV 曲线、按经纬度实时计算、推送提醒、定位权限申请、历史 UV 统计。

## 2. 术语与数据契约

### 2.1 UV 指数

UV 指数（UV Index）是表示太阳紫外线强度的非负数值，本特性统一按**四舍五入后的整数**展示和分级：

- 合法输入先校验，再执行 `Math.round`（0.5 向上取整）；
- 分级、展示、测试断言使用同一个整数，不得出现「展示 3、按 2 分级」的不一致；
- 不设置业务上限：任何有限且非负的数值都合法，`8` 及以上均为「极强」。

### 2.2 provider 数据契约

成功态数据在 `current` 下新增可选字段：

```js
current: {
  // ...既有字段
  uvIndex: 7, // number 或十进制数字字符串；可选
}
```

- `uvIndex` 缺失、为 `null` 或非法时，视为「暂无紫外线数据」，不影响当前天气、
  7 天预报和空气质量模块的渲染；
- 不从温度、云量、天气描述等字段推断 UV，避免产生虚假精度；
- 本地 fixture 可为每个城市补充一个合法 UV 值，但缺失也必须能正常降级。

## 3. 分级与出行建议（唯一权威表）

分级边界固定为：**0-2 弱 / 3-5 中等 / 6-7 强 / 8+ 极强**。

| UV 指数（取整后） | `levelKey` | 等级 | 出行建议 | 防护要点 |
|---|---|---|---|---|
| 0-2 | `weak` | 弱 | 一般无需特别防护，可正常安排户外活动；长时间暴晒仍建议基础防晒。 | 可选 SPF15+ 防晒；帽子、太阳镜按需。 |
| 3-5 | `moderate` | 中等 | 适合外出但需注意遮阳，10:00-16:00 避免长时间连续暴晒。 | SPF15+ 防晒霜、遮阳帽或太阳镜；出汗或游泳后补涂。 |
| 6-7 | `high` | 强 | 减少正午时段户外活动，外出务必加强防护。 | SPF30+ 防晒霜、每 2 小时补涂；长袖、宽檐帽、太阳镜。 |
| 8+ | `very_high` | 极强 | 尽量避免 10:00-16:00 外出；必须外出时采取全面防护并缩短停留时间。 | SPF30+/PA+++、遮阳伞、防晒衣、宽檐帽、太阳镜；注意晒伤。 |

文案要求：

- 「等级」必须严格使用上表的 `弱`、`中等`、`强`、`极强`，不得写成「较低」「很高」等近义词；
- 每条建议必须同时包含**行为指引**和**防护措施**，不得只显示「注意防晒」；
- 四个等级的建议必须互不相同；颜色只能作为辅助，不能作为区分等级的唯一手段；
- 上表文案为验收基准。实现可以调整标点或增加一句补充说明，但不得删除表中的关键短语。

## 4. 功能需求

### F7.1 读取与降级

- 从 provider 的 `current.uvIndex` 读取 UV 值；
- 合法值：`typeof value === 'number'` 且 `Number.isFinite(value)` 且 `value >= 0`；
- 合法数字字符串：去除首尾空白后匹配 `^\d+(?:\.\d+)?$`，例如 `'0'`、`' 7.6 '`；
- 其余输入一律非法，包括但不限于 `null`、`undefined`、空字符串、纯空白、`'abc'`、
  `'7abc'`、`'0x10'`、布尔值、数组、对象、`NaN`、`Infinity`、`-Infinity`、负数；
- 非法或缺失时不得抛异常，降级结果固定为：
  - `available: false`
  - `uvIndex: null`
  - `uvText: '--'`
  - `levelKey: 'unavailable'`
  - `category: '暂无数据'`
  - `advice: '暂无紫外线数据，无法给出出行建议。'`
  - `protection: ''`

### F7.2 展示

成功态在当前天气与空气质量之后展示「紫外线出行建议」卡片，至少包含：

| 元素 | `data-testid` | 内容 |
|---|---|---|
| 卡片容器 | `uv-card` | `data-level` 为 `weak` / `moderate` / `high` / `very_high` / `unavailable` |
| 数值 | `uv-value` | 取整后的 UV 指数；不可用时为 `--` |
| 等级 | `uv-category` | `弱` / `中等` / `强` / `极强` / `暂无数据` |
| 出行建议 | `uv-advice` | 第 3 节对应等级的建议 |
| 防护要点 | `uv-protection` | 第 3 节对应等级的防护要点；不可用时为空字符串 |

补充要求：

- 卡片在成功态始终存在，不可用时显示「暂无数据」而不是隐藏整张卡片；
- 卡片设置 `aria-label="紫外线出行建议"`，数值与等级以文本形式可读；
- 摄氏/华氏切换只影响温度，重新渲染后 UV 卡片内容必须保持不变；
- 同一份数据重复渲染不得产生重复的 `uv-card` 节点。

### F7.3 建议映射

- 每个合法 UV 值必须且只能命中一个等级；
- 等级、建议、防护要点由同一份分级结果派生，禁止视图层再写一套 `if/else` 边界；
- 建议内容按第 3 节表格输出，不得出现空建议或「undefined」。

### F7.4 非法输入处理

- 非法输入按 F7.1 的固定降级结果处理，进程不崩溃、Promise 不 reject、渲染不抛错；
- 降级只影响 UV 卡片，当前天气、7 天预报、空气质量必须继续正常渲染；
- 对同一个非法值重复调用纯逻辑函数，结果必须稳定且不产生副作用。

## 5. 非功能要求

- 零第三方运行时依赖，沿用原生 ES Modules；
- UV 分级、归一化、建议映射为纯函数，不依赖 DOM，可被 Node 单测直接 `import`；
- 新增测试使用 Node 内置 `node --test`，由 `npm test` 一并执行；
- 本特性不得导致既有 AC1-AC8 回归；
- 375px 与 1280px 视口下，新增卡片不产生横向滚动，长建议文本正常换行。

## 6. 验收标准（AC）

> 以下 AC 均要求可自动化验证；实现阶段的测试文件建议放在 `test/uvAdvice.test.js`，
> 但不得修改既有测试的断言来「适配」本特性。

### AC1：UV 指数分级边界完整且无重叠

**判据**

1. 边界值必须精确命中：

   | 输入 | `levelKey` | 等级 |
   |---|---|---|
   | 0、1、2 | `weak` | 弱 |
   | 3、4、5 | `moderate` | 中等 |
   | 6、7 | `high` | 强 |
   | 8、9、10、11、15 | `very_high` | 极强 |

2. 连续扫描 0-20 的每个整数，等级序列必须是：
   `0-2` 弱、`3-5` 中等、`6-7` 强、`8-20` 极强；不允许出现空洞、重叠或 `unavailable`。
3. 小数先四舍五入再分级：`2.4 -> 弱`、`2.5 -> 中等`、`5.5 -> 强`、`7.5 -> 极强`。
4. 每条输入的结果必须包含非空的 `levelKey`、`category`、`advice`、`protection`。

**自动化验证**

表驱动单测：逐项断言 `levelKey` 与 `category`；再用循环断言 0-20 的完整序列。
任一错位（例如把 `2` 判成中等、把 `8` 判成强）测试必须失败。

### AC2：四个等级的建议与防护要点一一对应

**判据**

| 输入 | 必须包含的关键短语 |
|---|---|
| 1（弱） | `无需特别防护`、`户外活动` |
| 4（中等） | `遮阳`、`SPF15+`、`10:00-16:00` |
| 6（强） | `减少`、`SPF30+`、`每 2 小时`、`太阳镜` |
| 10（极强） | `避免`、`10:00-16:00`、`SPF30+`、`遮阳伞` |

同时满足：

1. 四个等级的 `advice` 两两不同，且都非空；
2. 每个等级的 `protection` 非空；
3. `category` 严格为 `弱`、`中等`、`强`、`极强`；
4. 不存在「等级为强、建议却是弱」这类交叉错配。

**自动化验证**

对 1、4、6、10 四个代表值调用纯逻辑入口，断言 `category` 精确相等、`advice`
包含表中全部关键短语、`protection` 非空；再断言四条 `advice` 去重后仍为 4 条。

### AC3：成功态渲染 UV 卡片且不受温度单位影响

**判据**

1. 给定 `current.uvIndex = 4`，成功态必须存在唯一的 `[data-testid="uv-card"]`，
   且 `data-level="moderate"`；
2. `[data-testid="uv-value"]` 文本为 `4`，`[data-testid="uv-category"]` 文本为 `中等`，
   `[data-testid="uv-advice"]` 包含 `遮阳`，`[data-testid="uv-protection"]` 非空；
3. 依次以 `1`、`4`、`6`、`10` 渲染，卡片分别呈现 `weak`、`moderate`、`high`、
   `very_high` 与对应中文等级；
4. 同一份数据从摄氏切换到华氏重新渲染后，`uv-value`、`uv-category`、`uv-advice`
   的文本与切换前完全一致，且 `uv-card` 仍只有一个；
5. 卡片带有 `aria-label="紫外线出行建议"`。

**自动化验证**

复用现有 Fake DOM 方式的视图单测：构造带 `uvIndex` 的 fixture，调用成功态渲染函数，
按 `data-testid` 查找节点并断言文本与 `data-level`；摄氏/华氏各渲染一次后做快照式对比。
浏览器端可补充人工冒烟，但不作为 AC 通过的必要条件。

### AC4：非法与缺失输入安全降级

**判据**

对以下输入逐一验证：

```text
null, undefined, '', '   ', 'abc', '7abc', '0x10',
true, false, [], {}, NaN, Infinity, -Infinity, -1, -0.1
```

1. 纯逻辑入口不得抛异常；
2. 返回值满足：`available === false`、`uvIndex === null`、`uvText === '--'`、
   `levelKey === 'unavailable'`、`category === '暂无数据'`、
   `advice === '暂无紫外线数据，无法给出出行建议。'`、`protection === ''`；
3. 渲染包含该非法值的成功态数据时，`uv-card` 仍然存在且 `data-level="unavailable"`，
   `uv-value` 为 `--`，`uv-category` 为 `暂无数据`；
4. 同一份数据中，当前天气、7 天预报、空气质量模块仍正常渲染，节点数量与合法 UV 时一致；
5. 合法数字字符串必须被接受：`'0' -> 0/弱`、`' 7.6 ' -> 8/极强`；布尔值即使是
   `true`/`false` 也不得按 `1`/`0` 接受；
6. `current.uvIndex` 字段整体缺失时，结果与非法值一致，不得出现 `NaN`、`undefined`
   或空卡片文案。

**自动化验证**

用 `assert.doesNotThrow` 包裹逐项调用，随后断言完整降级字段；再用 Fake DOM 渲染
含非法 UV 的数据，断言 UV 卡片降级且当前天气、7 天预报、空气质量节点仍存在。
另加 `'0'`、`' 7.6 '` 两个合法字符串的正向断言，防止「一刀切拒绝所有字符串」。

## 7. 验收方式与完成定义

| 项目 | 要求 |
|---|---|
| 命令 | `npm test` 全绿，包含新增 UV 测试且不跳过 |
| 单元测试 | AC1、AC2、AC4 的纯逻辑部分全部由 `node --test` 覆盖 |
| 视图测试 | AC3、AC4 的渲染部分由 Fake DOM 视图测试覆盖 |
| 回归 | 既有 AC1-AC8 测试保持通过，既有测试文件不被改写 |
| 代码边界 | 分级与建议逻辑位于 `src/utils/` 一类纯逻辑模块，视图只消费模型 |
| 文档边界 | 本文档只定义需求与验收标准；实现与测试改动在后续开发任务中完成 |

完成本特性时，必须能逐条回答「AC1-AC4 分别由哪个测试文件、哪些断言证明」；
无法自动化的主观描述不计入验收。
