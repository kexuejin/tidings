## 三个根因（都在「门禁全绿」的前提下让功能 100% 不可用）

### 根因 1 —— 手机生成的是本地序号 id，不是协议要求的 UUIDv4 / 32 位 hex

`scaffold/composeApp/src/commonMain/kotlin/app/relay/app/RelayControllerScreen.kt` 原来用
`localMessageId()`（形如 `local-1-1791535251098`）当 `sessionId`，又用
`localMessageId().replace("-", "")`（形如 `local11791535251098`，含非 hex 字符、长度也不定）当一次性 token。

茶话间侧 `isScreenSessionId` 要求严格 UUIDv4、`isScreenToken` 要求 `/^[0-9a-f]{32}$/`，
不合格的帧在 `decodeEnvelopeObject` 阶段就被丢掉 —— **不弹邀请、不回 ACK**。
发起端因此只能等到重传耗尽，报「屏幕协助已结束 (连接已断开)」，看起来像网络问题。

修：
- `scaffold/core/src/commonMain/kotlin/app/relay/core/protocol/Ids.kt:26` 新增
  `fun newScreenToken(): String = Uuid.random().toString().replace("-", "")`；
  `:28-30` 新增 `private val HEX32 = Regex("^[a-f0-9]{32}$")` 与 `fun isScreenToken(value: String)`。
- `RelayControllerScreen.kt:82` `val sessionId = newId()`（原 `localMessageId()`）；
  `:183` `val token = newScreenToken()`（原 `localMessageId().replace("-", "")`）。
- 对称性缺口也一起收了：`scaffold/core/src/commonMain/kotlin/app/relay/core/protocol/Codec.kt:920`
  的 `validateScreen` 原来只对 `sessionId` 做 `isStr`，现在取字符串后 `isUuidV4`，
  四个 op 各钉精确键集（`ACCEPT` 额外判 `isScreenToken(token)`）——**否则本端自己发得出、收不下**。

### 根因 2 —— `TransferServer.serve` 的 `firstFrame` 先清后判，`openScreen` 永不可达

`scaffold/core/src/commonMain/kotlin/app/relay/core/transport/TransferServer.kt` 的 `serve()` 里：

    val decoded = TcpFrames.decodeBody(text)
    firstFrame = false                      // ← 先清
    when (decoded) {
        is TcpFrameDecode.Screen -> {
            if (firstFrame && frame is ScreenTcpFrame.Open) {   // ← 后判 ⇒ 恒 false

TS 参考实现（`/tmp/th_asar/out/main/index.js:2826-2831`，`FrameReader` 回调）是
**判断通过之后才 `firstFrame = false`**。Kotlin 移植把两处合并成一行前置清除，语义就反了。
后果：`lookup.openScreen(...)` 永远不被调用，每条入站 `screen-open` 连接都被 `return` 掉。

症状：手机侧 accept 后 `phase=Connecting` 等 15s；对端 TCP 明明连上了（手机能抓到
来自 192.0.2.82 的 TIME_WAIT），却始终等不到 `screen-ready`，最后
`screen-phase ended reason=disconnected`（`/tmp/orch-out.txt` 实测：t+17.5s
`"phase":"ended","reason":"disconnected"`）。

修：留下 `val isFirstFrame = firstFrame` 再清标志，`if (isFirstFrame && frame is ScreenTcpFrame.Open)`。

### 根因 3 —— ktor socket 的通道是一次性绑定的，处理器不能再自己开

修完根因 2 之后 `openScreen` 能被调到了，但 `ScreenSender.start()` 内部还会
`socket.openReadChannel()` / `socket.openWriteChannel()`。ktor 3.3.1 对同一条 socket
**只允许绑定一次通道**，第二次抛 `compareAndSet` 相关异常 ⇒ `ScreenSender` 起来就断。

修：把 `serve` 已经开好的 `read`/`write` 一路透传给投屏处理器（5 层签名）：
`OutgoingLookup.openScreen(socket, open, remoteAddress, read, write)`（`TransferServer.kt:71-88`）
→ `TransferManager.kt:258` → `NodeRuntime.kt:102` → `RelayController.kt:289-291`
→ `handleOnIncomingScreenSocket(..., read, write)`（`RelayControllerScreen.kt:401`）
→ `ScreenSender(readChannel = read, writeChannel = write)`（`RelayControllerScreen.kt:416`）。
`ScreenStream.kt` 的 `ScreenSender` 收两个默认 null 的新参数，只在调用方没给时才自己开通道。

同段还发现并修掉一条会泄漏连接的缺陷：`TransferServer.kt:250-267` 的 `acceptLoop`
原先**无条件** `socket.close()`，会把刚交接给投屏处理器的 socket 当场掐断；
现在按 `handedOff` 分流，交接后改为等 `socket.socketContext.join()` 再从 `sockets` 摘除。

## 方向一：手机当 Sharer（对端 Viewer）—— 实跑 PASS 60 帧

    python3 scripts/relay-screen-fixture.py viewer --phone 192.0.2.22 --secs 150 > /tmp/fixture-viewer2.log

夹具（`scripts/relay-screen-fixture.py`，本仓新文件）是一台「看得懂 screen 的桌面茶话间」线协议替身。
**为什么用夹具而不是真茶话间**：真茶话间 0.61.1 的桌面 GUI 只能当 Sharer（应答入站邀请），
没有「请求查看对方屏幕」的入口（`DesktopConversationsPane.kt:289` 用 `showHeader = false`
刻意绕过 `ChatHeader` 的 `screen_remote_view_action`，桌面宿主也不挂 `RelayApp` 而是直接挂
`DesktopShell`），所以「手机当 Sharer」这条只能用替身发 `screen.request`。

逐项读数（`/tmp/fixture-viewer2.log` 原样）：

    phone-profile {"nodeId":"bc19885f-...","nick":"我的手机","host":"Google Pixel 6",
                   "tcpPort":17879,"ver":"relay-0.1.0",
                   "caps":["tw1","mrec1","agn1","tbl1","rv1","rvs1","shr1"]}
    mode viewer（手机当 Sharer）
    phone-screen {"op":"accept","sessionId":"15d5f44f-e5d5-4f09-94dd-b90c8c0680b6",
                  "token":"fce3fac263734b9d8c475ed8ffc84867"}
    tcp-open-sent 15d5f44f-e5d5-4f09-94dd-b90c8c0680b6

    frame#30 864x1920 62220B jpeg-magic=ffd8

    result PASS frames 60

**怎么做的**：先 `relay-screen-fixture.py viewer` 起替身发 `{"op":"request","sessionId":<uuid4>}` →
手机上弹出「收到屏幕协助邀请 / 夹具桌面 请求查看你的屏幕画面」→ 点「同意共享」→
Android 弹 MediaProjection 系统对话框「要与"捎话"共享屏幕吗？」→
`共享一个应用 ▾` 选 **共享整个屏幕** → 点「共享屏幕」。

**期望看到什么**：邀请能落地、系统授权能走通、替身侧收到 `accept`（带 32 位 hex token）、
TCP `screen-open` 能被应答 `screen-ready`、之后持续收到真 JPEG 帧。

**实际看到什么**：全部成立，60 帧、7 种尺寸、每帧 JPEG magic `ffd8`、分辨率 864x1920
（= 1080x2400 按长边 ≤1920 缩放后的结果，与协议一致）。

**结论：通过。**

**操作坑（下次别踩）**：MediaProjection 对话框的按钮坐标必须用
`adb shell uiautomator dump /sdcard/ui.xml` 解析 `bounds` 求得，不要靠截图目测 ——
第一跑我就是靠目测点错、误触 `KEYCODE_BACK` 取消了授权。取消授权时夹具收到的是
`{"op":"reject","reason":"capture-failed"}`（不是 `permission-denied`），
手机横幅显示「屏幕协助已结束 (屏幕采集失败)」。

## 附带发现的非阻断项（未修，记录待处置）

- **`screen_reason_permission_denied` 是死字符串**：`ScreenPayload.kt:24`
  定义了 `PERMISSION_DENIED = "permission-denied"`，但代码在所有失败路径上只发
  `CAPTURE_FAILED`（`"capture-failed"`）。本次实测两次取消授权全部得到 `capture-failed`。
  设计稿 §5 写的是「权限拒绝 → reject `permission-denied`」，**文档与实现不一致**。
- **不止一个 reason 会漏成英文 token**：`scaffold/composeApp/.../Common.kt:331` 是
  `else -> reason` 的兜底分支，`capture-ended` 之类没有中文映射的理由会原样显示英文。
- **桌面端无法发起投屏**：见上文方向一的说明。设计稿把桌面列为可发起方，实际只有手机能发起。
