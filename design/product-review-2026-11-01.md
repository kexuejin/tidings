# 产品审核：这是一个产品，还是一个底座的操作面板？

审核日期 2026-11-01 · 审核对象：捎话 Tidings（手机端 + 桌面宿主，含 Agent 派单闭环）
审核尺子：`deepseek-ai/dsh-superagent-prototype` 的 `docs/000-philosophy.md`
证据来源：Pixel 6 真机截图、手机/桌面落库、源码行号、上一轮 27 秒端到端读数

---

## 0. 结论

**骨架已经是产品，肉还不是。**

把它拆成两层看：

| 层 | 判定 | 依据 |
| :-- | :-- | :-- |
| 交互骨架 | ✅ 成立 | 「群里 @ 一个人 → 它干活 → 卡片回群 → 点合并」这条链是真产品级的：27 秒闭环，人只做两个动作 |
| 产品外壳 | ❌ 没长出来 | 对外介绍是**架构描述**（"去中心化端对点传讯与私有 Agent 协同**底座**"），不是"你用它干什么" |
| 注意力账本 | ❌ 亏 | 一次任务完成，用户被动收到 3 个块，其中 2 个是工程噪音（噪音占比 2/3） |
| 概念预算 | ❌ 超支 | 5 个页签 / 11 个设置屏 / ~56 个可交互控件 / 53 处技术术语上屏 |
| 诚实性 | ⚠️ 有硬伤 | 打错字的指令被静默吞掉，用户以为生效了 |

一句话：**我们做出了一个很好的"底座演示程序"，但还没有做出"用户的产品"。** README 自己写的词是「底座」——
而底座是不该有 MainActivity 的。现在的矛盾是：底座的每一根管线都在界面上留了一个开关，
真正的用户动作（派一件活、看它干完、收下结果）只占了屏幕的很小一部分。

## 1. 尺子：dsh 的六条判据

原文核心一句：**Take as little human attention as possible, and give as much value as possible.**
"每一个消息、通知、提问、设置项、面板元素、一段文档，都在消耗某人的注意力，都必须产出比消耗更多的价值，否则删掉。"

拆成可逐条核对的六条：

1. **概念少** —— 只有领域概念，不为业务需求新增概念
2. **设置少** —— 一个默认值能覆盖几乎所有团队时，就用默认值替代设置项
3. **面板只显示待人处理的** —— 排前面的是"等你决策"，健康状态不占地方
4. **只在必须行动或能用上结果时出声** —— 干活时不吭声，请求确认一次，结果好了再说
5. **一次只问一个具体问题** —— 结构化，不埋在长报告里
6. **诚实报告** —— 草稿标未完成，失败就是失败，不为回避提问而绕过限制

## 2. 逐条核对

### 2.1 概念少 —— 不合格

用户要理解的顶层概念有 5 个页签：**消息 / 文件柜 / 节点 / 工作区 / 设置**。
其中「节点」是网络概念，「工作区」是 Agent 运行时的概念，都不是"用户想干的事"，而是"我们的实现长什么样"。

扫描到 **53 处技术术语直接上屏**（清单见附录 A），举三个最刺眼的：

- `SettingsDataSubpage.kt:300` —— 「luciola 加密信道」（**工程代号当开关名**）
- `WorkspaceDetailView.kt:344` —— 「这个工作区没有名字。对端只上报了它的标识 `ws-xxx`」，把 wsId 原文打印给用户
- `SetAvatarPage.kt:555` —— 「线上只走这 64 个十六进制」，一个换头像的页面在讲 sha256

### 2.2 设置少 —— 不合格

设置树 11 屏、约 56 个可交互控件（附录 B）。按 dsh 的判据，一个默认值能覆盖绝大多数人就该给默认值：

| 设置项 | 该不该存在 | 判据 |
| :-- | :-- | :-- |
| 默认 UDP 端口 + `udpPort` 字段名 | ❌ 删 | 99% 的人不会改；改错会导致"别人能发现你、你听不到别人" |
| 网段探测（CIDR / `/22`–`/30` / 1024 上限） | ❌ 挪进诊断，或删 | 这是运维工具，不是用户设置 |
| 能力声明（`tw1` / `mrec1` / `fd1` 三个能力码） | ❌ 删 | 协议协商应该自动，不该让人选 |
| 主题 / 通知 / 头像 / 简介 | ✅ 留 | 真用户设置 |
| 诊断（6 行读数 + 导出诊断包） | ✅ 留但降级 | 该是"出问题时才找得到"，不是首页第 8 项 |

**9 个首页条目里有 4 个是工程配置，用户打开设置第一眼看到的是「UDP 17878」。**

### 2.3 面板只显示待人处理的 —— 半合格

合格的部分：卡片的「待合并」状态、审批卡的「有 N 项高危操作等待机主审批 · 立即审批」——这正是 dsh 要的形状。

不合格的部分：**"重发"红字"、进度百分比、"第 1 版"、`+376 −46` 全在同一屏**，人要从工程读数里挑出"我该点哪个"。
更糟的是顺序错了：截图里两个「patch.diff 待接收 / 接收 / 拒绝」压在真正要决策的卡片**上面**，
人必须先做两次无意义决策才能看到那张卡。

### 2.4 只在该出声时出声 —— 不合格，且有硬伤

dsh 要求：**确认一次请求，干活时不吭声，好了再说。**

我们的现状（真机 18:29–18:30，截图 `shots/2026-11-01-e2e-before-stop.png`）：

```
18:29  @codex-e2e run sleep 300     ← 派单，正常
18:30  stp                          ← 用户想停
```

`stp` 不匹配 `DesktopWorkerOrchestrator.kt:576` 的关键词集合 `{stop, abort, cancel, 停, 取消}`，
所以它**变成一条普通群广播**：任务没停，界面没有任何提示，用户以为停了。

这是本轮审核里最严重的一条，理由不是"打字错了"，而是：
**产品把一个关键动作（停止）的实现方式设成了"记住一句咒语"，并且在咒语念错时保持沉默。**
卡片上 `AgentCards.kt` 全文没有任何停止/中止控件（grep 无命中）。这直接违反了第 6 条"诚实报告"。

#### 实测对照（2026-11-01 18:47–18:48，同一台 Pixel 6、同一宿主）

派单 `@codex-e2e run sleep 200`（18:47:12，沙箱 `t-9-e3e56d36` 启动），然后两组输入：

| 输入 | 时刻 | 31 s 后进程 | 沙箱目录 | 卡片 | 用户看到的反馈 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| `stp` | 18:47:33 | **3 个全在**（24937/24938/25128） | 在 | 无变化 | **什么都没有** |
| `stop` | 18:48:15 | 10 s 内消失 ✅ | **仍在** ❌ | **没有"已中止"** ❌ | 一条红字「[codex-e2e] 没有完成这次任务」 |

三个结论，一条比一条严重：

1. **拼错 = 静默无效。** 用户以为停了，任务还在跑，界面一个字都不说。
2. **拼对 = 被说成失败。** 我让它停，它回我一句红字"没有完成这次任务"。
   把"用户主动中止"报成"失败"，是第 6 条"诚实报告"的反面 —— 它报告的不是事实，是内部异常路径。
3. **本轮任务卡从未出现。** 截图里 `run sleep 200` 下面没有任何"执行中"卡片，
   只有上一轮 18:41 那张「待合并 · 第 1 版」。ACCEPTANCE §10d 第 4 条
   「受理 → 执行中 → 结论」在这轮**不成立**，之前那次"全通"只在结论卡上成立。

也就是说，§10d 第 5 条的两个判据（≤5 s 翻"已中止"、目录消失）**当前都不成立**，
而它当初被判"通过"，是因为验的是进程消失 —— 又是单点判据替真实体验背了书。

同类问题还有上一轮已修的那个：本地判定失败 → 挂红字「重发」→ 用户手打重发 → 队列变长。同一个病：
**用界面表达我们的内部状态，而不是用户的事实。**

### 2.5 一次只问一个具体问题 —— 未评估（这一层还没做到）

目前 agent 卡片的"提问"是零：它要么跑完，要么失败，没有"我需要你决定 A 还是 B"的结构化提问。
`AgentCards.kt` 有选项按钮的渲染能力（`:681-683`，推荐项实心），但端到端跑通的一次里没有出现过。
这不是缺陷，是**能力已备但产品化未验证**——正好是 dsh 说的"设计讨论了，原型没实现"的同款状态。

### 2.6 诚实报告 —— 有硬伤

| 现象 | 严重度 | 位置 |
| :-- | :-- | :-- |
| 打错字的指令静默吞掉，无任何反馈 | 🔴 高 | `DesktopWorkerOrchestrator.kt:576` + 卡片无停止控件 |
| 用户主动停止被报成红字「没有完成这次任务」 | 🔴 高 | 实测 18:48，截图为证 |
| 任务执行期间没有"执行中"卡片，只有结论卡 | 🔴 高 | 实测 18:47 派单，卡片区无本轮任务 |
| 卡片出现「15 个文件 +1817 −449 +1817 −449」重复数字 | 🟡 中 | `card_diff_summary = "%1$s +%2$d −%3$d"`（strings.xml:1885），而 `summary` 本身已含 `+N −N` |
| 同一份 patch.diff 推成「待接收」文件卡，同时卡片里又列一次 | 🟡 中 | 25 KB / 27.8 KB / 85.1 KB 三次复现，产物与文件消息双路 |
| 「运行自检」位置写「其它自检动作尚未接线」 | 🟢 低（但诚实） | `SettingsDiagSubpage.kt:258` —— 这句该表扬，是该有的诚实 |

## 3. 把"产品"拽回"堆砌"的三处实证

1. **一个换头像的页面有四张卡、两个只读协议键、一段协议状态说明。**
   `SetAvatarPage.kt`：选图 → 步骤 1/2/3/4 → 「线上只走这 64 个十六进制」（含 `profile.avatarHash`、
   `profileRev` 两行）→ 「保存会生效，但这张图还不上网」→ 保存。
   用户要做的事是"换个头像"，我们给了他一份实现说明书。

2. **诊断页的"适配对照"直接在产品里。**
   `SettingsDiagSubpage.kt:377` —— 「适配对照 / 顶部空白 / 导航栏 / 状态栏：真机症状与现状对照」。
   这是我们验收清单里的一节，被搬进了用户设置。

3. **工作区页面的空态在解释运行时。**
   `WorkspaceDetailView.kt:318` —— 「agent 宿主还没有为它上报会话。等它跑起来…」。
   用户不知道什么叫"宿主"、什么叫"上报"。

## 4. 已经长成产品的地方（不要推翻）

这四条是真正的产品资产，收敛时应该保住：

1. **@ 胶囊 + 帧内 `agentIntent` + 卡片回群 + 合并按钮** = 一条完整的产品动作链。
   用户不需要知道沙箱、worktree、patch，只需要"@ 它，说事，回来点合并"。
2. **27 秒闭环**（18:28:15 → 18:28:42），人只做两个动作。这是可演示、可说服人的东西。
   要如实标注它的边界：那次闭环在「一句请求 → 结论卡」这一段成立；中间的「执行中」状态
   与「中止」状态在本轮实测里都没出现（§2.4）。对外演示时说"从派活到拿到结果 27 秒"，
   不要说"全流程状态机通了"。
3. **空态文案的产品感**：「对方离线也没关系，消息会排队等它上线」（`ChatScreen.kt:1013`）——
   这句话是产品语，不是工程语。全仓还有很多句这个水准的。
4. **宽屏首启那一句**：「捎话在你自己的局域网里直接传文件，不经过任何服务器」
   （`DesktopConversationsPane.kt:544`）——**全仓唯一一句产品定位**。手机端一句都没有。

## 5. 若只做三件事

按"每投入一分，注意力账本改善多少"排序：

**第一件：给停止做成按钮，咒语留作后路。**
卡片右上角加「停止」，按下即 `onAgentAbort`；文本关键词仍保留（老用户/脚本）。
同时在"发给 agent 但没被识别成指令"时给一次轻确认：「这条只是群消息，Agent 不会收到动作 —— 要派活请用 @」。
这一条同时修掉审核里最严重的诚实性硬伤，和第 5 条"一次只问一个具体问题"的口子。

**第二件：把设置砍到 4 项。**
资料 / 通知 / 外观 / 数据（含备份）。把「连接」「能力声明」「网段探测」整体移到诊断页下的
「高级」，并从设置首页移除；诊断页本身从首页下移到"版本与更新"下面，或改成一个 5 次点击的入口。
9 → 4，是这一轮能拿到的最大注意力收益。

**第三件：卡片只说人话。**
- `card_diff_summary` 去掉重复的一次 `+N −N`（`strings.xml:1885` 或调用处改传不带增删的 summary）
- 「第 1 版」→ 只在有多个版本时才显示（或改成"已更新"）
- 产物不再以独立「文件待接收」消息推送，收进卡片产物区（现在同一份 patch 让人决策两次）

做完这三件，噪音占比会从 2/3 降到接近 0：一次任务只剩"一句请求 + 一张卡片 + 一个决定"。

## 6. 最后一句实话

用户问的是"是不是真产品，而不是功能堆砌"。诚实的回答是：

> **交互层已经是一个产品，外表面还是底座的调试台。**
> 我们不是因为不会做产品而像底座 —— 是因为一直在**同时**服务两类人：
> 用它的同事（要一键派活）和调它的我们（要看见 UDP 端口、CIDR、能力位）。
> 这两类人的界面混在同一棵树里，于是设置页第 8 项是"适配对照"，第 1 项是"UDP 17878"。

dsh 的做法是把它们分开：`docs/006-deployment.md` 讲运维，面板只讲"谁需要你"。
我们该做的是同一件事：**把调试台挪到诊断里，把产品的第一屏还给"你要干什么"。**
